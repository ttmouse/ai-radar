## 1. 今日最值得研究的 Observe：Serval Simulations

**产品**：[Serval](https://www.serval.com/) / [Simulations 官方发布](https://www.serval.com/blog/simulations) / [完整 Docs](https://docs.serval.com/sections/documentation/helpdesk/simulations) / [Catalyst 技术说明](https://www.serval.com/blog/how-an-ai-it-workflow-builder-actually-works)。

**状态：Observe；Tracking 5/5；Mechanism Novelty 2/4；Evidence B（官方文档足够详细，但无独立真实成功率）；新增 Pattern：否。**

### 1.1 真实问题：Agent 改了 Skill 后，如何证明没有破坏原本正常的业务？

IT 服务台的 Agent 可以处理设备申请、权限开通、入离职。一次对 Skill、表单或流程的修改，可能让某个旧员工类型、权限范围或审批条件失效。传统 ITSM 管理员在真实请求里发现错误，代价可能是错误授权或真实订单。软件开发有自动化回归测试，但 Agent 面对的是非固定话术、不同人员、工具调用与外部副作用。

**旧工作流**：管理员配置 Skill/Workflow → 测试一两条 Happy Path → 发布 → 员工真实请求触发 → 发现边界错误 → 回滚/人工补救。

**新工作流**：
```text
历史真实工单 / 人工定义的业务边界
    ↓
Catalyst 生成 Scenario（待人确认）
    ↓
Scenario Config + Expected Outcome + Revision
    ↓
Simulated Requester（LLM 扮演员工）
    ↓
真实 Help Desk Agent（可 pin 草稿 Skill/Workflow 版本）
    ↓
Mocked Tool/Workflow（默认不触碰真实系统）
    ↓
Judge（比较结果是否满足预期，不强制固定话术）
    ↓
Test Suite / Pass-Fail / Transcript / Versioned Evidence
    ↓
Human 审核失败原因与修订，决定发布
```

### 1.2 关键产品机制：测试对象从固定函数变成“业务情境与可接受结果”

官方示例：承包商申请笔记本，应收集 Sponsor 和合同到期日，并交 Sponsor 而不是直属经理审批。旧 HR 记录将其称为“Contingent worker”，新流程只识别“Contractor”，模拟套件揭露这个遗漏；Catalyst 协助分析失败原因，管理员修复后再发布。

- **Scenario Config 是可版本化对象**：requester、opening message、scenario context、expected result；一个 Suite 由多个 Config 构成，运行记录绑定 Config Revision，避免修改测试定义后混淆历史结果。
- **真实被测对象是生产同类 Help Desk Agent**，并可 pin 草稿/历史 Skill、Workflow 版本。外部 Workflow 默认 Mock；少数 Workflow 可明确确认后 live run，**live 副作用不可撤销**。
- **Judge 检查结果语义而非对话逐字一致**；甚至 “Not resolved” 也可以通过测试，如果预期是正确升级给人工。
- **Catalyst 可以从历史工单起草 Scenario**，也能调查失败，但官方 Docs 明确：它不会自动修改、发布或重跑；生成覆盖不等于已验证覆盖。
- **正式可用性边界**：官方发布称可用，Docs 明确写 **Beta**、需要 Test & Release capability 开通；不等于对所有客户 GA。

### 1.3 Composable Test：为什么不能评为强机制创新？

**1–2 天可以复刻 80% 演示**：历史工单 → LLM 生成 JSON 测试场景 → 用现有 Agent Runtime 调用被测 Agent → mock MCP 工具 → LLM Judge 评分 → SQLite 保存 run_id、revision、trace → CI/Gate。LangSmith、promptfoo、Agent Eval、GitHub Actions 等已提供基础部件。

**难以随手拼好的部分**：多版本 Skill/Workflow 精确 pin、真实授权隔离、工具调用 Mock/Live 边界、长期回归集版本比较、误判校准与权限控制。但这些是可靠工程化和产品集成，不是全新的 Human/AI/Software 组织方式。

**Mechanism Delta**：从“用几条聊天记录评估 Agent”变成“把业务情境、可接受结果和副作用隔离构造成可版本化的交付 Gate”。这是已有 #15 Proposed Action、#13 Deterministic Split、#20 Agent Operations Agent、#24 Evidence Gap → Active Investigation、#05 AI Build → Software Run → AI Repair 的重要落地；还不能证明新 #31。

### 1.4 Human / AI / Deterministic Software

| 角色 | 责任 | 必须保留的边界 |
|---|---|---|
| Human | 定义正确结果、审批测试案例、确定发布与真实权限 | 不把模型自评当成现实验收 |
| AI | 扮演请求者、生成测试候选、被测 Agent 处理任务、辅助失败归因 | 不能自己改写验收标准后自判通过 |
| Deterministic Software | 固定配置与版本、拦截副作用、权限、记录真实 Trace、执行 Gate | Mock 输出不是外部系统真实完成的证据 |

### 1.5 架构事实、推断与未知

**已确认**：Config/Suite/Revision、draft pin、Mock 与受权限保护的 Live workflow、Trace、Judge verdict、Suite pass-rate history、真实工单生成场景均在官方 Docs 有明确说明；运行详情保留每轮所考虑的 Skill/Workflow/Knowledge。

**合理推断**：测试 Runtime 至少需隔离工单对象、工具拦截器、Scenario revision、run parameters、agent/tool traces 与版本引用。LLM Requester/Mocker/Judge 很可能会产生相关性偏差。

**未知**：真实业务回归覆盖率、Judge 的误通过率/误拒绝率、Mock 与真实第三方系统行为差异、跨模型和 Prompt 版本的稳定性、历史工单覆盖长尾场景的程度。官方未提供独立对照的实际事故下降率。

### 1.6 最大反证：三个模型可能在共同“演一场正确的戏”

**模拟员工不是员工，模拟审批成功不是实际审批成功，LLM Judge 也不是业务事实来源。** 被测 Agent、Mocker、Judge 可能共享相似错误假设。特别是“承包商”字段，模型可在模拟中宽容处理，但真实 HR API 可能返回另一种枚举或拒绝访问。

Docs 明确说明 Mock 对话不能验证浏览器表单校验或真实外部系统提交。这一点比产品的通过率图更重要。必须区分：**模拟通过、接口集成通过、真实业务验收通过**。

### 1.7 对本地 Agent / AI 原生研发 / 应急 B/G 的最小迁移

有 Agent Runtime、CLI、SQLite、MCP、浏览器和文件访问时，**直接复刻 Scenario/Suite/Run/ExpectedResult/ToolTrace/MockPolicy 五个对象**，而不是购买或复制完整 ITSM：

1. 为现有本地 Agent 建 10 条真实失败/边界场景（权限不足、资料缺失、重复操作、状态已改变、外部 API 返回异常等）；固定预期结果，保留每次测试的配置版本。
2. 使用 Tool Gateway 的 Mock 模式隔离所有正式写操作，要求测试至少包含一个独立于模型的断言（如数据库状态未变、没有正式发文、没有真实授权）。
3. 逐条对照真实集成测试与人工验收，记录 false pass、false fail、执行成本和修复后回归结果。禁止仅凭 LLM Judge 的绿色分数发布高风险动作。

**应急管理**：构建“检查点—证据—结构化事实—检查结论”测试集，分别模拟无证据、证据模糊、重复上传、责任主体错配、历史整改已关闭但新证据冲突。Agent 可以生成隐患建议，确定性系统应阻止证据不足时自动生成正式隐患结论或督办文书；最后由专家裁决。

**不值得抄**：多 Agent 角色数量、漂亮的通过率仪表盘、模型自判即放行、把模拟结果混进真实检查数据。**跟踪 5/5**，优先寻找独立的假阳性/假阴性和真实生产回归数据。

## 2. Fresh Observe：Radar AI Investigations

**来源**：[Product Hunt 10/29](https://www.producthunt.com/products/radar-7) / [Apache-2.0 开源仓库](https://github.com/skyhook-io/radar) / [官方 50 故障基准与原始结果](https://radarhq.io/benchmark/ai-sre-tools)。

**Observe；Tracking 4/5；Novelty 2/4；Evidence B（开源 + 公开测试数据，仍是厂商设计/执行实验）。**

Radar 把 Kubernetes 资源拓扑、事件/变更时间线、日志、归属关系和风险上下文统一提供给人类 UI 和 MCP Agent。用户点击 Investigate，现有 Claude Code/Codex/Cursor 在只读模式调查，按证据给出根因和修复建议；实际修复需批准。不是“新的 AI SRE Agent”，而是把真实运维状态组织成 Agent 能消费的操作模型。

官方发布 **50 个 SREGym 故障 × 6 个工具** 的逐条结果：Claude Code + Radar MCP 44/50、kubectl-ai 41/50；平均耗时 79 秒 vs 288 秒。报告也承认每个故障只计一次，差一两题可能是随机波动；部分工具未启用 Prompt Cache，AWS 产品使用不同不可选模型，成本对比不能简单解释为相同条件。**这不是独立第三方 Benchmark。**

**有价值的细节**：创始人回答，警告/严重程度分类尽量保守，最近变更更多作为上下文，而不是强行给 Agent 一个“很可能就是这里”的高置信结论。否则 Context 包装方式本身会误导模型。

**Composable Test**：Kubernetes Watch + Prometheus/Logs + MCP + 现有 Coding Agent 可拼主要体验；生产级关联/可靠性需要工程投入。机制已被 #29 Operational Model、#24 Active Investigation、#13 Split、#15 Proposed Action 覆盖。新证据是结构化上下文在真实故障评测中可能比“更强 Agent”更重要，而不是新 Pattern。

**对 B/G 迁移**：不要把“风险等级上调”或“最近整改”直接当成隐患根因；为 Agent 提供有出处、时间戳和置信边界的上下文。**跟踪 4/5**，关注跨集群/跨系统因果证据和修复后验证闭环。

## 6. 今日结算

**Core 0｜Observe 2｜Reject/去重 4｜Maturation 3｜新正式 Pattern 0。**

**最值得记住的一条产品创新养料**：

> **AI 原生软件的测试，不是让几个模型互相演示“任务成功”，而是把可验证的业务结果和真实副作用作为边界。** 模拟可以帮助发现问题，不能自行生产事实。Human 负责验收定义与责任，AI 负责生成/探索/诊断，Deterministic Software 负责版本、权限、隔离和可独立核查的证据。

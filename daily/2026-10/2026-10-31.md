## 1. 今日重点 Observe：ilse —— 在真实 UI 上指明修改对象和影响范围

**产品**：[ilse 官方产品入口](https://ilse.design/en) / [10/30 Product Hunt 发布与创始人答疑](https://www.producthunt.com/products/ilse)。  
**状态**：Observe；Tracking 4/5；Mechanism Novelty 2/4；Evidence B/C（功能有具体说明和演示，真实可靠性、测试覆盖尚未独立验证）。**不新增 Pattern。**

### 1.1 真实问题与旧工作流

用户是设计师、产品经理、前端协作者，以及已有 React 代码仓库但不愿手工查找组件和文件的人。看到运行页面中某个按钮、间距或组件有问题时，传统 Agent 工作流要求人先把视觉位置翻译成文字：截图 → 描述「右上角第二个按钮」→ Agent 搜索代码 → 猜测对应组件 → 修改 → 运行 → 用户指出改错对象/破坏其他页面 → 再次修改。

关键损耗不是模型不会写 CSS，而是**人看到的 UI 实例、代码组件定义、设计 Token 和影响范围之间缺少明确的交接对象**。

### 1.2 新工作流与具体机制

```text
Human 打开正在运行的 React 应用
    ↓
直接点选 UI 元素 / 拖动 / 描述要改什么
    ↓
ilse 建立 UI 元素 → 源码文件/行/组件的定位
    ↓
Human 指定作用范围：Only this / All
    ↓
可确定的 Token / CSS Class 改动 → 软件直接修改（不必调用 AI）
语义不确定的布局/交互修改 → 现有 Claude Code/Codex/Cursor/Gemini Agent
    ↓
本地代码变化 + 运行预览
    ↓
Human 审核是否符合设计意图和其他实例约束
```

**产品机制细节（均来自 10/30 创始人在 PH 的公开说明）：**
1. 点击元素可把目标定位到源码文件/行，而不是仅把截图传给 Agent。
2. 对重复组件明确询问 **Only this / All**；默认只修改当前实例。Only this 尽量通过使用位置的 className/prop 实现，必要时加可选 prop，不直接修改所有实例；All 则修改组件定义。此为厂商描述，尚非对所有 React 结构的保证。
3. 读取 Tailwind 配置、CSS 变量或 tokens.json，让确定性修改尽量落在项目自己的设计尺度；简单 class 映射由软件直接执行，复杂修改才交给 Agent。
4. 可从现有组件生成 DESIGN.md 供 Agent 读取。**Test Mode 处于创始人预售阶段**；开发者表示当前能发现多尺寸横向溢出，但尚不能稳定检查德文长词溢出、阿拉伯语 RTL 细节。不能把宣传中的全流程测试当作已成熟能力。

### 1.3 Mechanism Delta / Composable Test v2

**Before：** 视觉反馈 → 自然语言转述 → Agent 猜测目标代码和影响范围 → 修改。  
**After：** 人在真实 UI 中提供位置与范围信号 → 软件建立实例/组件/Token 约束 → Agent 只处理非确定性部分 → 人审核结果。

**80% Composable Test：** 对单个 React 项目，现有 React inspector/source map、浏览器 DevTools、Tailwind Token、AST/Codemod、Claude Code CLI、Git Diff 与 Playwright，可以在 1–2 天内做出「点选元素→定位文件→修改→预览」的主要演示。通用化的多框架映射、组件作用域可靠性和复杂样式传播需要长期工程化，但技术困难本身不是新机制。

**结论：Composable but Structural 的局部组合，但不足以评为新的强独立机制。** 它把 #01 Human Signal + Machine Context、#13 Deterministic / Probabilistic Split、#15 Proposed Action、#10 Artifact → Semantic Object、#28 Generation as State Transition 组合在更贴近设计现场的输入层；目前缺少证据证明新的持续一等业务对象或不可被旧模式解释的默认工作方式。

### 1.4 Human / AI / Deterministic Software 的责任变化

| 角色 | 过去 | ilse 所提议的新分工 |
|---|---|---|
| Human | 截图、描述元素、解释「别改其他地方」 | 在 UI 直接指向对象、指定 Only this / All、确认设计意图和结果 |
| AI | 自己推断目标文件和样式并修改全部内容 | 仅处理需要语义判断的复杂变更；不必负责所有确定性 Token 操作 |
| Deterministic Software | 运行应用、保存代码 | 维护 UI→源码映射、设计 Token、修改作用范围、Git 可追溯变更 |
| 最终责任 | 人发现改错再纠正 | 人仍负责审查副作用、回归与发布；AI 不能替代真实验收 |

### 1.5 架构事实 / 推断 / 未知

**已确认（官方/创始人公开声明）：** React 应用覆盖范围、`npx ilse-design@latest` 安装方式、元素定位、Token 读取、Only this/All、使用用户自己的 Coding Agent、Test Mode 尚在预售、已知本地化测试缺口。

**合理推断：** 实现需要开发环境注入 UI Inspector、源文件定位元数据、组件使用位置与定义位置的区分、CSS Token 映射和 Agent CLI 调用；但不能由此认定其实际 AST 实现、Runtime 内部协议或 Eval 设计。

**未知：** 在嵌套组件、Portal、CSS-in-JS、动态渲染和跨页面复用时的定位准确率；Only this 是否总能避免影响其他实例；Token 变更是否经过视觉回归；复杂项目安全边界；真实用户节省时间及误改率。

**最大反证：** 如果 Only this 仍频繁修改共享组件，或者 UI 定位依赖易失效的文件行号，用户只是从「解释给 Agent」转为「修复 Agent 的错误定位」，并未真正减少净人工投入。

### 1.6 可迁移产品原理与最小复刻

**可迁移原理：把「我指的是哪一个对象」「这次改变影响哪些实例」「哪些约束不许突破」前置为明确输入。** 不要把这些本可确定的信息留给 LLM 猜。

对已有本地 Agent Runtime/CLI/浏览器/MCP/文件访问，最小复刻：
1. 在现有 React Demo 叠加元素选择器，捕获 DOM 节点、组件定位、文件/行和 Token 上下文。
2. 人确认 **当前实例 / 所有实例**，生成一个可审核的 ChangeRequest；简单 Token 修改用确定性补丁，复杂修改交给 Agent。
3. 对 10 个真实设计修改任务，记录错改范围次数、完成时间、回滚次数及其他实例是否被误伤。

**不值得抄：** 重新造 Coding Agent、为改一个间距增加复杂 Agent 编排、未验证就让 AI 全量重写设计系统、以「节省 Token」替代最终质量指标。

**对应急管理/B/G：** 类比专家在企业台账、隐患证据、检查点上直接圈选具体事实，并明确「只修正本条证据」或「对同类检查点规则统一修正」；前者是实例级判断，后者是规则级变更，必须具有不同权限、影响面和审批路径。不要把两者混成一条自然语言指令。

**继续跟踪 4/5**：优先观察源码定位、作用域隔离和真实回归数据。

## 2. Fresh Observe：Chopstick —— 从用户重复行为发现应该出现的操作入口

**来源**：[官网](https://chopstick.sh/?ref=producthunt) / [10/30 Product Hunt 与开发者问答](https://www.producthunt.com/products/chopstick)。  
**状态**：Observe；Tracking 4/5；Novelty 2/4；Evidence B。

Chopstick 在 Mac 上本地记录活动与跨应用切换，寻找跨多日的重复模式，建议自动生成可执行脚本的 Notch Widget；用户确认并可编辑，连接现有 Claude Code/Codex/Cursor 等 Coding Agent 编写 Widget。创始人称可排除指定 App/网站、过滤常见秘密模式，Widget 可按条件出现并随着工作流更新状态。官网有应用时间线与常见切换示例，但**未公开独立的误识别率、建议采纳率或本地日志审计**。

**旧：** 用户发现重复动作 → 自己配置 Keyboard Maestro / Raycast / Shortcuts。  
**新：** 软件观察活动 → AI 提出值得自动化的候选 → Human 确认 → Agent 生成 Widget/脚本 → 确定性软件在触发条件下运行。

**Composable Test：** macOS Activity/Accessibility 事件、SQLite、本地 LLM/CLI、AppleScript/Keyboard Maestro 和菜单栏/Notch Widget 可以组合主要体验。它非常明确地强化现有 **#08 Observe → Detect Pattern → Propose Automation**，并结合 #05 AI Build → Software Run、#06 Proactivity 和 #09 Generative Interface；**不新增 #31**。

**值得验证的不是「能生成多少 Widget」，而是建议是否比手工建立快捷方式更省事。** 指标：有效建议率、用户采纳率、误触发率、节省净时间、权限/隐私风险。对现有 Keyboard Maestro 用户，先用 7 天活动记录与人工审核候选自动化，比迁移到新 Widget 平台更低成本。

## 6. 今日结算

**新 Core：0；Observe：2；Reject/去重：4；Maturation：3；新正式 Pattern：0。**

**今天最值得记住的一条产品创新养料：**

> **Human 的优势不是把现场翻译成更长的 Prompt，而是直接指出对象、影响范围和不可破坏的约束。AI 的优势是处理剩下的不确定性。Deterministic Software 应承担定位、作用域、Token、版本与副作用验证。**
>
> 对一个真实 UI 实例的修改与对一个共享组件/业务规则的修改，可能只差一个「Only this / All」，但它们的权限、风险和验收标准完全不同。

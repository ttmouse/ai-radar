## 1. 今日最值得拆解的 Fresh 候选：SurgePix（Observe，不是 Core）

**入口**：[官网](https://surgepix.ai/) · [10/26 Product Hunt](https://www.producthunt.com/products/surgepix) · [官方 GitHub Agent Skills](https://github.com/SurgePix/agent-skills)

**Tracking：4/5；Mechanism Novelty：2/4；Evidence：B（官方产品说明与开源 Skill 可核查，核心跨界面语义连续性未验证）；判断：Observe。**

### 真实问题与旧工作流

市场团队或设计师用 AI 做海报、社交图、PPT 视觉，通常得到一张合成图。要修改一句标题、一个图层、某个局部，又容易触发整体重生成；要将同一视觉用于多个 Agent 流程，往往只能交接 PNG/URL，而不是可编辑的设计对象。

**旧工作流：** Prompt → 生成扁平图 → 下载 → 人在编辑器中重建文字/图层 → 修改 → 导出 → Agent 如需复用则再上传。

### 新工作流（官方描述）

1. Human 指定视觉目标、品牌要求与局部修改。
2. Designer Agent 生成视觉稿；用户在画布中编辑文字、图层、局部区域。
3. 可通过官方 Skills 在 Claude Code / Cursor / Codex 等环境中调用图像生成、修改、去背景、PPT 等服务。
4. 人在 UI 内继续修改或让 Agent 在外部流程里调用生成服务，最终导出文件。

**已确认的官方公开能力**：Product Hunt 声称完整图层可编辑、文本可替换、区域可重绘、品牌素材可用；官方 GitHub 提供 SKILL.md 兼容的生成与编辑脚本、API Key、异步任务轮询、sessionId。上述是“厂商公开的产品能力和接口设计”，并非独立验证效果。

### 最关键的反证：UI 的 Layer 和 API 的 Image 不是同一个已证明的对象

官方 Agent Skills README 明确列出：
- `surgepix-image-edit`：输入参考图片与指令，输出 **PNG**；
- `surgepix-generate-poster`：输出 **PNG**；
- `surgepix-generate-presentation`：输出 **PPTX**；
- `sessionId`：可将多轮请求归入同一个会话。

**但在目前公开的 Skill 文档里，没有看到可验证的 API 能力证明：Agent 能读取画布的图层树、针对某个稳定 layer_id 修改、保留图层之间的语义约束，再把编辑后的原生对象无损交回同一画布。**“没有看到公开证据”不等于厂商没有该能力；必须进一步验证。

这就形成了三个等级：

| 等级 | 交付含义 | 目前证据 |
|---|---|---|
| L1 像素可修改 | 用图片+Prompt 重绘，输出新的 PNG | 官方 Skill 文档支持 |
| L2 结构可修改 | 在 UI 中修改文字、局部图层 | 官方 Product Hunt/团队声明支持；未独立实测 |
| L3 业务语义可持续 | UI ↔ Agent API ↔ 文件之间保持同一对象身份、图层约束、版本和可追溯编辑 | **尚无充分证据** |

**机制判断**：它可能把“图像生成”升级为“可编辑视觉对象”，但现有证据不足以证明跨 Human UI / Agent Runtime 的统一持久设计对象。

### Composable Test v2

用现有图像 API + Canvas/Fabric.js + 分层编辑 + SKILL.md + 文件存储，1–2 天能拼出大部分演示：生成图、改文字、局部重绘、把图片返回 Agent。要实现长期稳定的原生图层 ID、版本化语义 Diff、跨端无损回写和约束验证，难度显著更高；但**目前没有证据证明 SurgePix 已把这一层做成默认工作机制**。

因此：**Composable but Structural（潜在）/ Observe**，不能凭“图层可编辑 + Agent 可调用”两句宣传就评 Core。

### Human / AI / Deterministic Software

| 角色 | 可能的新职责 | 证据边界 |
|---|---|---|
| Human | 定义视觉意图、局部审美判断、选择发布 | 官方交互描述 |
| AI | 生成视觉、按指令改局部、在外部 Agent 工作流中调用服务 | 官方产品和 Skills |
| Deterministic Software | 保存文件/会话、调用任务、维护 UI 图层、导出 | 公开接口能确认文件与任务；跨端原生对象同步未知 |

**架构事实**：API Key、任务异步轮询、Skill 脚本、sessionId、PNG/PPTX 输出。**合理推断**：UI 可能有内部图层对象模型。**未知**：稳定对象 ID、Memory、Runtime、图层级 Tool、Approval/Eval、回滚、跨端一致性、真实用户净投入。

### 与已有 Pattern 的关系

- **#10 Artifact → Semantic Object → Action**：从视觉文件变为可操作对象；当前证据主要到 L2。
- **#13 Deterministic / Probabilistic Split**：AI 生成、编辑器维护结构，但约束边界未披露。
- **#28 Generation as State Transition**：多轮修改同一工作对象；API session 不等于原生对象连续性。
- **#27 Context Belongs to Work**：只有在设计对象跨 Agent 和人的编辑中持续继承上下文时才构成增量。

与 [UseIt Studio](../products/useit-studio.md)（10/24）及 10/25 的 zCAD AI 对照，SurgePix 更接近“可编辑视觉”，UseIt 强调“可生产文件”，zCAD 强调“参数/装配约束”。**新的是一条更精确的跨产品反证问题，不是新的模式 #31。**

### 可迁移原则与最小复刻

**对 AI 原生研发 / 本地 Agent**：不要把 `sessionId` 当作 `artifact_id`。一个最小的可复刻对象应有 `artifact_id`、`revision`、`element_id`、`edit_intent`、`semantic_diff`、`validation_result`。先用现有 CLI/MCP/文件访问与 SVG/JSON Scene Graph 复刻“对同一对象的增量编辑 + 可复核 Diff”，不必复制图像模型或设计画布的复杂视觉交互。

**对应急管理 / B/G**：检查报告 PDF 可以多次生成，但真正的持久对象应是隐患 ID、证据 ID、责任主体、整改状态、复核结论及其关系。AI 生成或改写文书时，不得隐式重建、丢失或替换这些关系。

**不值得抄**：一堆图像生成 Skill、营销式的“Agent-callable”标签、仅靠新 PNG 覆盖旧 PNG 的“多轮编辑”。

**最大未知 / 降级条件**：若 UI 中的图层编辑只是一次性分层输出，或外部 Agent 只能做图片级重新生成且无法继承同一对象，长期机制新颖性降至 1/4。**继续跟踪 4/5**；下一轮要求完整的“UI 建稿 → Agent 改指定 layer → UI 接续编辑 → 导出/回导”实测和对象结构证据。

## 2. Fresh Observe：Kiwi（不是 Core）

**来源**：[10/26 Product Hunt 与创始人讨论](https://www.producthunt.com/products/kiwi-7) · [官网](https://heykiwi.co/)

**Tracking 3/5；Novelty 1–2/4；Evidence C/B。**

Kiwi 主张持续监控行程、账单、包裹和空闲时间，在 iMessage/WhatsApp 主动发消息；用户同意后才去网站操作。创始人表示：航班延误属于高优先级通知，周末活动建议只在适合时提出；只有第三方确认预订才应告诉用户“已预订”，并承认有网站的人机验证会阻断执行。

**可迁移机制**：Proactive Detection → Relevance Gate → Human Consent → Action → External Confirmation。关键不是主动提醒更多，而是降低打扰和避免把“Agent 已尝试”当作“业务已成功”。

**Composable Test**：日历/邮件触发 + LLM + WhatsApp + Browser Agent + Approval 可在 1–2 天复刻主体验。#06 Persistent State、#15 Proposed Action、#17 Judgment Queue、#26 Agent-facing System of Record 已覆盖。独立通知精度、真实预订完成率、用户净投入时间未知；不新增 Pattern。

## 3. Maturation：Tiden（历史 Core，今天新增独立证据，不重复入选）

**入口**：[Tiden Changelog（10/23）](https://tiden.ai/changelog) · [Docs](https://docs.tiden.ai/) · [10/19 历史研究](https://github.com/ttmouse/ai-radar/blob/main/daily/2026-10/2026-10-19.md)（历史 GitHub 文件目前缺失，不应视为可访问档案）。

10/19 研究结论是 **Intent → Independent Evidence → Delivery Gate**：Agent 生产代码和测试，持久 Spec 及实际运行证据由独立 Gate 计算；归入 #30 Intent as Source of Truth，不新增 Pattern。

**10/23 的真实机制增量（厂商 Changelog 已确认）**：
1. **关闭未合并分支但保留 Spec、关联测试、Review 与 Run History**。过去“放弃”意味着删除这段历史，现在拒绝交付的过程本身也成为可追溯的长期记录。
2. **会话 Gate 仅使用该 Intent Branch 自己的最新测试运行**，避免 main 或其他分支的绿色结果误证明当前任务。
3. **Issue 关闭/忽略/重开可记录原因**，理由附着于当前状态，后续状态变化会替换/清除；这让裁决有理由，但尚不是不可篡改的完整历史证明。
4. Merge Preview 标出重复测试；目前仍要求人手动删除重复项，**并未自动解决所有重复问题**。

**研究判断**：最重要的不是更多测试，而是**失败、放弃、拒绝和例外也必须有独立、可追溯的业务状态**。这强化 #15 Proposed Action、#21 AI Work as Shared Artifact、#27 Context Belongs to Work、#30 Intent as Source of Truth；仍不新增模式。

**对本地 Agent 的最小复刻**：为每次任务记录 `intent_id / branch / promises / evidence_run_id / verdict / reason / disposition / actor / timestamp`；允许 `abandoned` 但不能删除历史证据。严禁把其他任务/分支的测试结果拿来证明当前任务。SQLite + Git + CI 足以验证这个机制，无须复制 Tiden 全平台。

**最大反证**：保存完整历史不代表 Spec 正确；Agent 生成 Spec 与测试仍可能同源偏误。真实误放行率、维护成本、审查时间未有独立对照。**历史 Core 维持，跟踪 5/5；今日新增 Core 仍为 0。**

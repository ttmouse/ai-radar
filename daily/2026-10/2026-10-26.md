## 1. 今日最值得继续研究：Hycli（Observe，非 Core）

**资料**：[Hycli 官方开源仓库](https://github.com/Hybirdss/Hycli) · [README](https://github.com/Hybirdss/Hycli/blob/main/README.md) · [10 月 25 日 PR #69](https://github.com/Hybirdss/Hycli/pull/69)

**评级**：Tracking **4/5**；Mechanism Novelty **2/4**；Evidence **B（源码、官方设计与测试描述可见；独立跨站实测不足）**。

### 真实问题

本地 Agent 想操作没有正式 MCP 的业务网站时，通常只能反复看网页、点击、等待、猜测表单状态；网站一变，操作流程容易失效。另一方面，让模型直接持有浏览器 Cookie、自由提交表单，也会把技术能力误当成业务授权。

### 旧工作流

```text
Human 指定网站与目标
→ Agent 每次临时阅读页面 / 操作浏览器
→ 在视觉或 DOM 上寻找按钮、表单、记录
→ 直接提交或反复尝试
→ 失败后重新探索；动作语义与权限难以复用
```

### 新工作流（厂商描述）

```text
Human 指定站点与目标
→ AI 检查文档、OpenAPI/GraphQL、前端代码和浏览器网络证据
→ 生成结构化 SiteSpec、CLI 子命令与 MCP 工具
→ 在不进行真实写入的条件下验证可安全读取的动作
→ Human 对该站点开启写权限（默认关闭）
→ Agent 通过已准备的工具执行
→ Deterministic Check 重放已验证读取链，区分登录失效、站点变化、阻断、不可达
→ 必要时修复能力定义，而不是每次重新让模型猜页面
```

**已确认的产品设计**：官方 README 描述三名 AI worker、SiteSpec、CLI/MCP、按站点关闭写权限、凭据本地保存、只读链检查，以及写入结果不确定时不自动重试。项目使用本地引擎与浏览器能力；官方发布物和源码可访问。上述事实指**官方可核查的设计与代码描述**，不是独立证明所有网站均可工作。

**关键机制**：把临时的“浏览器观察”转成可复用、可检测漂移的**能力定义（Capability Definition）**，并将发现、验证和执行拆开。能力定义与执行凭据分离；Agent 不必直接读取真实 Cookie。

### 最有价值的反证：真实网站语义并不等于 URL 字面语义

10 月 25 日项目 PR #69 描述了一个真实的设计缺陷：部分网站通过 `GET /submit` 返回写操作所需的 CSRF Token。Hycli 的安全启发式曾把 URL 路径里的 `submit` 判为写入意图，连获取 Token 的**只读前置步骤**也被阻止。PR 尝试允许写操作内部的同源只读 preflight，但继续拦截危险查询参数；截至本轮读取该 PR 仍为 **open，未合并**。

这说明“按路径名称推断动作副作用”不是可靠的业务语义。安全策略不能简单地把 GET=读、POST=写，也不能只靠路径字符串推断是否改变状态。

**额外核验边界**：当前上游 README 将写权限描述为“按站点一次性开启，随后允许直接写入”；PR 文字提及写操作审批。两者是否指不同版本、不同审批层或文档滞后，**尚未核实**。因此不能声称该产品已具备所有写操作的逐次人工批准。

### Composable Test：为什么不进 Core？

使用 Playwright/Chromium + OpenAPI/GraphQL 解析 + LLM + CLI/MCP 生成 + SQLite/JSON Spec + Hook/Approval，**1–2 天可以为少数目标网站复刻 80% Happy Path**。生产级跨站兼容、权限隔离、漂移修复很难，但工程难度不是独立机制创新。

| 既有 Pattern | Hycli 对应关系 |
|---|---|
| #05 AI Build → Software Run → AI Repair | AI 生成可复用工具；软件运行并检查是否失效 |
| #11 Capability-on-Demand | 按任务发现/构建可调用能力 |
| #13 Deterministic / Probabilistic Split | AI 负责探索，确定性软件执行已定义动作 |
| #15 Proposed Action | 写入权限与不确定动作需要独立控制 |
| #26 Agent-facing System of Record | 与可信业务状态交互时需明确执行边界 |

**真正新增的证据**：现有模式在“未知网页 → 类型化可复用能力 → 确定性漂移检测”的具体实现中可以闭环；但没有证明需要新 Pattern #31。

### Human / AI / Deterministic Software

| 角色 | 职责 |
|---|---|
| Human | 指定站点、任务目标、允许的账户和动作范围，承担业务后果 |
| AI | 发现界面/API 线索，组织并修复 SiteSpec，决定调用哪项能力 |
| Deterministic Software | 保管凭据、限制同源和权限、验证读取链、执行工具、阻止不安全重试、记录结果 |

### 架构：事实 / 推断 / 未知

- **事实（官方代码/文档）**：CLI/MCP、结构化 SiteSpec、本地凭据隔离、Chromium/网络观察、只读检查、写入默认关闭、synthetic fixture 测试说明。
- **合理推断**：把网站抽象为可版本化的工具规范，可以减少重复的模型视觉探索与 Token 开销。
- **未知**：不同复杂业务站点的真实成功率、SiteSpec 漂移后的自动修复率、独立安全审计、审批实际粒度、是否有稳定的长期 Memory/Eval 体系。不能把“不会自动重试写入”误解为“绝对不会重复写入”。

### 对本地 Agent、AI 原生研发、应急管理/B/G 的启发

**值得直接复刻**：对已经获得授权的内部系统，优先从 OpenAPI、页面元数据或现有服务接口生成类型化 ToolSpec；每个工具记录输入/输出 Schema、可修改的业务对象、权限、最近一次验证结果、证据来源和版本。增加 `signed_out / site_changed / blocked / unreachable` 等可解释状态。

**不值得抄**：为了统一工具入口而逆向所有网站、重复开发浏览器底层、绕过网站访问控制，或让 Agent 在正式政务系统中使用未授权接口。应急管理优先采用受控业务 API；隐患关闭、风险等级变更、督办发送必须经独立业务权限与状态校验。

**最小验证实验**：在 3 个自有/明确授权的测试站点（列表查询、分页查询、草稿写入）比较 Browser Agent 与 ToolSpec 模式。测量：任务成功率、站点变更后的恢复时间、错误写入率、人工干预次数、净用户投入时间。写入先只对沙盒执行。

**最大未知/降级条件**：如果工具发现不稳定、写入语义不可验证，或维护 SiteSpec 的人力高于直接使用 Browser Agent，应从 Observe 降至 Reject。**继续跟踪：4/5。**

## 2. Fresh Observe：Microsoft Agensh（2026-10-24 开源）

**资料**：[官方 GitHub](https://github.com/microsoft/Agensh) · [README](https://github.com/microsoft/Agensh/blob/main/README.md)

**Tracking 3/5｜Novelty 1–2/4｜Evidence B（代码与论文；应用层用户验证不足）｜Observe（研究方向，不是 Core）**。

Agensh 让大量 Coding Agents 自行认领子任务、交换信息、异步合并工作，降低中央 Orchestrator 的协调瓶颈。官方于 **10 月 24 日开源**；论文预印本则早在 9 月 22 日发布，因此不能把研究机制当成 10 月 24 日才首次出现。

官方在五项 ProgramBench 难题、六小时预算和特定模型条件下报告：1 个 Agent 平均最终测试通过率 **19.31%**，128 个 Agent **28.78%**（相对提高约 49%，绝对提高 9.47 个百分点）。这是限定任务上的实验结果，不是“1024 个 Agent 就能可靠完成真实项目”的证明。

**Composable Test**：共享任务看板、Git、消息系统、并行 Agent 可以在 1–2 天拼出基本体验；去中心化协调的规模实验属于 Runtime/系统研究，而非已证实的全新应用层产品机制。与 #18 Spatial Agent Supervision、#20 Agent Operations Agent、#21 AI Work as Shared Artifact、#27 Context Belongs to Work 相邻，但不新增 Pattern。

**可迁移的原则**：协作规模变大时，先设计任务所有权、冲突检测、证据合并与回滚，而不是先增加 Agent 数量。对本地 Agent，建议用 2–4 个 Worker 对照单 Agent 测“净交付质量 / 冲突修复成本 / 总计算成本”；对 B/G 业务，不应把未经批准的多 Agent 共识当成正式业务结论。

**最大反证**：多 Agent 的重复工作、冲突合并和上下文传播成本可能超过收益。**继续跟踪：3/5。**

## 4. 今天真正新增了什么？

**不是新 Pattern，而是一个更清晰的机制边界：**

> 把模型探索得到的“能力描述”当作候选规范，而不是直接当成可信权限。只有经过验证、带来源和版本的能力，才进入可执行工具层；写操作还要经过独立授权与业务规则检查。

这个判断把 #05、#11、#13、#15、#26 联系得更具体。它可以成为已有 Pattern 的案例和研究证据，但**不需要新增编号**。

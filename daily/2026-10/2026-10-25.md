## 1. Fresh Observe：zCAD AI（2026-10-24）

**来源**：[zCAD 官网与 FAQ](https://zcad.ai/products/ai) · [Product Hunt 10 月 24 日发布及开发者问答](https://www.producthunt.com/products/zcad-ai)。

**状态**：Observe；Tracking **4/5**；Mechanism Novelty **2/4**；Evidence **B（官方文档/演示），独立真实生产验证 C**。

### 真实问题、旧流程、新流程

用户想做带螺丝孔的支架、壳体、传动组件等**必须精确配合的实物零件**。普通 AI 3D 生成多是视觉 Mesh；形状看起来像，改一个孔径或装配配合却常常需要重新用 CAD 建模。

旧：文本/草图 → AI Mesh 或参考图 → 工程师在 CAD 重建实体、特征、尺寸和装配关系 → 调整孔位/配合 → 导出 → 工程校验。

新（官方所述）：文本/参考图 + 功能、尺寸、接口、需保留的几何 → AI 创建 B-rep 实体零件/装配体 → 在原生 CAD 中继续修改尺寸、零件和装配关系 → 检查间隙/接口 → STEP 导出或继续在 zCAD Online 编辑 → 人做公差、材料、载荷和制造校验。

**真正的机制差异**不是“文字生成 3D”，而是**从一次性视觉形状转向可持续编辑的参数化工程对象**。官方明确说明生成的是 B-rep 实体，支持装配 mates、原生编辑、STEP 导出；但也明确提醒**STEP 通常不保留原始特征历史或装配约束**，且生成的工程几何不等于制造批准。

### Composable Test 与历史去重

用 LLM + CAD Python/API + 参数模板 + B-rep 内核 + 简单 Web CAD，1–2 天可拼出固定类别零件的主要 Happy Path。复杂装配和跨修改约束一致性难复制，但**难度不是创新证据**。

与昨天的 **UseIt Studio** 对照：
- UseIt：设计视觉意图 → 分层、刀线、出血等**印前生产对象**。
- zCAD：形状意图 → 尺寸、特征、配合关系等**工程实体对象**。
- 两者共享“**生成的主对象就是下游专业工作对象**”的机制；分别强化 #10 Artifact → Semantic Object → Action、#13 Deterministic/Probabilistic Split、#28 Generation as State Transition。
- **新增的不是模式，而是反证边界**：可导出文件不保证跨工具仍可维护原生语义。STEP 保留实体几何，可能丢失特征历史/约束；因此“可编辑”“可交付”“可验证”是三项不同的承诺。

**Human / AI / Software**：Human 定义功能、尺寸与验收并承担工程判断；AI 构建和修改模型；确定性 CAD 系统维护 B-rep/几何关系、执行可计算约束；制造/仿真与实物测试负责现实正确性。

**架构事实**：B-rep、零件/装配、原生编辑、STEP 是官方公开能力。**推断**：内部有结构化几何/特征模型及建模工具链。**未知**：具体 Agent Runtime、Context/Memory、Tool 协议、Approval/Eval、装配可靠性、真实打印/加工成功率、修改后的不变量违例率。

**本地 Agent/B/G 可迁移**：保留对象原生 ID、约束、状态机、证据关联；跨系统输出时做“语义损失检查”，不能只检查文件能否打开。应急隐患从检查单导出为 PDF 后，不能因此把 PDF 当成可持续维护的隐患对象。已有 SQLite/CLI/MCP 可先复刻 schema+validator+semantic diff，不值得复制 CAD 几何引擎。

**最大反证**：若复杂装配无法稳定局部修改、导出后丢失关键约束，或实际加工仍需工程师大量重建，价值应降级。**不入 Core，不新增 #31。**

## 2. Fresh Observe：Loom Record for agents（2026-10-22）

**来源**：[Loom 官方使用文档](https://support.atlassian.com/loom/docs/record-for-agent/) · [官方 Agent 页面](https://www.atlassian.com/software/loom/agents) · [Product Hunt 10 月 22 日榜单](https://www.producthunt.com/leaderboard/daily/2026/10/22)。

**状态**：Observe；Tracking **4/5**；Novelty **2/4**；Evidence **A/B（文档流程明确；效果未独立验证）**。

**旧流程**：人想让 Coding Agent 修改 UI，先截屏、复制 URL、手写多段文字描述、反复澄清。

**新流程**：人在屏幕上边操作边讲解 → Loom 采集语音、访问链接、视觉指示与选区 → 生成可供人检查的 Action Plan/Agent Prompt → 发给 Claude、Rovo、Cursor 等 Agent，或转 Jira 工作项。

**机制**：人的“指向、选择、示范、叙述”被组合成结构化任务输入；人主要负责指出“哪里、什么不对、希望怎样”，AI 补足表达。注意官方描述的是**生成并交付 Agent Prompt**，不是已经证明 Agent 可以稳定执行演示过程。

**Composable Test**：屏幕录制 + 语音转录 + URL/点击采集 + 多模态总结 + MCP/Jira API，1–2 天可拼出 80% 核心体验。对应 #01 Human Signal + Machine Context、#10 Artifact → Semantic Object → Action、#15 Proposed Action、#27 Context Belongs to Work；**不入 Core**。

**启发**：本地 Agent 可让产品经理在真实业务页面上圈选问题并说话，输出带对象定位、截图、原始语音和可复核意图的结构化修改请求。**风险**：示范不等于授权；记录到的页面可能包含隐私或过期状态；生成 Prompt 仍须人确认。

## 3. Maturation Observe：Clueso Agents 的“结果证据”成熟

**来源**：[Clueso 2026-10-21 官方行为分析（45,000 条视频）](https://www.clueso.io/blog/ai-agent-video-study) · [Clueso Changelog](https://origin.marketing.prod.clueso.io/changelog)。

**状态**：维持 Observe；Tracking **4/5**；Novelty **2/4**；Evidence **B（厂商聚合数据，非独立因果实验）**。

该产品早已发布（Agent 7 月正式推出，10 月 13 日前后已有公开更新），并非今天的新产品。它通过 Agent 录制产品操作、制作教程，并可基于产品更新检查旧视频是否过期；主要对应 #12 Source → Self-maintaining Artifact 和 #28 Generation as State Transition。

**新证据**：10 月 21 日厂商公布内部聚合行为数据：截至 10 月 21 日，10 月前 3 周 Agent 制作视频 3,314 条，占新建视频约 19%；在**同一批 710 名同时使用两种方式的人**中，Agent 视频的导出比例 52%，屏幕录制为 10%；Agent 视频从创建到导出中位数 15 分钟、修改约 4 轮。厂商明确将“导出”和“对外发布”定义为不同事件，并剔除了员工与测试环境。

**不能得出的结论**：同一用户两种工作方式也存在任务类型、意图强弱和难度选择偏差，52% vs 10% **不是随机实验，不能证明 Agent 使完成率提高 5.2 倍**；“导出”也不等于视频正确、被观看、业务有效。更不能据此验证“自动维护旧视频”的长期准确率。

**有价值的机制证据**：产品价值可能来自取消“先录一大段→再剪辑成成品”的中间交接，直接围绕可发布产物工作，而不是模型更强。已具备更好的**行为结果证据**，但没有新的机制，**不晋级 Core**。

**对 Radar 的启发**：把 Adoption / Export / Published / Correct / Net User Effort 分开记录；优先测量是否消灭人工交接和返工，而不是“Agent 完成了多少步骤”。

### 今天最值得记住的一条“产品创新养料”

> **AI 生成的结果“看起来能用”，与它“仍然保有可验证、可修改的业务语义”不是一回事。**
>
> Human 定义真实目标和不可丢失的约束；AI 负责提出与修改；Deterministic Software 维护原生对象、执行校验，并在跨系统交接时显式识别语义损失。真正要消灭的是**人工重新解释与重建业务对象**的交接，而不是仅增加一种导出格式。

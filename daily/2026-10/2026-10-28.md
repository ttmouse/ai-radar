## 1. 今日最值得研究：TheySaid 4.0（Observe，不是 Core）

**入口**：[官方 4.0 页面](https://www.theysaid.io/v4) · [10/27 Product Hunt 与创始人问答](https://www.producthunt.com/products/theysaid) · [Human vs. Synthetic 案例研究](https://www.theysaid.io/human-vs-synthetic-testers)。

**Tracking：4/5；Mechanism Novelty：2/4；Evidence：B（功能与研究过程有公开材料；独立、外推的预测效度不足）。**

### 真实问题

AI 编码和设计让“做一个版本”很便宜，但真实用户验证依然需要招募、预约、观察、归纳。结果是团队不断生成方案，却跳过了对用户是否理解、能否完成任务的验证。TheySaid 把这种缺口称为 Validation Debt。

### 旧工作流

产品/设计提出方案 → 制作原型 → 用研团队招募真实用户 → 制定测试任务 → 观察和归纳 → 反馈产品/研发 → 修订。因为研究周期较长，团队容易把“内部评审通过”误当成“用户验证通过”。

### 新工作流（官方产品机制）

产品或 Coding Agent 生成设计/原型 → Jira/Linear/ClickUp/Monday 的任务进入 Design Done，或从 Claude/Cursor 等通过 MCP 主动发起 → 读取共享 Synthetic Audience（由客户资料、访谈、支持工单等调校）→ 合成测试者通过浏览器实际尝试页面任务并讲述过程 → 生成带屏幕行为的可用性发现与修复提示词 → 反馈回原 Ticket / 开发工具 → 人决定修复及是否补做真实用户研究。

**最有研究价值的不是“AI 写用户反馈”，而是验证从一个需要人主动发起的项目，转为开发流程中的自动触发环节。** Synthetic Audience 成为可复用的研究对象，证据回流到具体工作对象，而不是只生成报告。官方公开了 MCP、Ticket 状态触发、并行合成用户、修复提示词和 Human/Synthetic 并列比较的设计。

### 必须拆穿的关键证据问题：84% 不是预测准确率

官方案例：25 位真人在 Amazon 选购 Dyson / Shark 吸尘器；AI 根据**这 25 位真人的录像、回答、动机和决策**构造 25 个对应 Synthetic Testers，再让他们做**同一任务**。21/25 个合成测试者选择了与其真人对应者相同的品牌（84%）；70% 的主要研究发现被覆盖（包含部分匹配）。这些是厂商报告的结果。

**关键反证**：同一批人的决策信息参与了 Persona 构造，随后又用同一任务的决策一致率证明相似度。这属于**样本内重建/拟合**，不能证明模型能够预测没有参与调校的真实新用户，也不能证明在新产品、新任务、不同文化和风险场景中有效。25 人、二选一购物题与“重大 B/G 决策的用户需求”之间还有明显的外推距离。

更严格的实验应当：
1. 使用 A 组真实用户校准合成 Audience，冻结模型和 Persona；
2. 让 B 组未参与训练的真实用户与合成 Audience 完成**新任务**，事先固定问题发现的判分标准；
3. 比较真实用户问题的召回率、合成反馈的虚假问题率、修复后的真实任务成功率和人工净投入，并与通用 Browser Agent + Persona 基线对照。

如果没有留出组、盲评和基线，**“Synthetic User 反馈”应标记为假设生成，而不是客户事实证据**。

### Composable Test：为什么不进入 Core？

1–2 天可用 Playwright/Browser Agent + LLM Personas + Ticket Webhook + MCP + Issue 评论拼出 80% 演示：打开页面、模拟不同用户、生成摩擦点、回填修复建议。难复制的是**经独立验证的用户行为预测模型、长期校准和稳定的组织级受众模型**；但当前证据尚未证明这一层达到高可靠性。

因此：**工作流产品化有价值，但目前不能评为强产品机制创新**。研究难度、100,000+ 小时训练数据宣传或 Product Hunt 排名都不能替代可迁移的结构性增量。

### Human / AI / Deterministic Software 分工

| 参与者 | 新职责 | 证据边界 |
|---|---|---|
| Human / UX Researcher | 定义真实用户群、任务和成功标准；解释冲突、决定是否做真实访谈 | 分工设计可确认；节省多少真实研究未知 |
| AI | 生成合成测试者、执行浏览器任务、总结疑似摩擦、提出修复建议 | 官方产品演示与案例 |
| Deterministic Software | 任务状态触发、测试任务和结果关联、留存视频/记录、回写 Ticket、保留 Synthetic 标签 | 官方公开集成与流程；实现细节未知 |
| 真实用户 | 提供不可被合成样本替代的现场事实、真实需求和最终效果验证 | 分析判断 |

**架构事实**：官方公开 MCP、Ticket 集成、合成用户浏览器操作、基于用户数据的 Audience 调校与 Human/Synthetic 标签。**合理推断**：使用浏览器执行环境、Persona/测试任务对象和结果关联层。**未知**：具体 Agent Runtime、长期 Memory 更新策略、合成用户独立 Eval、跨任务泛化、数据隔离、权限与 Approval 细节、假阳性率。

### 与历史 Pattern 对照：真正新增什么？

- **#08 Observe → Detect Pattern → Propose Automation**：从观察工作行为找改进机会；这里观察的是用户测试行为，不是员工自动化。
- **#17 AI Work Queue / Judgment Queue**：把人的工作变成审核验证结果、处理例外。
- **#20 Agent Operations Agent**：AI 持续评估系统，但对象从 Agent 运行质量换成了用户体验。
- **#24 Evidence Gap → Active Investigation**：发现验证缺口后主动获取测试证据；本次增量是“自动测试触发 + 合成受众 + Ticket 反馈”组合。
- **#27 Context Belongs to Work**：研究证据应跟随具体设计/需求对象，而非单独留在聊天。

**真正新增的是“把用户验证嵌入 AI 原生研发循环”的跨模式组合证据，不是新 #31。** 如果未来证明合成受众可以可靠预测未见过的真实用户并长期自动校准，再重新评估是否有独立模式。

### 对本地 Agent、AI 产品设计、应急管理/B/G 的启发

**可直接复刻**：在本地 Agent + Playwright + SQLite + Linear/GitHub 中，给每个原型或需求版本绑定一组可执行任务和证据；设计改动后自动跑“操作可达性 / 表单完整性 / 文案歧义 / 错误恢复”等低成本合成探索；把问题附着于对象和版本，并明确标注为 AI 发现。

**不值得抄**：大规模“虚拟客户画像”、让 AI 假装街道站长/专家并据此替代真实访谈、把模拟用户意见直接作为需求决策的客户证据。对于应急管理，现场监管权限、组织关系、任务触发、隐患证据有效性等必须来自真实业务现场和制度，不能靠模型生成的人物反应推断。

**最小实验**：选一条已有真实访谈和操作录像的企业端检查流程，隐藏一部分真人测试作为留出集。先用 3–5 个合成测试者找界面可用性问题，再对照真实用户记录，统计独立发现、误报、修复后真实任务成功率和研究人员投入分钟数。

**最大未知/降级条件**：如果合成用户只能复述训练用户的偏好，或导致错误需求优先级、减少真实访谈，价值可能为负。跟踪 **4/5**；下次必须寻找跨任务盲测和独立第三方评估。

## 2. Fresh Observe：Spacesheep（不是 Core）

**来源**：[官网及交互示例](https://spacesheep.dev/) · [10/27 Product Hunt 创始人问答](https://www.producthunt.com/products/spacesheep)。

**Tracking 4/5；Novelty 2/4；Evidence B/C。**

真实问题：Agent 产出越来越长，团队阅读和接手的成本没有同步下降。旧流程是 Agent 写长文档/代码 → 复制粘贴给同事 → 同事评论 → 人将意见翻译回 Agent Prompt → 生成另一份文档。

Spacesheep 的新流程：现有 Claude Code/Codex/Cursor 等 Agent 直接生成一个可分享的 Space（交互文档、仪表盘、Mockup、小应用）→ 同事在具体行或对象上评论并 @Agent → Agent 修改同一个 Space → 保留版本、Undo、共享访问；部分 Space 可连接实时数据，官方声称能同步到 Google Drive 或 GitHub。

**机制价值**：人不必反复将评论转述成 Prompt；工作产物从“发出去的一次性答案”变成“人和 Agent 共同持续维护的界面”。但 Claude Artifacts + Git + 共享网页 + 评论 + Agent Webhook 在 1–2 天可以复刻主要体验；真正的跨 Agent 语义状态、权限、多人并发冲突和数据源一致性尚无独立证据。已有 **#21 AI Work as Shared Artifact、#27 Context Belongs to Work、#28 Generation as State Transition** 充分覆盖，不新增 Pattern。

**可迁移**：将检查报告/风险态势图从一次性 PDF 改成带对象 ID、评论、版本和可追溯数据来源的共享工作视图。**不值得抄**：为了把所有内容做成“活网页”而把正式检查结论和审批记录变成可随意重写的页面。正式业务对象必须独立保存与审计。

## 3. Maturation：Tiden 的重要纠偏（历史 Core）

**来源**：[Tiden 官方 Changelog：10/21 与 10/23](https://tiden.ai/changelog) · [长期档案](https://github.com/ttmouse/ai-radar/blob/main/products/tiden.md)。

10/21 官方发布了一项前次档案未充分解释的机制：**所有关联代码 PR 已合并、Intent 静默 24 小时后，Tiden 会自动描述已合并代码、判断承诺并把 Intent Branch 合并到 main；部分工作在 7 天后把已交付部分合并，未完成承诺移到新的 Intent。**可以 Hold 暂停，也可在产品设置关闭自动合并。10/23 又增加关闭未合并 Branch 但保留历史。

**关键纠偏：**以前把 Human 职责概括为“决定合并”，容易混淆两个不同动作：**Git 代码 PR 合并**与 **Tiden 语义 Spec/Intent 分支的合并**。前者按代码仓库自身规则执行；后者在特定条件下由 Tiden 自动对账/合并，不必每次由人手动确认。它不是“Agent 可以绕过 PR 审核自动部署”，也不是“所有语义变更都必须人工合并”。

新的对象生命周期：**Intent → 实际 PR 交付证据 → 静默/超时/人工 Hold → 已交付部分对账入主线 + 未履行承诺转入后续 Intent**。这比“Agent 说完成即关闭任务”更能保持承诺与交付状态的连续性，但也引入**自动裁决错误、时间窗过早、语义错链**风险。

**对本地 Agent / B/G**：可以复刻“已交付事实自动对账、未完成承诺不得丢失、异常进入判断队列”；但**不要把代码分支的自动对账照搬成隐患自动闭环或正式督办自动批准**。现实检查结论仍需符合责任、证据、法定流程。归属 #21/#27/#30；历史 Core 维持 **5/5**，不重复计入今日 Core。

## 6. 今日结算

**新增 Core：0；Fresh Observe：2（TheySaid 4.0、Spacesheep）；Maturation 深化：1（Tiden）；Reject / 去重：4（PulseDev、Nuvio 5.0、Overmind、Oracle）；新正式 Pattern：0，仍为 30。**

**今天最值得记住的一条产品创新养料：**

> **AI 可以主动制造验证机会，却不能自己制造客户事实。把“模拟用户发现的疑点”当作待验证假设，把“真实用户在现场的行为”当作证据，把“业务规则与权限”交给确定性软件。真正有价值的 AI 原生研发，不是让验证环节看起来自动化，而是让验证更早发生、来源更可追溯、错误判断更容易被推翻。**

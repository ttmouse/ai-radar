## Core 深拆：ChatGPT Intelligent UI

**官网与第一手证据：**
- [OpenAI 官方发布，2026-10-07](https://openai.com/index/gpt-6-for-everyone/)
- [OpenAI 开发者社区公告](https://community.openai.com/t/gpt-6-and-intelligent-ui-in-chatgpt/1404139)
- [TechCrunch 演示报道，2026-10-07](https://techcrunch.com/2026/10/07/chatgpt-is-getting-a-lot-more-visual-with-the-launch-of-a-new-interface/)
- [Anthropic Claude 视觉/交互内容官方说明，2026-03-16（重要先例）](https://support.claude.com/en/articles/13641943-visual-and-interactive-content)

### 1. 真实问题

聊天式 AI 把所有任务压成「一条文本消息」：解释、比较、计算、选择、执行下一步都依赖用户阅读、再打字。用户经常需要的是可以调整参数的计算器、可探索的结构图、可勾选清单，而非另一段说明。不是每个需求都值得创建完整 App，但纯文字又无法承载低成本交互。

### 2. 旧工作流

Human 提问 → AI 输出文本/表格 → Human 自己想象结构、反复追问或复制到表格/浏览器 → 再调整参数 → 返回对话。即便 AI 能写 HTML，也通常需要用户显式要求「生成一个应用」、打开独立预览、管理额外产物。

### 3. 新工作流

Human 提出意图 → 模型判断文本/视觉/表单/控件哪种组合更合适 → 原生可流式组件与内容一起逐步出现 → Human 直接点选、修改输入、查看局部变化 → 必要时继续对话。官方例子包括自行车部件分解、餐食人数调整、购物清单、退休储蓄计算器、分账工具。官方明确称它适用于 Chat 标签页，2026-10-07 起向付费用户滚动发布，次日扩大至 Free/Go。

### 4. 关键机制 / 交互创新

**Answer → Intent-shaped Interactive Surface**：回答不再只有字符串，而成为模型实时组织的「可操作界面」。真正的原语变化是 **用户无需先要求“创建应用”，系统可以把交互本身作为回答的默认形式**。这不同于简单嵌入图片或把一段代码显示成预览。

官方明确披露：native streamable components library + compiler，在生成过程中逐步处理 UI；模型训练包含布局、视觉、交互与何时不使用 UI 的判断。由此形成三层分工：模型选交互结构，组件/编译器保证可渲染和风格约束，用户在界面中直接探索。

### 5. Composable Test

**可拼部分（1–2 天）**：LLM 输出结构化 JSON、前端组件映射、图表库、状态管理、动态表单与简单计算器。一个 Demo 完全可以做到 80% 视觉效果。

**不应被 Demo 等价替代的部分**：在任意开放问题上自动决定「要不要 UI」、持续生成时稳定增量渲染、组件可交互但不越权、模型/组件共同形成一致体验、在大规模主对话工作流中默认触发。它改变的是「答案如何被消费」而非只是给聊天框加一个按钮。

**限制**：官方未证明该机制能持续维护复杂业务状态或跨会话复用生成界面；不能把它等同于真正的可持续业务应用。

### 6. Human / AI / Deterministic Software

| Actor | 过去 | 现在 |
|---|---|---|
| Human | 阅读答案、想象结构、再次提问 | 直接在答案内探索、调参、选择 |
| AI | 主要生成解释和代码 | 同时判断表达形态、布局与交互结构 |
| Deterministic Software | 固定聊天 UI / 文本渲染 | 原生组件、编译器、确定性计算与交互状态 |

责任边界没有消失：涉及真正业务写操作仍需权限、校验、审计。生成一个「按钮」不等于授权执行。

### 7. 架构、Runtime、Context、Memory、Tool、Approval、Eval：事实与推断

**已确认事实**：原生可流式组件库；生成时处理 UI 的编译器；模型被训练去选择内容、布局和交互；评估关注 clarity/usefulness/completeness；适用于 Chat 而非 Work/Codex 模型替换。

**合理推断**：系统可能有结构化 UI 表达协议、组件白名单、增量解析和局部状态管理；业务计算应尽量落在确定性逻辑而不是反复询问模型。**这些是架构推断，不是公开实现细节。**

**未知**：UI schema、客户端/服务端执行边界、可用组件清单、复杂状态是否持久化、生成组件的权限隔离、失败恢复、UI 交互是否回写长期 Context、真实任务完成率、Eval 数据。没有证据表明有独立 Agent Runtime 或审批体系；不要虚构。

### 8. 可迁移产品原理

**Interface is a function of intent, not a fixed destination.** 交互界面可以按当前问题即时组织，但确定性计算、数据来源、权限与正式业务对象仍要有稳定承载层。高质量生成式 UI 的关键不是能生成多少组件，而是 **什么时候该生成、什么时候只需一句话、什么时候必须跳转到稳定业务界面**。

### 9. 对 AI 设计 / 原生研发 / 本地 Agent / 应急 B/G 的启发

AI 产品设计：从「所有答案放进聊天」转为「意图 → 最小合适交互原语」。复杂对比用矩阵、参数敏感问题用可调控件、审批用证据卡片、任务分配用队列，而不是一律生成段落。

AI 原生研发：优先做受约束的组件注册表与 schema，而不是让模型任意吐 HTML。把 Layout 决策交给 AI，把执行和校验交给确定性软件。

本地 Agent：CLI/Browser/MCP 已足够支撑 Tool 调用；真正值得补的是 **result-to-interaction layer**：Agent 返回可选择、可复核、可继续执行的操作对象。

应急/B/G：专家看企业风险时，不应先读 20 段 AI 分析；系统可按意图呈现风险对比、证据差异、待补证据、建议督办等不同视图。但**正式检查文书、风险判定规则、审批/签发仍须稳定对象模型和明确权限**，不能由生成式 UI 替代。

### 10. 本地复刻：值得与不值得

**值得 1–2 天验证**：固定 5 种交互组件（Comparison、Evidence、Parameter、Decision、Timeline）；Agent 输出受限 schema；渲染器负责状态与可用性；敏感动作仅生成 Proposed Action，再由系统校验/审批；对比纯文本完成时间与误判率。

**不值得抄**：自研通用流式 UI 编译器、无限组件库、让模型直接生成可执行任意脚本、为了视觉复杂而牺牲可审计性。最初应选择固定、可解释、可测量的组件。

### 11. 最大反证 / 可能被高估

- **不是首创**：Anthropic 官方 2026-03-16 已说明 Claude 可自动生成可交互图表、图解与结构化输入。因此「AI 自动选择交互内容」不是 OpenAI 首次发明。
- **可视化不等于正确**：漂亮图表可能掩盖事实错误，用户更容易相信错误结果。
- **微工具不等于持久软件**：若生成界面不能复用、协作、追溯，就只是更丰富的回答格式。
- **默认使用不等于默认有效**：需比较任务成功率、交互次数、错误率、用户主动关闭比例，而非只看展示效果。
- **UI 不是 Agent 权限系统**：展示审批按钮不能证明真实授权边界。
- 目前多是官方发布、媒体演示与早期反馈；实际采用证据尚弱。

### 12. Tracking

**5/5**：持续跟踪，因为这是大规模 Chat 默认交互形态的变化。**Mechanism Novelty 2/4**：重要扩展但不是全新类别。**Evidence B**：官方架构细节清楚，缺独立长期数据。未来优先追踪：组件可用范围、交互行为是否持久化、是否可复用/共享、是否产生稳定 Action Object、实测任务完成率。

## 与历史产品和 Pattern 的严格比较

- **#09 Headless System + Generative Interface（Claudeforce）**：已涵盖 AI 组织界面的方向；Intelligent UI 新增的是「对话答案层的原生流式组件 + 默认意图选型」，而非首次提出生成式界面。
- **#10 Artifact → Semantic Object → Action**：只有当组件真正连接业务动作时才触及；目前不能直接等同。
- **#13 Deterministic / Probabilistic Split**：模型决定表达，组件执行交互逻辑；是现有原则在 UI 的具体落地。
- **#15 Proposed Action**：仅在生成界面承载可审核的真实业务动作时才相关。
- **#28 Generation as State Transition**：若 UI 能持续演化为可继承工作状态才成立；目前没有证据。

**真正新增的是证据强度和交互层级，而不是一个未曾出现的 Pattern**：生成式 UI 从专门工具/企业软件实验，走向大型通用聊天产品的默认回答能力。故不新增 #31。

## Methodology Reflection

**不新增 Pattern。** 今天值得记录的反证是：一个机制进入大众默认工作流，不等于它首次出现。区分 **Mechanism Novelty** 与 **Distribution / Default Adoption**，避免把大厂规模误当原创性；现有 v2 的评分和 Default Workflow Test 已足够，无需增加新筛选规则。

**交付真实性缺陷必须修正**：10/07 日报称 Pages 已增加 Methodology，但 main 分支实际未更新。新增低风险交付校验：涉及 GitHub/Pages 修改时，必须读取真实目标文件、提交、回读 main 分支验证，再报告「已更新」。无法核验 Pages 部署时，只能说「源码已提交，部署待验证」。

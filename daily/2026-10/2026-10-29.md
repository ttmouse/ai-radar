## 1. 今日 Core：Entire Trails（条件入选）

**产品**：[Entire](https://entire.com/) · [10/26 官方发布](https://entire.com/news/entire-launches-an-independent-git-forge-for-agent-human-collaboration) · [Trails 功能页/交互示例](https://entire.com/features/trails) · [CLI GitHub](https://github.com/entireio/cli) · [Entire Brain](https://github.com/entireio/entire-brain)。

**首次研究：2026-10-29；Tracking 5/5；Mechanism Novelty 3/4；Evidence A/B（CLI/文档/界面可核查，真实生产质量证据不足）；状态：Core，条件成立；新 Pattern：否。**

### 1.1 真实问题与用户

目标用户是使用 Claude Code/Codex/Cursor 等 Coding Agent 的研发团队，尤其是同时处理多个仓库、分支和 Agent 的负责人。

AI 生成代码速度提升，但 PR 仍以 diff、评论、CI 状态和人逐段阅读为主要交付入口。生成成本与审核成本失衡。一次功能变更可能横跨 API、Web、测试、配置与多次 Agent 会话；仅看最终 diff，容易丢失「为什么改、谁做了什么、哪次修复回应哪个问题、当前能否交付」。

**不要误述旧流程**：传统 GitHub PR 也支持 CI、必需审批和自动 Code Review；Entire 并非首次发明这些能力。其假设是 **PR 作为主要审核对象的粒度与人的注意力分配方式需要改变**。

### 1.2 旧工作流 → 新工作流

```text
旧：
Human 提 Issue/需求 → Agent 生成代码 → Git Branch/PR
→ CI + Review Bots + 人看 Diff/评论 → 修改 PR → 人 Merge

新（Entire 所提倡）：
Human 定义目标/验收与合并责任
→ Trail（可跨仓库关联需求、Branch、Agent Sessions）
→ Agent 在多次 Push 中实现、修复
→ 每次 Push 触发 Runner/Eval，产出分数与 Findings
→ Agent 读取 Findings、修复、再 Push
→ Deterministic CI / Gate / Approvals 汇聚当前证据
→ Human 看意图、风险、未解决问题与证据，必要时深入 Diff
→ 按权限和 Gate 决定 Merge
→ Session / Checkpoint / 决策成为后续 Agent 可检索的 Context
```

**Trail 是核心一等对象**：官方说明，一个 Trail 可连接多个仓库的改动，保留工作意图、讨论、分支、会话、审查、CI、发现与审批。其交互页面将审查从线性 diff/评论转向以“风险、证据、未解决问题”为主的工作仪表板。[Trails 官方页](https://entire.com/features/trails)。

### 1.3 可验证的关键机制

1. **Trail / Change / Finding / Gate**：`entire trail create/show/watch/finding/approve/merge/resume` 已在开源 CLI README 中列出；Runner 以风险、信心、漂移、安全、审查等检查每次 Push，并生成可处理 Finding。Runner 配置位于 `.entire/runners/`，`entire runner setup` 仍标记为 experimental。[CLI README](https://github.com/entireio/cli)。
2. **跨会话 Context 不再属于某个 Agent 聊天窗口**：`entire enable` 安装 Agent/Git Hooks；与 Agent 工作关联的 Commit 通过 `Entire-Checkpoint` trailer 链接 prompt、transcript、文件变化。默认 Checkpoint 使用独立 Git refs（`refs/entire/checkpoints/...`），不往工作分支添加额外 Commit；`entire checkpoint explain` 和 `entire search` 允许追溯。[CLI README](https://github.com/entireio/cli)。
3. **Code Graph + Memory**：Entire Graph 提供代码结构，Entire Brain 将会话、Checkpoint、文档和经过审查的事实形成可检索项目记忆。可确认其公开组件和接口，**不能推断记忆内容已经被独立证明准确**。[Entire Brain](https://github.com/entireio/entire-brain)。
4. **人的意见与 Agent Finding 分离**：Entire CLI 10/26 的 v0.12.2 Release 明确规定 Agent 会话内禁止 `entire trail comment` 的写操作，转而使用 `entire trail finding`；Human Comment 是人的讨论记录，Agent Finding 是机器发现。不是简单把机器人当成同权限评论者。[CLI Releases](https://github.com/entireio/cli/releases/tag/v0.12.2)。
5. **GitHub Mirror 不绕过现有治理**：官方说明 GitHub mirror 保持 GitHub 为 Source of Truth，Push 转发给 GitHub，分支保护和必需检查继续生效。不能把 Trail 说成可绕过 PR 审核的替代权限。[CLI README](https://github.com/entireio/cli)。

### 1.4 Composable Test：为什么仍可条件入选 Core？

**1–2 天可复刻的 80% Demo**：GitHub Issue + PR + Actions + Agent Code Review + CLI Hooks + SQLite/Markdown Session Log + 规则分数看板，可以做到“每次 Push 触发 AI Review，Agent 读反馈继续修复，人最后 Merge”。这部分不创新。

**真正的结构差异**：Trail 成为跨仓库、跨 Agent、跨多次 Push 的持续工作对象，统一管理 Intent、Session/Checkpoint、Findings、CI、Approval 与 Merge；默认审查入口从“代码差异列表”变成“工作是否有足够证据交付的判断面板”。如果这个对象长期稳定成立，改变的是工作组织方式和人的注意力，而非多加一个 Bot。

**结论：Composable but Structural，条件 Core。** 若实际用户仍主要依赖原有 PR+CI，Trail 只是另一个漂亮 Dashboard；或 GitHub + 常见 Hooks 能以低成本长期等价运行，则应降级 Observe。不能因为 Entire 的分布式 Git 速度宣传或创始人背景而入选。

### 1.5 Human / AI / Deterministic Software 分工

| 角色 | 新的默认职责 | 不应越界 |
|---|---|---|
| Human | 定义需求/验收/高风险边界，处理冲突与例外，承担合并与交付责任 | 不因 Eval 全绿就无条件放弃判断 |
| AI | 生成实现、解释 Agent Session、运行/辅助 Eval、处理 Findings、提出修复 | 不应自行批准自己生成的高风险变更 |
| Deterministic Software | Git 版本、身份权限、CI 真运行、测试结果、Gate、审计与状态流转 | 规则绿灯不等于业务意图正确 |
| Trail/Context Layer | 将目标、Agent 行为、证据和判断关联到持续工作对象 | 不应把机器推断当成不可质疑的事实 |

### 1.6 架构事实 / 推断 / 未知

**已确认**：Entire 10/26 正式公布 Trails 与 Git-compatible forge；CLI MIT 开源，公开 Trail/Checkpoint/Search 命令；Git refs 与 Commit trailer 保存 Session 关联；Runner 可配置，部分 setup 实验性；GitHub Mirror 保留上游治理；可集成 Buildkite/Depot；目前原生私有仓库已开放，公开仓库、自托管节点属于未来计划。

**合理推断**：Trail 需要稳定 ID、Change/Repo 关系、每次 Push 的 Eval Run/Findings、Gate 版本、Human Approval 与 Session Link；跨仓库关联可能显著减少人为拼接上下文的时间。

**未知**：真实团队的误放行率/误拦截率、Agent Review 与真实缺陷相关性、跨仓库合并一致性、Eval 结果是否会被模型与 Prompt 变化污染、Memory 的错误固化率、企业级权限隔离、实际用户净节省的审查时间。厂商宣称 Push 最高 89 倍、节省最高 71% tokens，缺少本轮独立对照验证，**不作为 Core 理由**。

### 1.7 必须重视的反证：证据层自身可能不可靠

- **同源自证**：Coding Agent 生成代码，另一个 Agent 根据相似上下文给出“低风险”，并不能证明原始需求正确；Eval 不可替代独立测试与业务验收。
- **实际未闭合的工程缺陷**：公开 [Issue #2378](https://github.com/entireio/cli/issues/2378) 描述在某些清理条件下未压缩的 Checkpoint Commit 可能失去可达性（不影响正常工作树的已提交代码），本轮回读为 Open；不能把所有 Agent 历史视为绝对可靠的审计记录。
- **Trail Gate 显示缺陷**：公开 [PR #2909](https://github.com/entireio/cli/pull/2909)（本轮仍 Open）说明项目级 Trail 的 `trail show --json` 曾丢失 per-change mergeability/gates 输出；可见 UI/CLI 的状态完整性仍在迭代。
- **隐私与泄密**：官方明确指出 Session Transcript 会上传 Git Remote；公有仓库可被他人读取，自动脱敏只是 best-effort。应默认使用私有存储、最小保留与上传前检查。[CLI 安全文档](https://github.com/entireio/cli#security--privacy)。
- **责任错位**：厂商宣传“Eval 满足后可以不看代码直接 Merge”是一种工作流选择，**不是对安全性或正确性的保证**。高风险变更必须保留人工复核。

### 1.8 与现有 30 个 Pattern：真正新增什么？

| 已有模式 | 与 Entire 的关系 | Entire 的增量 |
|---|---|---|
| #17 AI Work Queue / Judgment Queue | 人集中处理需判断事项 | 把 PR 审查转为多次 Push 的风险/证据判断 |
| #21 AI Work as Shared Artifact | Agent 工作过程成为团队可继承资产 | Trail 将目标、多个 Repo Changes、Session、Review 关联为同一对象 |
| #27 Context Belongs to Work | Context 属于工作而非 Agent | Checkpoint/Memory 与 Trail/Commit/Repo 关联 |
| #30 Intent as Source of Truth（G5/Tiden） | Intent/Spec 作为软件上位控制对象 | Entire 不宣称拥有 Tiden 那样独立 Spec 质量 Gate，重点是连续 Eval + 审查工作面 |
| #13 Deterministic / Probabilistic Split | 模型判断与规则执行分离 | Agent Eval + CI/Gate + Human Approval 三者协作 |
| #20 Agent Operations Agent | AI 评估其他 Agent | Eval Runner 对 Coding Agent 的产出持续评估 |

**真正新增的是已知模式在「Git Forge 核心协作对象」层的深度产品化，而不是无法被既有模式表达的全新 #31。** 今日 Core 不等于新增 Pattern。

### 1.9 对本地 Agent / AI 原生研发：可直接复刻什么？

已具备 Agent Runtime、CLI、Git、SQLite、文件访问、MCP 和浏览器时，**不建议迁移 Entire Git Hosting**，先复刻最有价值的结构：

```text
WorkTrail
├── trail_id / intent_id / acceptance_criteria
├── linked_repo / branch / commit_sha
├── agent_session_id / checkpoint_ref
├── eval_run_id / runner_version / evidence_sha
├── findings: open | fixed | dismissed
├── deterministic_checks: pass | fail | missing
├── approval: human_id / scope / reason
└── verdict: blocked | needs_judgment | ready
```

**最小实验（3 步）**：
1. 选一个真实的本地项目，保留 GitHub 原工作流；用 Hooks + SQLite 把 Issue/Intent、Commit、Agent Session、Test Run、Finding 关联到一个 Trail ID。
2. 每次 Push 触发一条代码/安全规则 Eval 和至少一项真实确定性测试；模型产生 Finding，但不允许修改 Human Approval；CI 失败时不得显示 Ready。
3. 对照 10 个历史 PR/任务，测量漏报、误报、错误放行、人工复核分钟数、换 Agent 继续工作的恢复时间。**不先做新 Git 服务器或复杂 Dashboard。**

**不值得抄**：分布式 Git 加速、多模型 Eval 数量、无条件“全绿即自动 Merge”、无上限存储原始 Agent Transcript。

### 1.10 对应急管理 / B/G 产品

把「检查」而非「任务列表」作为可独立发起的工作对象。检查可能由任务、AI 异常、专家主动抽查或现场触发。检查对象关联：责任主体、检查点、证据、事实、结论、隐患、整改/复核和专家判断。

类似 Trail 的启发是：**持续检查工作面展示的是“证据是否充分、哪项风险未闭环、谁需要判断”，而不是只展示一堆操作记录。** AI 可收集和组织证据、提出风险/整改建议；确定性系统负责对象关系、权限和流转；正式检查结论、风险等级与督办发文仍需遵守法定和组织责任边界。软件“绿灯”不能证明现实现场已经安全。

**跟踪 5/5。** 下次优先获取真实团队在 Trail 与 GitHub PR 上的对照、风险误放行案例、Session 可靠性修复及跨仓库 Gate 的生产证据。

## 2. Fresh Observe：Dedica（Tracking 4/5，Novelty 2/4，Evidence B/C）

来源：[10/28 Product Hunt](https://www.producthunt.com/products/dedica)；[官网](https://getdedica.com/)（本轮官网抓取受限，具体功能以 PH 创始人公开答复为主）。

**真实问题**：网站面向人设计的交互，可能让 Agent 无法找到价格、跨过 JS 渲染、处理验证码或完成购买。Dedica 宣称提供 125 项 Discovery/Access/Usability/Payment 检查、评分和给 Coding Agent 的修复指令，并称混合静态检查与真实 Agent 导航测试。

**Mechanism Delta**：从只衡量 Human UX/SEO 转向衡量 Agent 是否能完成业务动作；这是一项新的**测试对象与评价视角**，但不是新的 AI 原生软件基本组织方式。Browser Agent + Playwright + 静态规则 + 修复 Prompt 能在 1–2 天复刻主要体验；已有 #26 Agent-facing System of Record、#29 Operational Model、#13 Deterministic Split 可解释。Observe，不晋级 Core。

**独立用户反证**：一位 PH 用户报告其 MCP/OpenAPI 实际存在于子域，却被审计判定不存在；创始人回复可通过 llms.txt 链接发现。说明“审计未发现”与“业务能力不存在”必须区分；评分覆盖率、假阳性率和真实任务完成率未知。

**可迁移**：给应急管理企业/政府端做“双客户测试”——人能否完成、Agent 在合法授权下能否完成；不应为了让 Agent 通过验证码而削弱安全权限。真实指标应是任务成功率、误阻率和安全越权率，而非 Agent 友好分数。

## 3. Fresh Observe：Revix AI（Tracking 4/5，Novelty 2/4，Evidence B）

来源：[10/27 Product Hunt 与创始人问答](https://www.producthunt.com/products/revix-ai-2)、[官网](https://www.revix.ai/)。

Revix 先扫描代码仓库自动抽取架构/编码惯例，转成可编辑规则；之后对每个 PR 给出带规则来源、严重性和意图的评论，并在合并后尝试更新规则。创始人承认早期评论可能误判，官方允许人工编辑/关闭规则。

**最重要的反证**：**仓库中“反复出现的写法”是观察到的事实，不等于团队“批准的规则”。** 如果从历史代码归纳规范，又用合并结果自动强化规范，可能把遗留坏习惯和偶然错误固化为政策。

Composable Test：代码索引 + LLM 规则提取 + PR Webhook + GitHub Actions 可复刻核心流程。已有 #08 发现模式、#19 组织学习、#30 Intent/规则控制与 #13 分工足以解释；不晋级 Core。

**可迁移**：本地 Agent 可以自动提出“候选工程规则”，但必须保留 source、confidence、human_approved、version、deprecation_reason，不能未经确认就把“现状”当“应然”。

## 6. Radar Methodology / Pages 自检

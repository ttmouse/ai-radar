## 重点观察：Unified.to — 把“集成工作”交给 Coding Agent

### 1. 它解决什么真实问题

AI Coding Agent 已经能写大量业务代码，但第三方 SaaS 集成仍然包含大量不适合纯代码生成的摩擦：读供应商文档、判断对象和字段、处理 OAuth、配置 webhook、创建 sandbox、观察 API logs、注册生产应用等。

Unified.to 的新方案不是再提供一个“生成 integration code”的聊天框，而是把自身产品表面重新暴露给 Agent：

- 100+ `SKILL.md`，把集成知识变成 Agent 可直接读取的操作说明；
- Core MCP server，让 Agent 能查询 docs、检查 integration support、创建 connection/webhook/environment、读取 API-call logs；
- Sandbox 用 synthetic data，让 Agent 在没有真实客户账户时完成端到端验证；
- GenAI Task，把交给 Cursor、Devin、Jules、Claude Agents 等云 Agent 的工作抽象成统一 Task；
- Enterprise-Managed Authorization，把访问政策重新收回企业 IT 控制面。

### 2. 过去工作流

```text
Developer
→ 找 vendor docs
→ 注册 OAuth app
→ 理解 schema
→ 写 integration
→ 创建测试账号/数据
→ 配 webhook
→ 跑测试
→ 看日志
→ 修代码
→ 上生产
```

Agent 最多负责其中“写代码”的部分，其余环境、授权、调试和供应商配置仍由人穿梭完成。

### 3. 新工作流

```text
Human: 定义“我要接什么系统/完成什么集成”
        ↓
Coding Agent
        ↓
Skill：获得领域操作知识
Core MCP：操作 integration workspace
Sandbox：生成/验证 synthetic environment
Logs：观察失败
        ↓
Agent 自己修改实现并再次验证
        ↓
Human：审批 plan / production credentials / vendor-side final registration
```

### 4. Mechanism Delta

真正变化不是“Agent 会调用更多 API”，而是：

> **原本为 Developer 设计的 Integration Platform，开始出现一个平行的 Agent-facing Operational Surface。**

过去 API/Docs 是给开发者读取和调用；现在 Docs 被 Skill 化，管理控制面被 MCP 化，测试环境被 Agent 可操作化，日志成为 Agent 的反馈信号。

这使 Integration 从“人操作平台 + AI 帮忙写代码”向“人定义目标 + Agent 操作平台完成工作”移动。

### 5. 为什么仍然不进入 Core

这个变化重要，但目前没有足够新的产品机制。

它主要是现有三个 Pattern 的组合与成熟化：

- #11 Capability-on-Demand：Agent 按任务加载 Skill/能力；
- #26 Agent-facing System of Record：传统 SaaS 暴露可信状态与确定性动作给 Agent；
- #29 Runtime + Source + Telemetry → Operational Model → Agent Execution：Agent 能读取运行日志并修正自己的实现。

Enterprise-Managed Authorization 又主要强化 #14 Governance Layer / #22 Agent Identity 所在的治理簇。

因此它新增的是一个很强的**实现证据**：一个成熟 SaaS 若想真正 Agent-native，不只是“提供 MCP”，而要同时重构 **Knowledge Surface + Action Surface + Test Surface + Telemetry Surface + Authority Surface**。

但这还不足以新增 Pattern。

### 6. Composable Test v2

如果已有：

`SKILL.md + MCP + Sandbox + API logs + OAuth + coding agent`

1–2 天可以拼出一个针对单一 API 的 70–80% Happy Path。因此从实现组件看高度可组合。

难复制的是把 1000+ integrations 长期维护成统一 schema、统一 sandbox、统一日志、统一授权和统一 Agent surface。这是数据/平台工程护城河，不等于新的应用层产品机制。

结论：**Composable but Structural，结构变化主要被已有 Pattern 覆盖。**

### 7. Human / AI / Deterministic Software 分工

| Actor | Before | After |
|---|---|---|
| Human | 查文档、配置、编码、调试、上线 | 定义目标、审批 plan、提供/批准生产权限、处理供应商侧例外 |
| AI | 辅助写 integration code | 读取 Skill、操作 workspace、写代码、测试、读日志、自修复 |
| Deterministic Software | API + OAuth + logs | 进一步成为 Agent 的 sandbox、权限边界、状态与验证基础设施 |

责任变化是真实的，但它本质上是 #26 Agent-facing System of Record 的强案例。

### 8. 事实 / 推断 / 未知

**已确认事实**

- Unified.to 官方 10 月 2 日更新确认已发布 100+ Agent Skills。
- Core MCP 可让 coding agent 管理 connections、webhooks、environments，并读取 API-call logs。
- Sandbox 可使用 synthetic data，不需要真实客户账号即可构建和验证流程。
- GenAI API 新增 Task，对接 Cursor、Devin、Google Jules、Claude Agents 等九类 agent integration。
- Unified API/MCP 已支持 Enterprise-Managed Authorization。

**合理推断**

- Unified.to 正在把传统 integration platform 的主要操作面从 human-first 改造成 human + agent 双表面。
- Logs → Agent → Fix 的闭环，会逐渐减少开发者承担常规 integration debugging 的比例。

**未知**

- Agent 实际端到端完成生产 integration 的成功率和人工介入率。
- 供应商 developer portal 中仍需人工完成的步骤占多少。
- GenAI Task 是否会成为跨 Agent 的稳定工作对象，还是只是统一 API schema。

### 9. 可迁移产品原理

今天最有价值的抽象不是“给产品加 MCP”，而是：

> **Agent-ready SaaS = Knowledge + Action + Test + Telemetry + Authority 五个表面同时 Agent-readable / Agent-operable。**

只有 Action Surface，没有 Test/Telemetry，Agent 无法自己闭环；只有 MCP，没有 Authority，企业无法规模部署；只有 docs，没有 deterministic sandbox，Agent 只能生成代码而不能可靠验证。

### 10. 对本地 Agent / AI 原生研发的启发

本地已有 Agent Runtime、CLI、Browser、MCP、文件访问时，可以直接复刻：

```text
Skill / Docs
   ↓
Agent
   ↓
Deterministic Tool Surface
   ↓
Sandbox
   ↓
Telemetry / Logs
   ↓
Agent evaluates & repairs
   ↓
Human only on authority boundary
```

值得抄的是闭环结构，不值得抄的是为了“Agent-native”盲目把每个功能都 MCP 化。

### 11. 对应急 / B/G 产品的启发

如果未来让专家 Agent 操作应急系统，不能只给它 API：

- Knowledge Surface：规则、检查点、企业画像、政策依据；
- Action Surface：创建检查单、生成督办、读取隐患；
- Test/Evidence Surface：模拟/预览动作、验证对象和规则；
- Telemetry Surface：动作结果、失败原因、闭环状态；
- Authority Surface：哪些动作自动执行，哪些必须专家/领导批准。

这比“做一个专家 Agent + 一堆工具”完整得多。

### 12. 最大反证

最大的反证很直接：如果 coding agent 仍需要开发者频繁处理 OAuth portal、schema edge case、production credential、vendor review 和失败恢复，那么所谓“Agent 完成 integration”只是把代码生成比例提高了，并没有真正改变默认工作方式。

因此目前保持 Observe。

## 其他候选

### Progress Smart Agent — Reject / Observe 边缘

Agentic RAG 把复杂问题拆分、选择知识源、访问 live business apps、验证结果。能力有价值，但本质仍是 retrieval orchestration + tool use，主要落在已有 Agent workflow / evidence 机制内，没有看到新的业务对象或责任关系。

### Lexis+ with Protégé — Observe

法律知识图谱 + authoritative sources + specialized agents + human review 是可靠垂直 Agent 的合理组合，但“domain context + orchestration + citations + HITL”目前仍不足以形成新的应用层 Pattern。更值得追踪的是 evidence provenance 是否成为法律工作的第一等对象。

### Meta Muse Gadgets — Reject

把 Muse 接到 displays/buttons/sensors/actuators 很有探索价值，但当前更像新的 I/O surface 和硬件 SDK；没有证据显示它已经形成新的稳定工作流或责任结构。

### ZoomInfo / Gong / Apollo GTM Agents — Reject as Core

近期 GTM 产品集体转向“watch signals → decide → execute”。这进一步证明 Agent workflow 正在商品化，但也正因为三家几乎同时出现类似结构，它更像行业收敛到已有 #03/#06/#26，而不是新的机制创新。

## 与历史 Pattern 比较

今天没有发现现有 30 个 Pattern 无法解释的稳定机制。

反而出现一个值得后续 Pattern Audit 使用的信号：

> #26 Agent-facing System of Record 可能需要更精确定义。真正 Agent-facing 的系统不只是“提供 API/MCP”，而是是否同时提供 Agent 可理解的知识、可执行动作、可验证环境、可观察反馈和确定性权限边界。

这属于对已有 Pattern 的**定义加深候选**，不是新 Pattern。

## Methodology Reflection

今天是 Methodology v2 的一个正向验证案例。

如果只看“新功能数量”，Unified.to 很容易被评成强创新：Skills、MCP、Task、EMA、Sandbox、Logs 都齐了。但 Mechanism Delta + nearest-pattern comparison 把它压回了正确位置：**这是 Agent-native platform engineering 的高质量成熟案例，而不是足够新的产品机制。**

同时也发现一个后续方法论问题：未来 Pattern Audit 应该区分“Pattern 的名字”和“Pattern 的成立条件”。#26 目前名字正确，但必要条件定义过薄，容易把“有 MCP 的 SaaS”都算进去。

# AI 应用创新日报｜2026-10-05

## 今日结论

**Core：1 — Oracle Fusion Claw。**

今天没有为了追逐 10 月 4/5 日的“新品”而降低门槛。反而在对过去一周遗漏候选做补漏时，Oracle 9 月 29 日发布、最近几天文档逐步公开完整的 Fusion Claw 达到了 Core 标准。

- Tracking Score：5/5
- Mechanism Novelty：3/4
- Evidence Maturity：A/B
- Composable Test：Composable but strongly structural

真正值得研究的不是“Oracle 也做 Agent”，而是它把企业软件从 **System of Record** 明确推进为 **System of Outcomes**：人定义 Outcome、Authority、Accountability 与 Operating Envelope；AI 负责规划、持续重规划和推进；确定性企业软件负责精确计算、真实事务、权限约束与审计。

---

## 1. 它解决什么真实问题

企业 Agent 进入财务、HR、供应链等核心流程后，真正难的不是“模型会不会建议下一步”，而是：

> 如何让 AI 在一个数小时/数天、路径会变化的业务过程中持续推进目标，同时不把计算精度、权限、政策、审批、审计和责任也交给概率模型？

传统 Copilot 可以给建议；传统 workflow 可以稳定执行预定义步骤；但大量专家工作同时包含研究、异常调查、计算、模拟、优化、重新规划和真实交易执行。

---

## 2. 过去工作流

```text
Human owns process
→ 打开 ERP/HCM/SCM 多个模块
→ 收集数据
→ 分析异常
→ 计算/模拟方案
→ 判断下一步
→ 发起审批
→ 执行事务
→ 条件变化后重新分析
→ 人持续维持整个过程的状态与责任
```

AI 最多存在于某个步骤中。

---

## 3. 新工作流

```text
Human
→ Desired Outcome
→ Operating Envelope
   objectives / SOPs / policies / constraints
   permissions / risk thresholds / decision rights
   approvals / escalation boundaries
        ↓
Outcome Run
        ↓
AI reason / plan / adapt / re-plan
        ↓
Deterministic enterprise computation
calculate / simulate / optimize / transact
        ↓
Trust Harness
identity / capability / data / action authority
        ↓
approval / exception escalation when needed
        ↓
继续推进
        ↓
Outcome Receipt
```

---

## 4. Mechanism Delta

**Before：** Task / workflow / application 是主要执行单位，人持有目标并负责跨步骤推进。

**After：** **Outcome 成为持续执行对象。** 人定义目标、权限和责任边界；AI 决定动态路径；确定性系统执行受约束动作；系统为整个 Outcome Run 保存证据、决策、事务与最终 Receipt。

因此核心变化不是“Agent 自动做更多步骤”，而是：

> **软件的执行单位从 predefined workflow 上移到 business outcome under delegated authority。**

---

## 5. 为什么不是普通“加 AI”

Oracle 官方不是只增加一个 chat/agent：

1. 明确提出 **System of Outcomes**；
2. Fusion Claw 支持 larger-scale / longer-running work 与 continuous replanning；
3. Frontier model 负责 reasoning/planning/adaptation，deterministic enterprise computation 负责精确执行；
4. Enterprise Operating Envelope 把 objectives、SOP、policy、constraints、permissions、risk threshold、decision rights、approval、escalation 组合成执行边界；
5. Outcome Trust Harness 在每个 run 上执行 identity/capability/data/action authority；
6. Outcome Receipt 最终记录 authority、evidence、decisions、actions/transactions 和 result。

这已经不是“在 ERP 里加 Copilot”，而是在重新定义 ERP 上面的执行层。

---

## 6. Composable Test v2

表面组件完全可组合：

`Agent Runtime + workflow engine + policy engine + RBAC + approval queue + ERP API + audit log`

1–2 天可以做出 Demo。

但无法等价复制完整核心体验，因为真正产品对象是一个贯穿长期执行的 Outcome Run：它需要持续重规划、实时受企业政策和权限约束、概率推理与确定性计算分层、执行真实事务、异常升级、完整追踪 evidence/decision/authority，并产生 Outcome Receipt。

结论：**Composable but strongly structural。**

---

## 7. Human / AI / Deterministic Software 分工

| Actor | Before | After |
|---|---|---|
| Human | 持有目标，也负责逐步推进、跨系统操作 | Outcome Owner；定义 authority/accountability/guardrails，处理例外 |
| AI | 建议、生成内容 | 研究、规划、模拟、判断、持续重规划并推进 Outcome |
| Deterministic Software | 保存记录、执行人触发事务 | 精确计算、约束验证、权限、事务执行、审计、Receipt |

最关键变化：**Human 从 Process Operator → Outcome Owner / Authority Setter。**

## 8. 事实 / 推断 / 未知

### 已确认事实

- Fusion Claw 是 governed agentic execution runtime。
- 支持 longer-running work、continuous replanning、deterministic execution。
- Operating Envelope 明确包含 objectives、SOPs、policies、constraints、permissions、risk thresholds、decision rights、approval requirements、escalation boundaries。
- AI 不能给自己授予 authority；越界时请求 approval / escalation。
- Outcome Receipt 记录 authority、evidence、decisions、actions/transactions 和 result。
- 已有 25 个 Claw-powered applications，覆盖 Ledger、Workforce Staffing、Shipping Consolidation、Account Territory Growth Plan 等。

### 合理推断

- Outcome Run 必须具有独立于 conversation 的持久状态，否则 long-running / replanning 很难成立。
- Context 应围绕 Outcome 聚合业务状态、政策、证据和中间决策，而不是围绕某个 Agent。
- Trust Harness 实际承担 deterministic policy enforcement point。

### 未知

- Outcome state schema 与 checkpoint/recovery 机制。
- Frontier model 与 deterministic optimizer 的具体切换协议。
- 自动执行与人工升级的 eval / confidence 机制。
- 真实生产环境中的人工介入率、失败率和恢复方式。

---

## 9. 它真正新增了什么

现有 Pattern 已经分别覆盖：

- #03 Goal → Autonomous Work
- #13 Deterministic / Probabilistic Split
- #14 Governance Layer
- #15 Proposed Action
- #17 Judgment Queue
- #22 Agent Identity
- #26 Agent-facing System of Record
- #27 Context Belongs to Work
- #29 Operational Model → Agent Execution

Fusion Claw 的新增不是这些单点，而是把它们收敛到一个更高层的一等执行对象：

> **Outcome Run = Goal + Persistent State + Authority + Evidence + Decisions + Actions + Completion + Receipt**

今天形成新的 **Pattern Candidate：Outcome as First-class Execution Object / System of Outcomes**。

按照 Methodology v2，暂不新增 #31。需要继续寻找至少两个独立产品验证它不是 Oracle 的营销命名。

---

## 10. 可迁移产品原理

1. **持久的是 Outcome，不是 Agent。** 模型、Agent、conversation 可以更换，业务 Outcome 继续存在。
2. **Autonomy 必须绑定 Authority。** 能力与授权是两件事。
3. **Reasoning 与 Execution 分层。** 模糊判断交给 AI，精确计算和真实事务交给 deterministic software。
4. **Audit 单位应该等于责任单位。** 人委托的是 Outcome，最终就应该得到 Outcome-level Receipt。
5. **Human-in-the-loop 放在 authority boundary / exception，而不是每一步。**

## 11. 对本地 Agent 的启发

本地已有 Agent Runtime、CLI、Browser、MCP、文件访问时，下一步不是继续堆 Tool，而是建立：

```yaml
outcome:
  goal:
  owner:
  authority:
  policies:
  constraints:
  evidence:
  current_state:
  plan:
  decisions:
  executed_actions:
  waiting_conditions:
  exceptions:
  completion_criteria:
  receipt:
```

Runtime 每次唤醒 Agent 都围绕 Outcome 恢复状态，而不是依赖同一 conversation。

---

## 12. 对应急 / B/G 产品的启发

现在的“周期任务 → AI看/视频看/现场看 → 隐患 → 督办 → 验收”可以进一步抽象成：

> **Outcome：在本周期内，使责任主体达到可接受风险状态，并形成完整证据与责任闭环。**

AI 根据当前证据动态选择检查手段、发现 evidence gap、要求补充视频/现场检查、生成督办、跟踪整改；确定性系统守住企业权限、正式文书签发、期限、风险阈值和审计；专家主要处理高风险判断、例外和授权边界。

这比在每个现有页面塞一个 AI 按钮更接近 AI-native 重构。

---

## 13. 最大未知 / 反证

最大的反证是：**System of Outcomes 可能只是 long-running governed workflow + agent 的重新包装。**

如果实际运行仍然是固定 workflow，只在少数节点调用 LLM，那么 Mechanism Novelty 应从 3 降到 2。

后续重点验证四件事：

1. 路径是否真的会因新证据持续变化；
2. Outcome 是否拥有独立于 Agent/conversation 的持久状态；
3. Operating Envelope 是否在 runtime 动态约束动作；
4. Receipt 是否足以重建关键决策链。

## 今日其他候选

### AWS Strands Decider 2B — Reject as application-layer Core

10 月 1 日发布的 Strands Decider 2B 很有意思：它移除 language-model head，用 pointer head 在固定选项间做低延迟、有校准置信度的决策，可用于 model routing、tool selection、argument checking、triage、guardrails、eval 和 hybrid agents。

它强化了一个重要架构方向：**不要让一个 frontier LLM 同时承担生成、路由、政策判断、工具选择和 eval。** 但这是模型/Runtime 架构创新，不是应用层产品机制；而且它明确受到 Jev 启发。因此不进入 Core，也不新增 Pattern。

### Oracle 25 个具体 Claw Apps — 不分别计入 Core

Ledger、Staffing、Shipping 等不是 25 个新的产品机制。它们是同一个 System-of-Outcomes 机制在不同业务领域的实例。为了避免“行业实现 = 新创新”的计数膨胀，只把 Fusion Claw 作为一个核心研究对象。

## Methodology Reflection

今天暴露了 Radar 的一个检索偏差：如果只追“过去 24 小时新品”，会漏掉**发布几天后 Docs 才逐步完整、机制才变得可判断**的产品。

因此以后 Discovery 应保留两条并行窗口：

- Fresh Window：过去 24–72 小时新发布；
- Maturation Window：过去 7–14 天已经发布、但最近出现 Docs / Demo / real usage evidence 的候选。

Fusion Claw 正是第二类。它在 9 月 29 日发布，但最近几天 Oracle 26D docs 把 Operating Envelope、Outcome Receipt、delegated authority 等关键机制补全后，才足够做 Core 判断。

这是方法论上的实质修正候选，但本日不自动修改 L1 原则。

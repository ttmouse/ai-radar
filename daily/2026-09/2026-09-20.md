# AI 应用创新日报 — 2026-09-20

## 结论

**今天没有发现达到核心创新标准的新产品。**

今天最值得记录的不是新增产品，而是 Salesforce AIforce 对既有 Pattern 09「Headless System + Generative Interface」提供了更强的产品化证据。它没有创造新模式，但把一个此前偏前瞻的判断推进到了大型企业 SaaS 的正式架构方向。

## 今日重点观察：Salesforce AIforce / Claudeforce

### 1. 真实问题
传统企业 SaaS 要求用户先理解软件的菜单、对象、页面和字段，再把工作目标翻译成操作路径。Agent 已经可以直接理解目标、跨记录获取 Context 并调用动作，因此固定 UI 开始成为额外中间层。

### 2. 过去工作流
`用户目标 → 打开 CRM → 找页面 → 找记录 → 拼 Context → 改字段 / 跑 Workflow`

### 3. 新工作流
`用户目标 → Claude / Slack / Coworker → AIforce 读取数据 + 语义 + 权限 + 业务逻辑 → 动态组织 live interface → Salesforce 执行确定性 Action`

### 4. 最关键机制
真正变化不是“Salesforce 接入 Claude”，而是把企业软件拆成：

- **可信业务底座**：State、Semantics、Permission、Rules、Workflow、Actions；
- **Runtime Interface**：AI 根据当前 Intent / Context 临时组织当前任务所需的界面。

也就是：**Interface 从设计期资产逐渐变成 Runtime 资产，而业务事实与业务规则仍然保持 deterministic。**

### 5. Composable Test
不通过“新增 Pattern”门槛。

`LLM + Salesforce API/MCP + generative UI` 很容易拼出 80% Demo。真正有价值的是所有动态界面仍共享同一套业务语义、权限、规则和动作层。这强化现有 Pattern 09，但不足以创造 Pattern 31。

### 6. Human / AI / Software 分工
- Human：目标、判断、例外和高风险决策。
- AI：理解 Context、决定当前需要展示什么、生成任务表面、建议/发起动作。
- Deterministic Software：权威状态、权限、业务规则、Workflow、审计和最终动作。

### 7. 事实 / 推断 / 未知
**事实**：Salesforce 官方将 AIforce 定义为 live interface layer；它把 Data 360 / Customer 360 中的数据、语义、权限、逻辑和动作开放给 Claude、Slack、Coworker 等 AI surfaces；Slackforce Surfaces 支持生成可交互 live interface；动作仍回到 Salesforce 执行。

**推断**：企业 SaaS 的核心设计对象会从固定页面逐渐上移到 semantic/action/permission schema；低频、跨对象、跨系统的任务更适合生成式工作表面。

**未知**：动态 UI 是否会破坏用户空间记忆和熟练度；复杂长流程能否保持一致性与可审计性；多 Agent / 多 surface 并发写入时如何治理冲突。

### 8. 可迁移产品原理
> 固定 UI 不再等于业务系统。业务系统首先应该是可信、可调用、可治理的状态与动作层；界面可以按任务动态组织。

但“所有 UI 都生成”是错误外推。高频、稳定、依赖肌肉记忆的操作仍适合固定 UI。

### 9. 对 AI 产品 / B/G 的启发
对应急管理后台，应优先统一责任主体、任务、检查、隐患、证据、整改、验收等业务对象及其状态机、权限和 Action，而不是先争论每个功能应该放在哪个菜单。

专家工作台可以变成：

`专家意图 → 当前任务 Context → 动态任务表面 → 确定性业务动作 → 回写权威系统`

AI看 / 视频看 / 现场看可以是 Runtime 可选择的能力，而不必天然成为固定一级入口。

### 10. 本地可复刻 / 不值得抄
值得直接复刻：统一业务对象与 Action schema；权限和状态机 deterministic；Agent 动态组织任务面板；所有写操作回到权威底座；Browser 只补 API 缺口。

不值得抄：Salesforce 的大平台包装；为了追求 Generative UI 把所有稳定页面推倒重做。

### 11. 最大反证
如果实际用户最终仍大量依赖固定 Salesforce 页面，只把 AIforce 当快捷入口，那么这不是 Interface architecture 的迁移，而只是更高级的 command palette。真正验证指标应该是：**用户完成核心业务任务时，对固定 SaaS UI 的依赖是否持续下降。**

### 12. 跟踪评分
**4/5，继续跟踪，但不作为今日新核心产品。**

## 与历史模式比较
AIforce 没有真正新增机制。它强化：

- Pattern 09 — Headless System + Generative Interface
- Pattern 13 — Deterministic / Probabilistic Split
- Pattern 26 — Agent-facing System of Record

因此 **新 Pattern：0**。

## 今日主动淘汰 / 观察
- **Meta Muse**：个人 Agent 的主流化和产品成熟度很高，但仍可由 Persistent State + Agent Identity + Governance + Tool Use 解释，没有新一级机制。
- **Google Home MCP**：把智能家居能力开放给外部 Agent 很重要，但 MCP / Tool Exposure 本身不是产品机制创新。
- **Perplexity Portable Computer for Windows**：本地 Agent、Local MCP、Scheduled Tasks 有工程和隐私价值，但没有改变 Agent 产品的基本组织方式。
- **Salesforce Koa**：垂直 CRM reasoning model 可能有能力价值，但“模型更懂 CRM”不是应用层产品机制创新。

## 今日结果
- 真正新增核心产品：**0**
- 重要既有产品演化：**1 — AIforce / Claudeforce**
- 新 Pattern：**0**
- 更新产品档案：`products/claudeforce.md`

## 今日产品创新养料

> **Generative UI 真正值得关注的不是“AI 会画界面”，而是 UI 的所有权发生变化：过去产品团队预先决定每个人看到什么；未来系统可以根据 Intent 和 Context 在 Runtime 决定当前需要什么界面。但业务事实、权限和动作规则反而必须比过去更确定。**

这也是今天最重要的边界：**AI 可以生成界面，不应该生成业务真相。**

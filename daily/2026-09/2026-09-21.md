# AI 产品机制创新日报｜2026-09-21

## 结论

**今天没有发现达到核心创新标准的新产品。**

今天的筛选结果是：核心入选 0；新模式 0。最接近核心候选的是 **Lua Workflows**，其次是 **OpenAI Agents API**。两者都值得跟踪，但都没有跨过“不是把已有 Agent Runtime 产品化，而是改变应用层基本组织方式”的门槛。

---

## 候选一：Lua Workflows

### 1. 真实问题

长时任务常常不是“3 秒完成”的问答，而是需要持续数小时、数天，甚至跨多个等待点的工作：等待外部回复、等待新数据、等待某个时间窗口、等待人工批准，或在中途失败后继续恢复。传统 Agent 产品通常把这类需求压缩成一条长 prompt、一个定时任务，或一个由工程师维护的外部编排器。

Lua 的官方描述是：Workflows 让 Agent 在用户离线时继续工作，Lua CLI v3.31.0 提供构建能力，Workflow 被作为持续执行对象发布到生产环境。

### 2. 过去工作流

```text
用户提出目标
→ 工程师把步骤串成 prompt chain / cron / webhook / queue
→ 每一步需要手工处理状态、重试、恢复、等待和上下文
→ Agent 执行一次或一段时间
→ 结束后由人重新启动下一轮
```

### 3. 新工作流

```text
用户定义一个长期目标
→ Workflow 被部署为持续运行对象
→ Agent 根据状态、事件和等待条件继续推进
→ 在需要时暂停 / 等待 / 恢复
→ 处理外部输入或人工批准
→ 直到目标完成
```

### 4. 最关键的机制

Lua 最值得看的不是“Agent 能工作三天”，而是它把 **时间跨度、等待、恢复、持续状态** 作为应用层对象，而不是工程侧的隐藏实现。

这相当于把：

```text
Session = 一次对话
```

推进为：

```text
Workflow = 跨时间、可暂停、可恢复、带状态的工作对象
```

但目前公开资料只足以确认它把长时运行作为产品能力公开，并不能证明它形成了新的业务对象模型，也不能证明它比 Temporal / durable execution / job queue + Agent 更接近应用层重构。

### 5. Composable Test

严格执行 Composable Test 后，Lua Workflows **未通过强创新门槛**。

使用现有组件，在 1–2 天内可以拼出大部分原型：

```text
Temporal / Inngest / Trigger.dev
+ Agent SDK
+ durable state
+ cron / webhook
+ retry / checkpoint
+ human approval
```

可以复刻：

- 长时间运行
- 事件触发
- 断点恢复
- 等待人工批准
- 外部系统回调
- 结果持久化

因此，“Agent 持续工作”本身不足以新增模式。它更像把 Pattern 03（Goal → Autonomous Work）、Pattern 06（Persistent State → Proactive Action）和 Pattern 28（Generation as State Transition）产品化组合在一起。

### 6. Human / AI / Deterministic Software 分工

**已确认：**

- Agent 不再只运行在单个同步请求内。
- Workflow 需要持久状态与长期执行。
- CLI 被用于构建或管理这些 Workflow。

**合理推断：**

- Deterministic Software 负责调度、等待、重试、持久化、恢复和外部事件接收。
- AI 负责在每个节点上判断下一步、调用工具和生成中间产物。
- Human 被推到目标定义、关键批准和异常处理位置。

**未知：**

- Workflow 是否拥有独立于 Agent 的长期业务身份。
- 状态是否是显式、可检查、可迁移的业务对象，还是仅为运行时内部状态。
- 人工审批是否有统一对象、证据和审计模型。

### 7. 可迁移产品原理

长时 Agent 产品的关键不是“让模型一直跑”，而是把以下东西显式化：

```text
Goal
State
Waiting Condition
Resume Trigger
Evidence
Approval
Failure / Recovery
Completion
```

如果这些只是运行时细节，产品仍然只是 Agent Runtime；如果它们成为用户和组织可见、可管理、可审计的一级业务对象，才可能上升为真正的应用层机制创新。

### 8. 对你的启发

对本地 Agent：

- 可以直接复刻 durable state、checkpoint、resume、retry、wait。
- 不值得照抄“持续运行”的表面叙事。
- 应优先设计 `WorkItem / State / Approval / Evidence / Exception`，再接入 Agent。

对 AI 原生研发：

- 不要把“每天自动触发同一会话”当成长期记忆方案。
- 应该维护可迁移的工作状态，而不是依赖单条对话上下文。

对应急管理 / B/G：

```text
周期检查任务
├── 当前状态
├── 待补证据
├── 待人工判断
├── 下一触发条件
├── 责任主体
└── 恢复点
```

Agent 只是工作项的执行资源，不应成为工作项本身。

### 9. 最大未知与高估风险

最大风险是把基础设施成熟度误判为产品机制创新。只要 Workflow 仍然只是工程师定义的 DAG、队列和重试，用户并没有获得新的工作对象，也没有改变人与软件的分工。Lua 可能很有用，但目前证据更支持它是 **Agent Runtime 的更好产品化**，而不是新的应用层范式。

### 10. 跟踪评分

**3/5。** 值得跟踪它是否把 Workflow 变成可被非工程人员直接理解、修改、审计的业务对象。若未来出现“业务人员可声明长期目标 + 系统自动形成/修正执行图 + 运行中持续积累可复用状态”，再重新评估。

## 候选二：OpenAI Agents API

OpenAI 于 2026-09-10 发布 Agents API，公开提供 Codex harness 的长时会话、上下文压缩、工具搜索、程序化工具调用、子 Agent 并行、沙箱和多种执行环境。官方明确把它定位为开发者可调用的 Agent Runtime / Harness。

它的价值很高，但定位非常清楚：**这是基础设施和运行时产品，不是应用层产品。**

它强化了现有模式：

- Pattern 03：Goal → Autonomous Work
- Pattern 11：Capability-on-Demand
- Pattern 14：Agent Workspace + Governance Layer
- Pattern 18：Spatial Agent Supervision（弱相关）
- Pattern 27：Context Belongs to Work

但没有出现新的业务对象、交互原语或组织分工结构。`multi_agent`、MCP、sandbox、tool search、context compaction 都不能单独视为新的应用层机制。

### Composable Test

未通过。用已有 Agent SDK、沙箱、队列、MCP、子 Agent、上下文压缩和可观测性即可拼出大部分核心体验。

### 跟踪评分

**3/5。** 主要作为本地 Agent Runtime 设计参考，不进入应用层模式库。

## 与历史模式库的比较

今天没有新增模式。

- Lua Workflows 是 Pattern 03 + 06 + 28 的组合和产品化。
- OpenAI Agents API 是 Agent Runtime 能力的系统化封装，强化 Pattern 11、14、27。
- 二者都没有证明“Workflow / Session / Agent”之间形成了新的应用层业务对象关系。

当前最需要保持的判断边界是：

> **持续运行、长上下文、多 Agent、MCP、沙箱、可恢复执行，首先属于 Runtime 能力；只有当这些能力改变了用户管理工作的对象、流程和责任结构，才属于应用层机制创新。**

### 淘汰

# AI 应用创新发现 · 2026-09-07

今天的核心主题是：**AI 与确定性软件如何重新分工。**

## Airtop Agent Builder — ★★★★★
[产品深度卡片](../../products/airtop-agent-builder.md)

真实问题：如果让 LLM 每一步都在线执行自动化，成本、延迟和稳定性都很差；但纯脚本/RPA 又会在页面变化后失效。

核心机制：**AI Build → Software Run → AI Repair**。AI负责理解流程、生成自动化和异常修复，高频稳定步骤交给确定性软件。

为什么不是普通加 AI：新点不在浏览器 Agent，而在 AI 从持续执行者变成自动化系统的 builder / maintainer。

可迁移原则：确定性步骤尽量编译成软件，不确定性和环境变化再交给 AI。

对本地 Agent/BG 的启发：后台录入、数据同步、固定通知等不要让 Agent 每次推理；AI负责发现流程、处理例外和修复。

## Fambot — ★★★★☆
[产品深度卡片](../../products/fambot.md)

真实问题：很多事情不是用户不会问，而是用户不知道此刻应该问什么。

核心机制：**Persistent State → Proactive Action**。系统持续维护状态，由状态变化触发 AI，而不是只有 Prompt 才触发。

可迁移原则：AI 的下一步不一定是回答更好，而是知道什么时候应该出现。

## Fireflies Voice Agents — ★★★★☆
[产品深度卡片](../../products/fireflies-voice-agents.md)

核心机制：**Recorder → Participant → Worker**。会议 AI 从旁听和总结，进入实时提问、采集信息、承担部分标准化沟通。

对 B/G 的启发：应急视频核查、电话回访等也可以从“AI看材料”升级为“AI参与核验过程”。

## Perplexity Hybrid Compute — ★★★☆☆
[产品深度卡片](../../products/perplexity-hybrid-compute.md)

核心机制：**Invisible Compute Routing**。系统根据隐私、成本、延迟和任务复杂度自动选择本地/云端/模型，不把基础设施决策交给用户。

## 今日横向判断
Airtop 与 Nex 后来形成了同一条更稳定的架构原则：**Deterministic → Software；Probabilistic → AI；High-stakes → Human。** Fambot 则补充了另一个维度：Agent 需要 Persistent State 才可能真正主动。

## 今日产品创新养料
> 不要问“这一步能不能让 AI 做”，而要问“这一段工作应该长期属于 AI，还是应该被 AI 编译成稳定软件？”

# 核心产品：Frigade Assist API

**评分：5 / 5**  
**判断：Core，长期跟踪**  
**新增模式：Product → Learned Operational Model → Guidance / Action**

## 1. 真实问题

绝大多数产品内 Agent 其实“不认识自己所在的产品”。

它们通常读取 Help Center、FAQ、Docs，再回答用户“按钮在哪里”“怎样设置 webhook”。但产品发布速度远高于文档更新速度，于是 Agent 的根本问题不是模型不够聪明，而是 **Context Source 已经过时**。

Frigade 的核心问题定义是：

> 为什么要让 AI 从人类写的二手描述理解软件，而不是让 AI 自己使用软件？

## 2. 过去工作流

```text
产品发布
→ 人写帮助文档 / Tour
→ 工程绑定页面与 selector
→ Chatbot 检索文档
→ 用户自己照着步骤点击
→ 产品改版
→ 文档和 Tour 失效
→ 人再次维护
```

这是一条“Software → Documentation → AI”的间接知识链。

## 3. 新工作流

Frigade 改成：

```text
给 Browser Agent 一个真实账号
→ Agent 像用户一样操作产品
→ 遍历真实 workflow
→ 建立 Product Model
→ 产品发布后重新学习变化
→ 用户自己的 Agent 调用 Frigade
→ 返回当前版本的答案 / UI walkthrough / action
```

用户问“怎么添加 webhook”时，结果不再是一段五步文字，而可以直接：打开正确页面 → 高亮真实按钮 → 要求用户输入 URL → 测试事件 → 完成。

## 4. 最关键的产品机制

### Product as Source of Truth

传统 AI 产品知识：

```text
Product → Human Docs → RAG → Agent
```

Frigade：

```text
Product → Browser Exploration → Operational Product Model → Agent
```

Grounding Source 从“文档”变成“软件真实行为”。

### Procedural Knowledge

它保存的不只是“某功能是什么”，而是“在当前版本、当前角色和权限下，如何完成这个 workflow”。

这是一种程序性知识，而不是普通文本知识。

### Continuous Re-learning

产品每次发布后，Frigade 自动重新学习流程；按钮移动、功能增加、路径变化都会进入新的 Product Model。

因此知识变成持续状态，不再是一次性 Artifact。

## 5. 为什么不是普通“加 AI” / Composable Test

“LLM + Browser Agent”可以很快拼出来；“Docs + RAG + Chatbot”更没有门槛。

Frigade 真正值得入选的是这个完整闭环：

```text
Autonomous Product Exploration
→ Workflow Mapping
→ Role-aware Operational Model
→ Release Change Detection
→ Re-learning
→ Runtime Guidance / Action
→ Human Steering
```

单个组件可拼，但要让一个复杂软件持续产生并维护“自己怎样工作”的可执行 Context，并稳定供其他 Agent 消费，不是 1–2 天的组合 Demo。

## 6. Human / AI / Deterministic Software 分工

**Human**：给权限、批准可执行 Skill、纠正错误回答、定义高风险边界。  
**Learning AI**：探索软件、理解 workflow、更新 Product Model。  
**User-facing AI**：理解用户意图并调用产品知识。  
**Software**：身份权限、真实状态、UI overlay、动作执行、日志和审计。

核心仍是：**AI 负责学习/理解，确定性系统负责真实权限与动作。**

## 7. 架构：哪些是事实，哪些是推断

### 官方已确认

- Browser Agent 使用真实用户权限登录产品；
- Agent 会实际运行 workflow 并映射产品结构；
- 发布后自动重新学习；
- Assist API 底层包含 Product Model；
- 可以基于当前 UI 生成 walkthrough；
- Skills 可从产品操作中发现 create/edit/delete 等动作，并需团队批准；
- Guidance 遵守当前用户权限；
- Support / CX 可以直接纠正回答而无需改代码。

### 合理推断

可用的 Product Model 大概率要包含 Page/State、Semantic Element、Workflow Graph、Precondition、Role/Permission、Action、Transition、Outcome 等结构，但官方没有公开 Schema。

### 未知

最大未知是 workflow coverage、复杂角色权限、异常分支、自动 retraining 的 Eval，以及错误模型如何回滚。

## 8. 可迁移原则

> **当运行中的软件本身已经是最准确的知识源时，不要继续让人手工把它翻译成 AI Context；让 AI 从软件实际行为中建立可执行知识。**

这比“RAG over docs”更值得长期关注。

## 9. 对本地 Agent / 应急 B/G 的启发

与你的浏览器插件 / 专家工作台高度相关。

现有政府后台不会消失。如果每个页面都手工适配，维护成本高；如果每次任务都让通用 Browser Agent 临时推理，又慢、贵、不稳定。

Frigade 提供第三种结构：

```text
Learning Agent 预先探索现有后台
→ 建立企业 / 任务 / 隐患 / 检查单 / 督办的操作模型
→ 运行时 Agent 优先消费已学模型
→ 路径失效时再进入 Browser reasoning
→ 后台变化后重新学习
```

它正好位于“纯 API 重构”和“每次现场推理”之间。

## 10. 可以直接复刻什么

你已有 Runtime、浏览器、Cookie、CLI、MCP、原系统 API，因此不要做完整 Frigade。

先拿一个流程：

> 找企业 → 找最新待验收隐患 → 看整改证据 → 打开验收入口。

让 Learning Agent 多次跑通，并保存：Goal、Page/State、Action、Semantic Target、Resulting State、Role、Evidence。

运行时优先走已学 workflow；失败才调用 Browser reasoning。

第二阶段再做 Change Detection；第三阶段才做“高亮页面 + 人确认”的 Guided UI。

## 11. 不值得抄什么

- 不要做完整 Product Adoption SaaS；
- 不要全站扫描，先学 5–10 个最高价值 workflow；
- 已有稳定 API 的动作继续走 API；
- 不要把“自动学习”当可靠性的替代品，Coverage / Eval / Change Detection 才是难点。

## 12. 最大未知 / 反证

1. **复杂产品覆盖率可能被高估。** 几条漂亮 workflow 与数百状态、角色、异常分支完全不是一个难度。
2. **UI 行为不是业务规则。** 会点击并不等于理解为什么允许这么做，B/G 场景必须绑定 API、权限与业务规则。
3. **维护成本可能只是被隐藏。** 如果 retraining 后仍需大量人工验收，所谓 self-learning 只是换了维护位置。

## 与已有模式比较

- **Browzer**：Source 变化 → 派生文档自维护；Frigade 是 Software → Operational Model → Guidance/Action。
- **Airtop/Nex**：解决 AI 与确定性执行怎么分工；Frigade 解决 AI 怎样获得“具体软件如何工作”的知识。
- **Tadata**：观察人的真实工作，发现值得自动化的流程；Frigade 是 synthetic agent 主动探索软件，建立软件能力模型。

因此今天认为它确实新增了一个独立模式，而不是旧模式换行业。

# 主动淘汰 / 观察

## DealHub MCP for Admin — 观察，不入核心

它让 Agent 用自然语言修改 pricing rule、approval workflow、guardrail，很实用，但目前更接近 **Airtop 的 AI Build/Repair + Accordio 的 Agent-facing System of Record + Approval/Governance** 的组合，没有看到新的一级机制。

## Workable Agent — 观察，不入核心

“先结构化定义 hiring criteria，再让 Agent sourcing/screening”是正确产品设计，但 1–2 天可以用 ATS + structured intake + agent workflow 拼出大部分机制。产品价值高，不代表机制创新强。

## Lightfield — 强产品，暂不新增核心

“CRM 作为持续 customer world model”非常值得跟踪，但与 Atlas 的 Organization Context Layer、WRITER 的 Organization Learning Loop、Accordio 的 Agent-facing System of Record 重合较多。现阶段更像这些模式在 CRM 里的优秀组合，而不是新的一级机制。

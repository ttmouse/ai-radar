# AI 应用创新日报｜2026-09-30

## 今日结论

**今天没有发现达到核心创新标准的新产品。**

今天最值得研究的候选是 **OpenAI dots + ChatGPT Space**。它很重要，但严格执行 Composable Test 后，我把它放在 **Observe（3/5）**，不进入 Core。

原因不是能力弱，而是它目前公开出来的关键机制——持续运行、并行项目、跨应用执行、长期偏好/上下文、主动工作、共享团队空间、审批与安全边界——大部分已经分别出现在既有模式 #03、#06、#14、#17、#21、#27 中。它更像这些机制第一次被 OpenAI 大规模整合成消费级/企业级产品，而不是新的软件组织方式。

## 重点候选：OpenAI dots + ChatGPT Space

### 1. 真实问题

传统 Chat/Agent 的核心限制不是“不会做事”，而是**工作所有权仍然属于人**：人要记住目标、重新打开线程、补上下文、检查进度、再次触发。

长期项目因此被切成一系列人工唤醒的会话。

dots 试图把这一点改成：用户交付一个持续责任，Agent 自己维持工作状态并推进多个项目。

### 2. 旧工作流

```text
Human remembers responsibility
→ opens chat/tool
→ restores context
→ prompts Agent
→ waits for result
→ manually checks/continues
→ repeats
```

### 3. 新工作流

```text
Human assigns ongoing responsibility
→ Dot keeps persistent project state
→ works across apps/cloud computer
→ notices changes / continues work
→ prepares artifacts/actions
→ Human reviews exceptions or outcomes
→ Dot continues
```

OpenAI 官方给出的软件开发例子很具体：Dot 持续看客户反馈，发现重复需求，scope 小改进和 bugfix，构建、测试，然后把完整 PR 和演示视频交给开发者审核；与此同时开发者继续主线工作。

### 4. 最关键机制

真正值得看的不是“可爱 Agent avatar”，而是：

**Responsibility → Persistent Worker**

过去第一类对象是 Conversation / Task；dots 试图让 **ongoing responsibility** 成为 Agent 持续拥有的工作。

ChatGPT Space 则把这个工作放进 Human + Agent 的共享表面，而不是让 Agent 的状态困在个人会话里。

### 5. Composable Test

**结论：没有通过强创新门槛。**

用现有 Agent Runtime + automation/scheduler + browser/cloud computer + connectors/MCP + project state store + approval queue，在 1–2 天内可以拼出大约 80% 的核心工作模型。

真正难复制的是可靠性、安全监控、4000+ 应用生态、跨端分发和规模化基础设施；这些是工程/平台优势，不等于新的应用层产品机制。

### 6. Human / AI / Deterministic Software

**Human**
- 定义目标与边界
- 审核高风险动作和最终产物
- 处理例外/判断

**AI**
- 持续维护责任
- 拆解、推进并行项目
- 主动发现下一步
- 生成/修改工作产物

**Deterministic Software**
- 权限、连接器、账号身份
- 任务/项目状态持久化
- 安全监控与暂停
- 审批与审计边界

变化在于：Human 从“每轮工作的启动器”向“目标拥有者 + 例外判断者”移动。

### 7. 架构判断：事实 / 推断 / 未知

**已确认**
- Dot 可持续工作，并同时推进多个项目。
- 官方描述其可跨复杂项目和日常任务工作。
- 官方软件开发示例包含反馈监控、scope、build/test、PR 和视频交付。
- OpenAI 表示安全监控可以暂停或停止 Dot。
- ChatGPT Space 被官方描述为 humans and agents 的 shared surface。

**合理推断**
- Dot 必须有独立于单次聊天的持久项目/任务状态。
- 主动工作需要某种 scheduler/event trigger/continuation runtime。
- Space 很可能承担一部分 Work-owned Context，而不是 Agent-owned Context。

**未知**
- Responsibility 是否真的是明确的一等数据对象，还是营销层对长期 task/session 的称呼。
- Agent 如何判断“下一步值得做什么”。
- Context/Memory 的具体分层与压缩机制。
- 多 Dot 未来如何处理 authority、冲突、delegation 和共享状态。
- 企业审批、证据链和审计粒度到底有多深。

### 8. 与已有 Pattern 比较

- **#03 Goal → Autonomous Work**：高度重合。
- **#06 Persistent State → Proactive Action**：高度重合。
- **#14 Agent Workspace + Governance Layer**：安全与执行环境重合。
- **#17 Judgment Queue**：人逐渐处理例外/审核。
- **#21 AI Work as Shared Artifact**：Space 强化共享工作资产。
- **#27 Context Belongs to Work**：Space 有潜力强化，但目前证据不足以证明其对象模型真的如此。

与 Claude Code Projects 的差别主要是 dots 更强调持续自主推进；与 Ando 的差别是 Ando 从协作空间出发，dots 从持久 Worker 出发再进入共享 Space。

**真正新增：目前没有足够证据。**

值得继续观察的假设是：

> 如果 OpenAI 后续把 Responsibility 做成独立于 task/project/session 的一等对象，并让 Agent 对它持续承担 SLA、状态、预算和结果责任，那么可能形成新模式：Responsibility as First-class Work Object。

现在还不能编号。

### 9. 对 AI 产品 / 本地 Agent / B/G 的启发

对本地 Agent 最值得抄的不是 avatar，而是把长期目标改造成：

```text
Responsibility
├── Goal
├── Scope
├── State
├── Evidence
├── Next Action
├── Waiting Condition
├── Authority
├── Budget
├── Human Attention
└── Completion / SLA
```

这与当前长期目标 Agent 方向高度一致：不要让“同一个聊天持续很久”冒充持久工作；让工作对象持久，Agent 可以替换。

对 B/G 场景同样适用：周期任务、专项任务、持续异常监控都应该拥有持久责任状态，AI 负责持续推进，人处理高风险判断和例外。

### 10. 可以复刻 / 不值得抄

**可以直接复刻**
- Persistent Work Object
- scheduler/event trigger
- next-action loop
- browser/MCP/tool execution
- human attention queue
- evidence + approval
- 多项目并行状态

**暂时不值得抄**
- Agent 人格/avatar
- “多个 Agent = 更高级”的表面设计
- 为了持续运行而强行保持同一个 conversation
- 4000+ connector 数量竞赛

### 11. 最大未知与反证

最大的反证是：这可能只是 OpenAI 把 automation + Work + connectors + memory + cloud computer 包装成一个角色化入口。

如果未来拆开来看，Dot 没有独立的 Responsibility/Authority/State 对象，只是一个 persistent agent session，那么它在机制上并没有越过现有模式。

### 12. 跟踪判断

**3/5 — Observe**

产品重要性：高。
平台影响：高。
当前机制新颖度：中低。
继续跟踪重点：Responsibility object、multi-dot delegation、Space 的 work-owned context、authority/approval model。

## 主动淘汰 / 观察

### Autoheal — Observe，未入 Core
“AI 评估/修复 AI coding agent 留下的工作”与 #20 Agent Operations Agent 高度重合。自改进软件工厂值得关注，但当前证据更像 Agent Ops 在软件工程领域的实现，没有新增对象模型。

### Viralway — Reject
从 brief 自动生成并发布短视频，本质是生成 pipeline + publishing automation；1–2 天组合性很高。

### ZenABM — Reject
MCP + AI Agent 操作 LinkedIn Ads，属于既有 SaaS action layer/automation 的行业实现。

### GPT-6 Sol/Luna — Radar Reject
能力/成本曲线显著变化，但属于模型层，不是应用层产品机制。

## 今日 Pattern 判断

**新 Pattern：0。**

观察中的潜在命题：**Responsibility as First-class Work Object**。目前证据不足，不新增编号。

## 今日产品创新养料

> **不要把“Agent 一直在线”误认为创新。真正值得看的，是软件是否把“持续责任”从人的脑子里拿出来，变成一个拥有状态、边界、证据、下一步和完成条件的持久业务对象。**

## 为什么今天只选它

今天出现了多项 Agent、客服、治理和 AI 开发产品更新，但大多数仍是已有 Agent + Context + Tools + Governance 的行业组合。G5 值得单独留下，因为它提出的问题更基础：**当 AI 开始成为主要代码作者，人类是否还应该把 Code / PR 当成软件协作和审核的最高层对象？**

## 产品是什么

G5 是位于 Claude Code、Codex 等 Coding Agent 之上的 semantic + governance layer。它把业务需求、数据模型、业务规则、workflow、架构决策和组织 policy 组织成 System Ontology，并声称通过 self-learning bi-directional compiler 保持 Ontology 与代码双向映射。

官方核心主张不是普通的自然语言生成代码，而是：Intent 可以被编译、diff、merge、govern；修改 intent 会改变代码，修改代码后 ontology 也会重新学习。

## 真实问题

Coding Agent 让实现速度大幅提高，却把瓶颈推到理解、验证和协调：当 Agent 一次生成数万甚至更多代码时，人逐行 review 所有实现会越来越不现实。

传统流程：

```text
需求 → 人写代码 → Git Diff → Code Review → Merge
```

G5 尝试改成：

```text
Intent / Ontology
→ 人审核语义
→ Agent 生成实现
→ Tests / Policy / Trace 验证
→ Semantic Diff / Merge
→ 人裁决真正的业务冲突
```

## 最关键机制

1. **Intent 成为持久对象**：不是开发前写完就老化的 spec，而是贯穿系统生命周期。
2. **Bidirectional Grounding**：Intent ⇄ Implementation，而不是单向 Spec → Code。
3. **Semantic Diff / Merge**：冲突从文本层上移到业务语义层。
4. **Human Review 上移**：人重点审核需求、规则、架构、policy 和成本，而不是逐行阅读 Agent 输出。

## Composable Test

容易拼的部分：Spec + Claude Code/Codex + GitHub + Tests + CI + Approval，1–2 天就能得到大部分 Demo。

真正难拼的是：

```text
Legacy Code ⇄ Persistent Semantic Model ⇄ New Code
```

并在长期变化中保持 ontology 不漂移、code-intent traceability、semantic conflict detection 和跨 Agent policy enforcement。

因此判定通过，但真正创新是否成立取决于这层双向同步能否长期可靠。

## Human / AI / Software 分工

- Human：定义与裁决业务意图、架构和治理边界。
- AI：恢复旧系统语义，把批准后的意图转换为实现。
- Deterministic Software：版本、测试、trace、policy、approval、release、rollback。

核心变化：**人从代码作者/逐行审核者，上移为意图维护者和语义裁决者。**

## 事实 / 推断 / 未知

已确认：官方公开描述 bidirectional compiler、ontology-code trace、semantic merge、multi-agent coordination、policy 和 cost controls；并称已用于受监管行业的 legacy modernization。

合理推断：真正可靠的 ontology 必须拥有稳定 ID、revision、dependency graph 和 code trace metadata；semantic merge 很难只靠 LLM，必须与 deterministic validation 组合。

未知：大型持续变化代码库中的同步准确率、外部直接改代码后的恢复能力、ontology 可移植性、semantic merge 错误率，以及公司自报生产规模的独立验证。

## 与历史模式比较

它不是 Pattern 25 Business Semantic Layer：后者让 Agent 理解业务数据；G5 试图让 semantic model 成为软件实现本身的上位控制对象。

也不是 Pattern 20 Agent Ops：Nova 管 Agent 的运行质量；G5 管多个 Coding Agent 共同应该实现的 Intent。

它与 Kiro / GitHub Spec Kit 的 spec-driven development 最接近。新增点不是“有 Spec”，而是把 Spec 提升成 application-wide、持续存在、双向 grounding、可 semantic diff/merge/govern 的 System Ontology。

## 对本地 AI 原生研发的启发

不应该复制完整 G5。先验证一个更小的问题：**Intent 能否成为稳定控制层。**

V0：在真实项目建立 `/intent`，保存 product、entities、workflows、constraints、decisions。要求 Coding Agent 每次修改说明：改变哪个 Intent、哪些代码实现它、哪些测试验证它。

V1：建立 Requirement ID → Task → Code → Test → Commit 的 Trace Graph。

V2：对 Code Change 反向判断：它是否改变 Intent、是否冲突、是否需要人工批准。

## 对应急 / B/G 的启发

把隐患生命周期、角色权限、证据要求、状态流转、人工确认节点提升为机器可读的 Intent Layer。网页后台、桌面专家工作台和 Agent 都消费同一套业务语义，而不是分别实现自己的闭环。

这与你之前反复指出的“不同产品闭环不一致”是同一个底层问题：缺少实现之上的统一业务语义控制层。

## 最大反证

如果 Ontology 自己也持续漂移，G5 只是把维护代码的问题换成维护另一套模型。真正的验收标准不是生成多少代码，而是半年以后 Ontology 是否仍然比代码更可信、更容易维护。

## 主动淘汰 / 观察

- Zendesk Specialized AI Agents：行业 Agent + 企业 Context + Tools + Workflow，商业产品很强，但没有看到新的一级机制。
- AI Agent Hotlines：Agent 可以主动举报其他 Agent 的异常行为，概念新奇，但更像安全基础设施/研究机制，暂不进入应用层模式库。
- GPT-Live-1：模型/API 能力升级，不属于应用层产品机制创新。

## 今日产品创新养料

> **当 AI 把“实现”变得廉价以后，人类监督的位置应该上移，而不是继续强迫人类检查越来越多的机器产物。**

真正值得设计的新对象，可能不是更好的 Code Review，而是可验证、可追溯、可冲突合并的 Intent。

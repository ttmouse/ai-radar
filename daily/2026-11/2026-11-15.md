## 1. 重点观察：n8n durable schedule 与 Agent 恢复失效证据（Observe；Tracking 4/5）
**产品对象**：n8n 及 Nod 的持久任务调度/运行时，不是新发布的独立产品。公开问题：[n8n #43133](https://github.com/n8n-io/n8n/issues/43133)（11/08，导入工作流导致已发布工作流的持久 Schedule Trigger job 丢失）；[Nod #735](https://github.com/n8n-io/nod/issues/735)（11/11，任务询问用户后计划检查未启动）；[Nod #738](https://github.com/n8n-io/nod/issues/738)（11/11，确认模型失败导致动作失败）。这些是 issue 报告，不代表所有环境可复现，亦不代表修复已上线。

**真实问题**：持续工作的 Agent 的价值依赖可靠的触发、暂停、恢复与授权。但用户界面中的“计划已存在”与底层调度器中“下一次执行已登记”可能不一致。

**旧工作流**：用户设置自动化 → 软件保存工作流配置 → 认为计划任务将运行 → 失败后通过投诉/日志发现。

**可取的新工作流（分析建议，非已证实的 n8n 新产品功能）**：Human 定义目标、触发条件、期限和审批 → AI 提出步骤与异常处理 → Deterministic Software 持久化 Workflow Definition、Schedule Registration、Execution Attempt、Approval Decision 和 Result Evidence 五类对象 → 每次部署/导入/重启后核对定义与真实队列状态 → 异常进入待处理队列而不是静默失效。

**机制判断**：不是让 Agent 更聪明，而是把“未来会发生的动作”变成可验证的持久承诺。一个计划的成功标准不应是“配置保存成功”，而是“可观察、可恢复、可撤销且在授权范围内真正触发”。这是对已有 #06/#15/#20/#26 的工程细化，并非已验证的新 Pattern。

**Composable Test**：SQLite/Postgres + cron/queue + execution ledger + reconciliation worker + approval table + GitHub Actions/PM2，在 1–2 天可搭建限定场景 80% 体验，因此不晋级 Core。其创新价值更偏可靠性工程而非新交互原语。

**事实/推断/未知**：
- 已确认：GitHub Issues 记录上述失败报告；n8n 与 Nod 公开了相关项目。
- 合理推断：工作流定义与调度登记的双重状态，以及模型审批与确定性授权混用，可能导致静默失效或不可恢复等待。
- 未知：每个 issue 的根因、受影响版本比例、是否已经修复、真实生产复现率。不可把 issue 标题当作根因证明。
- 架构/Runtime/Context/Memory/Tool/Approval/Eval：调度和审批问题存在公开报告；具体实现细节及根因未核实。推荐的五对象模型属于分析设计，不是产品事实。

**分工**：Human 决定目标、审批与例外；AI 提议行动、识别异常；确定性软件维护任务登记、幂等、重试、授权、审计和实际执行结果。

**迁移**：本地 Agent 可先做任务登记核对器：每天比较“应存在的定时任务”与“实际调度器中的任务”，并对重启/导入/用户答复后恢复做故障注入。应急管理可用于周期性检查、整改到期提醒、专家复核：必须区分“任务创建”“已安排执行”“已执行”“业务闭环”。不值得复制整套通用 Agent UI 或开发新的调度框架。

**反证与高估风险**：这可能只是普通调度器 bug，不是 AI 特有问题；若仅靠可靠队列和幂等即可解决，则不应包装成 AI 产品创新。**Tracking 4/5（工程参考），Novelty 1/4（应用层机制）**。

**养料：持续自动化的最小可信单位，不是“保存了一条任务”，而是“系统对未来行动的可验证承诺”。** Human 负责授权与责任，AI 负责判断何时该行动，确定性软件负责保证计划已登记、状态可恢复、执行有证据。不要把普通调度可靠性问题误称为新的 AI 产品模式。

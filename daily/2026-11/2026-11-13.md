## 1. 重点观察：Plurai Simulation（Observe；Tracking 5/5；Novelty 3/4；尚不晋级）
来源：[官方发布 2026-11-11](https://www.plurai.ai/blog/introducing-plurai-simulation-self-improving-layer-for-ai-agents) · [架构详解 2026-11-11](https://www.plurai.ai/blog/how-plurai-tests-real-agents-in-simulated-worlds) · [测试选择 2026-11-11](https://www.plurai.ai/blog/deciding-what-to-test-lessons-from-building-a-simulation-engine) · [Product Hunt 2026-11-12](https://www.producthunt.com/products/plurai)。

**真实问题**：Agent 的失败不只发生在回答文本，还发生在跨 CRM、订单、支付、邮件、知识库的一系列真实状态变更。简单对话测试和孤立 mock 无法证明工具调用在同一业务世界中一致。

**旧工作流**：开发者写 prompt 和少量测试样本 → 人工 mock 单个 API → LLM Judge 评回答 → 生产暴露长尾状态错误 → 事后修复。

**新工作流**：编码 Agent 扫描真实 Agent 代码、工具和 KB → 人确认 mock/real 边界 → 生成共享状态的模拟世界（实体、用户角色、约束、API、文档）→ 在本地运行真实 Agent 与模拟用户 → 读取最终世界状态与执行轨迹 → 生成失败解释和修复提案 → 人接受修改 → 回放回归测试。

**核心机制**：测试对象由「一个问答样本」升为「带状态、约束和可演化事件的业务世界」。一个订单取消、退款、邮件通知必须作用于同一组状态，不能让三个 mock 各自给出看似合理但互相矛盾的结果。真实生产 trace 可以恢复成模拟场景，并用于后续版本回归。人以自然语言修改模拟世界的扰动条件。

**Composable Test**：用 pytest、模拟数据库、FastAPI mock、LLM 模拟用户、LangSmith/Langfuse、Coding Agent 可以在 1–2 天拼出限定领域 80% 的可见体验；因此不把完整产品组合认作强机制创新。区别在于自动从真实 Agent 代码推导工具依赖并生成**一致的状态世界**，这是有意义的工程难点，但还缺独立证据证明其跨领域可泛化、显著超出既有测试框架的机制价值。结论：Observe，不晋级 Core。

**Human/AI/Software**：Human 定义风险、测试意图、接受修复；AI 抽取 Agent 结构、生成场景、发现失败、提修复；确定性软件负责 schema、实体 ID、状态机、工具副作用、可解性检查、回放和版本绑定。LLM Judge 仅评需要语义判断的部分。

**架构事实**（厂商文档）：Claude Code/Codex/Copilot 插件；本地 SDK 执行真实 Agent；远端 backend 构建 world graph、mock、场景和评估；本地生成 plurai_sim/、simulate.py；mock 工具共享同一场景状态；代码和凭据留本地（厂商声明）；可用生产 trace、知识库、样本单据增强模拟。**合理推断**：共享状态可以减少孤立 mock 的假阳性；按 commit 绑定 world graph 便于回归。**未知**：真实环境覆盖率、world graph 与生产漂移、敏感数据上传边界、模拟用户真实性、独立复现实验、修复后生产事故下降幅度。官网 15x/82% 等指标不能当独立证据。

**可迁移原理**：Agent Eval 的基本单元应从 response 变为 world-state transition；评估 Agent 是否真正完成业务目标，而非是否说出了正确答案。

**AI 原生研发**：从 Git diff 自动生成状态一致的模拟环境，测试失败不仅存 transcript，也存初始状态、工具副作用、最终状态、断言和代码版本。**本地 Agent**：先复刻最小订单/邮件/日历模拟器与 trace replay，不必买全套平台。**应急/B/G**：围绕「隐患发现→整改通知→上传证据→专家复核→闭环」建立模拟责任主体、检查文书、整改状态、权限和时间线，测试 AI 是否误判已整改、越权下发、重复发文。

**直接复刻**：状态一致 mock、业务最终状态断言、生产失败回放、异常注入、人工审批修复；**不值得抄**：通用 world graph 自动生成平台、通用训练流水线、营销上的“递归自我改进”。

**最大反证**：模拟世界与真实业务的差异可能让测试通过率虚高；自动生成的测试与 Agent 共享同一错误假设；自我修复可能修改测试目标而非修正实现。跟踪 5/5，优先等待跨真实业务的独立事故率对照及状态一致性 Eval。

**历史比较**：#05 AI Build→Run→Repair、#13 Deterministic/Probabilistic、#20 Agent Ops、#24 Evidence Gap、#29 Operational Model 均覆盖其主干。**真正新增的候选机制**是“从 Agent 工具依赖自动构造一个可执行、跨工具状态一致的测试世界”；暂列 #20/#29 的强化实现，不创建 #31，等待独立反证测试。

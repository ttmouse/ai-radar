## 1. 今日最值得观察：Testifly｜谁有权修改测试的“正确答案”？

**来源**：[11/03 Product Hunt 发布与创始人答复](https://www.producthunt.com/products/testifly-launch)｜[官网](https://testifly.dev/)｜[Self-Healing 官方文档](https://testifly.dev/self-healing-adaptation)｜[CI/Production Monitoring](https://testifly.dev/runs-monitoring)｜[Blast Radius/MCP](https://testifly.dev/blast-radius-mcp)。  
**结果**：Observe；Tracking **5/5**；Mechanism Novelty **2/4**；Evidence **B**；不进入 Core，不新增 Pattern。产品在 2026-01-09 已有一次 Product Hunt 发布，本次为 11/03 新版本发布，不能误报为首次出现。

### 1.1 真实问题与新旧工作流

真实问题不是“不会写 E2E 测试”，而是：产品迭代导致 UI 定位、流程和业务规则不断变化；测试用例需要维护，错误的红灯增加噪声，错误的绿灯又掩盖真正的业务回归。

**旧工作流**：人编写 E2E → CI/部署运行 → 选择器/界面变化使测试失败 → QA 判断是否真的坏了 → 人改脚本 → 重新运行；线上环境配置错误可能直到真实用户报障才发现。

**Testifly 提出的新工作流**：
1. 输入 URL 和测试账号；Browser Agent 探索真实应用和登录后的流程，生成测试。
2. 在 staging/production/CI 定时运行；失败附带录屏与原因分析。
3. UI 选择器小幅变化时，自动修复定位和测试脚本；影响到业务行为时，试图区分有意变更与真正回归。
4. 不确定时，交给 Human 看视频/原因并确认“新流程是预期”或“这是缺陷”；确认后再更新测试、重跑或记录 Bug。
5. 通过 MCP/IDE 连接测试结果、代码变更与 Blast Radius，减少全量盲测。

**Mechanism Delta**：从“测试脚本是静态人写资产”转为“持续观察应用、自动发现和维护测试，但遇到业务意图变更必须有明确裁决”的测试工作对象。其真正难点不是 Agent 能否点击按钮，而是**谁有权更新测试预期**。

### 1.2 最关键的反证：官方营销与创始人答复并不等价

[Self-Healing 文档](https://testifly.dev/self-healing-adaptation) 使用了“No manual updates, ever”并表示特性行为变化时也会自动调整测试。这一表达容易让人以为任何变化都可以无人确认地变成新正确答案。

但创始人在 [11/03 Product Hunt 问答](https://www.producthunt.com/products/testifly-launch) 中针对“注册表单有意变化还是 Bug”明确表示：**不确定时 maker 需要确认一次**；系统再决定更新测试、重试或标记 Bug；Jira/Linear 工单和 IDE 变更可提供意图线索。创始人也明确要求不要宣传“系统会随着部署上下文长期自动学习”，因为 Docs 尚未证明这点。

这并不必然是已证实的产品缺陷，而是**自动适配边界必须核实**：
- Selector 漂移：若业务结果不变，可以自动修复；
- 已授权的业务规则变化：应先验证变更来源/版本，再更新预期；
- 意图不明：不得为了让测试变绿而自行修改 Expected Result；
- 真实业务回归：必须保留失败证据并阻止错误放行。

官方/创始人还说明：当前只测试真实浏览器 Web；原生移动尚未提供；真实 2FA 需要特殊测试账号或 staging 绕过；测试可能修改业务数据，因此建议隔离环境；不能替代单元测试；不同屏幕尺寸支持仍在近期计划中。不要将“Zero maintenance”理解为零风险或零人工责任。

### 1.3 Human / AI / Deterministic Software 分工

| 角色 | 旧职责 | Testifly 所提议的新职责 |
|---|---|---|
| Human | 编写维护用例、判断所有红灯 | 明确业务验收意图；只裁决语义不确定的变更和高风险例外 |
| AI | 辅助生成单个测试 | 探索真实流程、生成测试、判断漂移/回归、给出原因候选 |
| Deterministic Software | 执行固定脚本、记录结果 | 保存测试版本、账号/环境、真实浏览器 Run、视频、CI Gate、变更前后证据；禁止未经授权的预期升级 |

**已确认公开设计**：URL+账号驱动发现；自愈/变更适配/回归区分的产品说明；CI Gate、生产环境定时运行、录屏、MCP/Blast Radius；创始人关于人工确认、2FA、环境隔离、原生移动限制的具体答复。

**合理推断**：如果把 TestSpec / ExpectedOutcome / FlowVersion / EvidenceRun / Approval 建成持久对象，人工维护成本可能下降；但需要独立验证。

**未知**：真实业务回归被“自愈”吞掉的比例、复杂多角色测试覆盖率、对生产数据的副作用、误报漏报、人工裁决频率、测试对业务意图的长期一致性。未自行运行产品或独立对照测试。

### 1.4 Composable Test、最近邻模式与结论

使用 Playwright、Browser Agent、CI、录像、LLM 差异解释、Git 变更、Linear/Jira、SQLite 版本化 Expected Result 和人工 Approval，**1–2 天可实现单应用主要演示**。跨角色、复杂登录、长周期可靠性和真实回归识别难度高，但属于工程可靠性挑战，不自动构成新产品机制。

最近邻：**#05** AI Build → Software Run → AI Repair（生成/维护测试）；**#08** Observe → Detect Pattern（主动发现流程）；**#13** Deterministic/Probabilistic Split（模型提出、真实 Run/CI 验证）；**#15** Proposed Action（修改预期先成待批准动作）；**#24** Evidence Gap → Active Investigation（失败触发调查）；**#30** Intent as Source of Truth（正确答案不能由执行器擅自改写）。

**它真正新增了什么？** 在 QA 领域把“测试自身可以演化”与“测试意图不可自行篡改”的边界具体化；是现有模式的交叉验证，不是 #31。

### 1.5 本地 Agent / B/G 的最小复刻

已有 CLI、浏览器、Agent Runtime、文件/MCP，无需重建 QA SaaS。先定义：

`FlowContract(id, role, env, expected_outcome, version, owner)`  
`ObservedRun(flow_id, browser_trace, screenshot, actual_outcome, commit)`  
`ChangeProposal(reason, old_expectation, new_expectation, evidence, approval)`

做 12 个对照用例：4 个纯 UI 变化、4 个真实业务回归、4 个合法需求变更；测 **错误自动放行数（第一优先）**、人工审核时间、错误阻断、复现可读性。明确规定只有 Locator 可在条件满足时自动改，Expected Outcome 的语义改变需要审批。

对应急管理：专家检查点/隐患识别规则可以随法规和流程演进，但不能因为现场材料不符合旧规则，AI 就自行把验收标准改成“已通过”。任务、检查、证据、规则版本、正式结论必须解耦。

**不值得抄**：全量自建测试平台、宣传零维护、直接用 LLM Judge 替代业务断言、无隔离账号地在生产执行写操作。  
**最大反证**：若独立测试发现 Testifly 的自愈会静默吞掉关键回归，产品价值可能从减少维护成本变成制造虚假安全感。**继续跟踪 5/5。**

## 2. 第二个 Observe：Synter Canvas｜广告 Agent 的“可信动作”必须与真实转化口径绑定

**来源**：[11/03 Product Hunt 与创始人答复](https://www.producthunt.com/products/synter-canvas)｜[官方 MCP/审批文档](https://docs.synterai.com/mcp/approval-model)｜[官方产品](https://synter.dev/)｜[官方 Attribution](https://syntermedia.ai/features/attribution)。  
**结果**：Observe；Tracking **4/5**；Novelty **2/4**；Evidence **B**。该公司早在 [2026-01-29](https://docs.synterai.com/changelog/mcp-server-launch) 已推出 MCP；11/03 是 Canvas 应用层发布，不能误称为首次有广告 Agent。

**旧流程**：优化师分别在 Meta/Google/TikTok 等平台查看报表、比较 CPA/ROAS、决定预算、逐平台改动；不同平台各自声称转化归因，汇总可能重复计数。

**新流程**：Agent 汇总广告平台与 CRM/GA4/服务端事件 → 统一业务转化口径 → 提议 Campaign/预算/素材变更 → 读取真实平台状态、做 preflight 和风险评估 → 审批/受限自动化 → 平台 API 执行 → readback / audit。

**具体证据**：
- 创始人 11/03 明确解释跨平台预算调整不应相信任一平台自报归因，而应从 CRM/GA4/Server Events 去重后比较；增量性检验仍在添加中，不能当作已交付。
- [官方审批文档](https://docs.synterai.com/mcp/approval-model) 明确 `Off/Suggest/Auto` 多档位、硬性预算上限、按工具/金额/时间拦截、`pending_review + audit_id`、`dry_run`、只读模式、读回验证。
- **重要限制**：文档说明 production 的未审批 Campaign Plan 不能执行，且 `qa_override_approved` 默认 false；但 staging 的 API Key/MCP 途径可以自动批准 draft/in-review plan，默认 true，并记录为 “MCP Operator”。这是明确的**环境边界**，不能据此断言生产审批被绕过；却说明测试环境的绿灯不能自动证明生产授权路径正确。
- 另有保护性暂停/降低预算可以按策略立即执行；因此“所有动作都必须人工批准”也不是精确描述。
- [官方 Readback](https://docs.synterai.com/mcp/approval-model) 仅覆盖指定平台，其他平台返回 unsupported；不能将所有写操作宣称为已独立核验。

**Composable Test**：广告 API + MCP + CRM/GA4 事件 + 规则引擎 + Approval + 审计，可以在 1–2 天针对 Meta/Google 做大部分流程原型。30+ 平台集成与归因口径治理很有商业价值，但并未证明新的基本软件组织方式。归属 **#15、#25、#26、#13、#29**，不新增 Pattern。

**Human / AI / Software**：Human 定义 ROAS/CPA 目标、预算边界、归因口径和例外；AI 提出跨平台投放调整；确定性软件掌握实际转化去重、权限、预算上限、变更审计与平台读回。**真实问题不是 Agent 会不会调整预算，而是它是否基于独立的业务真值做决定。**

**对现有 FB/Google 投放业务的可迁移实验**：先做只读版，统一 Install/FD/Purchase/ROAS 的事件定义，给每次预算建议附 `attribution_source + evidence_window + current_budget + proposed_budget + risk + expected_result`；在人工批准前，不让 Agent 写账户。比较 2 周内错误建议率、人工分析时间、真实增量 ROAS。不要先复制 30 平台连接器或 Canvas。

**最大未知**：跨平台去重的实际误差、平台回传延迟、因果增量效果、账户权限分离、预算错误回滚、正式生产审批是否在所有执行路径一致。**继续跟踪 4/5**。

## 4. Maturation（10/21—10/28）重新检查

### 4.1 Fini Agent Handshake（10/28）：语义相同的请求，不应被多个 Agent 反复改写出不同决定

[官方完整机制页](https://www.usefini.com/agent-handshake) 现可直接查看 Intent 归一、账户身份匹配、规则校验、草稿发送前检查、超出规则的退款/例外交给 Owner、审计日志等产品对象。**新证据成熟的是治理流程描述，不是独立性能结果**。厂商的“无论问多少次都给同一个答案”需要在真实政策更新、不同账户/时间窗、身份冒用和例外审批下验证。

这可由 **#13、#15、#22、#23、#26** 解释；尤其 #23 对抗性 Agent + 独立裁决器，但本例并未证明使用了独立 Referee，不能机械套用“对抗架构”。**Observe，未晋级 Core**。可迁移原则：将 `RequestIntent + PolicyVersion + AccountFacts + Decision + ExceptionApproval` 与自然语言表达分离；“一致”必须是同一业务条件下的一致，不能阻止合理政策变更。

### 4.2 Entire Trails（10/26）与 4.3 Tiden（10/23）

已对照 [Entire](../../products/entire.md) 和 [Tiden](../../products/tiden.md) 的长期档案。两者分别强调持续 Trail 与独立 Intent/Spec→Run Evidence→Gate。今天 Testifly 的“自愈可能重写验收”反证强化了 #30：**Expected Result 的修改必须有来源与版本，不能由同一个执行者无条件重写。** 本轮没有新的独立部署/误放行对照，历史 Core 判断不变；未对原档案做无实质信息的修改。

> **今日最值得记住的产品创新养料：让 AI 自动修复，不等于允许 AI 修改“什么算正确”。** Human 确定业务意图和例外；AI 发现偏差、提出修复；Deterministic Software 维护验收标准的版本、授权、真实执行证据与回滚。最危险的系统是它看起来一直绿灯，却悄悄失去了阻止错误的能力。

## 1. 重点观察：Plurai SCOPE（Observe；Tracking 4/5）
**来源**：[官方 2026-10-29](https://www.plurai.ai/blog/introducing-scope-compile-any-policy-into-a-stable-efficient-program)；[研究论文](https://arxiv.org/abs/2610.31062)。

**真实问题**：Agent 的授权/合规策略是多条件、多轮、带例外的业务规范。用大模型每次直接解释整套规则，可能昂贵、不稳定，且难定位哪条规则导致判断。

**旧流程**：策略文本 → 每次将全文发给 LLM Judge → 得到允许/拒绝判断 → 人工排查不一致。

**新流程**：Human 定义自然语言政策和种子样例 → 编译器把政策拆为小模型二元谓词、确定性抽取器与 Python 组合代码 → 对抗样本查找偏差并迭代编译 → 运行时执行较小的程序 → 每个结论能追溯到谓词及规则分支。

**机制**：把“政策文本”升级为可编译、可测试、可追溯的运行时程序。模型只承担窄语义判断，计数、分支、阈值由确定性代码处理。对抗式样本针对规则覆盖盲区，不仅拟合固定数据集。

**事实**：官方 10/29 技术文档和论文描述 SCOPE、SDK、四类策略评估任务及自测；**推断**：在某些复合策略下比单体 Judge 更稳定、更便宜；**未知**：独立生产复现、政策变化后的回归可靠性、错误谓词造成的系统性漏判、策略编译器的安全边界。厂商 9/12 单元胜出或持平是自测，不能直接外推。

**Composable Test**：LLM 拆规则 + Python 规则引擎 + 小模型分类器 + pytest + 反例生成，在 1–2 天内可复刻限定领域的主要交互。SCOPE 的优化器与自动编译有研究复杂度，但技术复杂不等于产品机制创新；更像 #13 Deterministic/Probabilistic Split、#15 Proposed Action、#20 Agent Ops、#30 Semantic SDLC 的深化，不创建 #31。

**分工**：Human 定义政策、标注关键反例、批准策略版本；AI 编译候选谓词和寻找反例；Deterministic Software 执行明确规则、版本控制、权限与审计。注意：小模型谓词仍是概率判断，不能称为全确定性授权。

**迁移**：应急管理可用“哪些整改复核必须专家确认、哪些照片缺证据、何时不得闭环”构建 Policy-as-Executable-Artifact。AI 原生研发可将验收规范编译为可回放断言。已有本地 Agent 可直接复刻 5 条高风险规则的最小编译/评估闭环；不值得先复制 SCOPE 通用优化器。**反证**：简单规则引擎 + 单次 LLM 解释可能已经足够，复杂编译反而增加错误和维护成本。跟踪 4/5，等待独立可复现基准及变更审计案例。

## 2. Fresh 观察：Nectar Creator Agent（Observe；Tracking 3/5）
[TechCrunch 2026-11-12](https://techcrunch.com/2026/11/12/nectar-launches-an-ai-agent-to-automate-creator-discovery-and-outreach-for-brands/)：从 3 亿以上创作者资料中发现候选、理解视频与品牌适配、持续排名、发私信、管理合同/礼赠/履约，并保留历史互动。公司称已覆盖 Instagram/TikTok；MCP 接入是计划，不是已完成能力。

**旧流程**：人工筛选 → 表格记录 → 手动私信 → 跟进合同/履约。**新流程**：品牌设目标与语气 → Agent 连续发现和维护候选 → 提议并发送外联 → 将关系状态与营销结果连接。

**Composable Test**：爬取/搜索 API + CRM + LLM 视频分析 + 自动外联 + 定时任务，限定场景可拼出 80% 核心体验；区别主要是创作者数据覆盖和行业运营，不是新的软件组织机制。对应 #06/#08/#19/#25/#26。未知真实转化、骚扰/隐私风险、人工审批粒度及多平台身份一致性。对投放业务可借鉴“持续更新潜在合作关系”，不值得复制创作者数据库。

## 3. Maturation：Nod 的真实失效证据
[n8n Nod GitHub Issues](https://github.com/n8n-io/nod/issues) 11/11 出现 #738（确认模型失败导致动作失败）、#735（Agent 向用户提问后计划检查不启动）、#737（Windows 后台服务无响应）。这些是公开 issue 报告，**不是已复现的普遍缺陷**。它们揭示两条重要边界：
- 审批判断服务不可用时，Agent 不能把“未能确认”当作“已授权”；必须显式 fail-closed、记录原因和可恢复操作。
- 用户回复后的后台调度与恢复，是独立于 Agent 推理的持久状态机问题。
这进一步支持 11/12 Nod Observe 结论，不晋级 Core。可用故障注入测试审批模型超时、重启后续跑、重复动作幂等性。

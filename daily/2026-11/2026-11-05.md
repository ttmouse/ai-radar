## 1. 今日主观察：fileForensics｜AI 读懂文件之前，是否应该先相信文件？

**身份与时间**：[fileAI 官网](https://www.file.ai/fileforensics)｜[官方 API 文档](https://docs.file.ai/forensics/overview/)｜[检测器/状态定义](https://docs.file.ai/verify/forensics/)｜[Product Hunt 新功能发布](https://www.producthunt.com/products/fileai-ai-ocr)。fileAI 早在 2025 年已发布 OCR/MCP；此次研究对象是新推出的 fileForensics，而非首次出现的 fileAI。

**结果**：Observe；Tracking **5/5**；Mechanism Novelty **2/4**；Evidence **B**。不是 Core，不新增 Pattern。

### 1.1 真实问题

企业用 OCR/LLM 把发票、身份证明、理赔材料、检查照片和业务附件抽取成结构化字段，接下来往往直接让 Agent 或规则引擎执行后续流程。问题是：**抽取准确，只说明正确读出了文件内容，不说明文件本身没有被伪造、编辑或复用。** 对高风险业务，这一层信任缺口会被自动化放大。

**旧工作流**：上传材料 → OCR/AI 抽取 → 字段校验 → 自动处理/人工抽查。原始文件真实性检查通常依赖另一个流程、专家经验或事后反欺诈。

**fileForensics 提议的新工作流**：
1. 在上传时开启 `FILE_FORENSICS`，或用已存储文件的 `file_id` 发起 `POST /v1/forensics`。
2. 在原始文件上并行运行文件结构、修改痕迹、来源凭证、AI 生成、复用/重复、内容一致性等检测；与提取流程分离。
3. 每个 detector 返回独立状态与证据；`issue` 进入复核，`skip` 不代表通过，`error` 也不能当作无风险。
4. Human/业务规则根据风险和业务价值决定复核、补件或继续处理；系统记录检测版本、来源和裁决。

**Mechanism Delta**：从“文档一旦被成功解析就可被业务系统消费”，变为“原始证据的可信性是进入后续 AI 自动决策前的独立门槛”。这是值得迁移的控制点，但并非全新一等对象：现有证据治理、审批和异常队列可表达。

### 1.2 源码/API 层面的已确认事实

- [官方 Overview](https://docs.file.ai/forensics/overview/) 列出 **55 项检查**：18 项基础文件检查、20 项 forensic 检测、17 项内容完整性问题；其中 AI-generated text 检测被标注为 **尚未启用**，不能宣传所有检查都已能独立给出结论。
- API 以 `run_id` 跟踪异步检测；`POST /v1/forensics` 的 `spec_filter` 必填，避免将来增加检测器时悄悄改变旧集成的行为。[API Reference](https://docs.file.ai/verify/forensics/)
- `queued / running / complete / error` 是 **Run 状态**；`none / issue / found / skip / error` 是 **Detector 状态**。**Run complete 不等于所有检查通过**。`web_presence` 缺失不能解释为“没在网上出现”。
- 官方 API 文档写明 **没有统一的全局风险分数**，建议按单项信号路由；[营销页](https://www.file.ai/fileforensics) 仍强调可汇总的评分卡/置信分。这不必然矛盾：可能是平台展示层按业务规则聚合，但不能把营销评分当成 API 的统一可验证事实。
- 检测结果提示的是可疑迹象，**不是对文件“真/假”的法律或事实裁决**；官方保留 Human-in-the-loop 的最终判定。

### 1.3 Human / AI / Deterministic Software 分工

| 角色 | 旧流程 | 新流程中的合理分工 |
|---|---|---|
| Human | 人工抽查、判断疑似欺诈 | 定义证据可接受性、风险阈值、最终复核与申诉 |
| AI | OCR/字段提取、简单内容分析 | 发现图像/内容异常、给出有定位的可疑信号 |
| Deterministic Software | 存文件、跑抽取、推进流程 | 保留原文件哈希、检测器版本、每项状态、业务 Gate、复核记录与真实执行结果 |

**已确认**：上传与存量文件均可触发检测；检测项独立返回；异步轮询与重试；部分检测尚未启用。  
**合理推断**：把可信性检查放在 Agent 决策之前，可减少“精确读取假材料”带来的错误自动执行。  
**未知**：各类真实造假样本的误报漏报率、对低质照片/扫描件的鲁棒性、篡改检测器之间的相关性、来源独立性、生产吞吐和申诉成本。没有独立对照实验，不能声称能够“证明真实性”。

### 1.4 Composable Test v2 / Default Workflow Test

**Composable / Commodity（主要体验）**：OCR/LLM + 文件哈希/EXIF/PDF 元数据 + C2PA/签名校验 + 图像异常检测 API + 规则引擎 + Review Queue，在 1–2 天能针对有限文件类型组合出 80% 的演示。跨格式检测器质量、对抗性样本、规模化证据保全非常难，但主要是专业算法/可靠性壁垒，不自动等于新产品机制。

**Default Workflow**：厂商尝试把“原文件可信性检查”前置为默认业务门槛；但缺少独立生产数据证明用户真的改变默认工作流。故维持 Observe。

**最近邻**：#16 Context Supply Chain（外部证据不默认可信）、#24 Evidence Gap → Active Investigation（发现缺口并调查）、#13 Deterministic/Probabilistic Split（信号与规则裁决分离）、#15 Proposed Action（可疑时不自动推进）、#17 Judgment Queue（异常才由人裁决）。**它真正新增的是这些模式在“原始文件可信性 Gate”上的清晰实现，而非新 Pattern。**

### 1.5 对本地 Agent、应急管理和 B/G 的最小复刻

不必复制 55 个检测器或购买完整平台，先建立独立 `EvidenceGate`：

- `Evidence(id, subject_id, source, file_hash, captured_at, provenance)`
- `CheckRun(id, evidence_id, detector_version, status, checks[])`
- `Finding(check, status, location, explanation, source_ref)`
- `Disposition(evidence_id, accepted|review|rejected, owner, reason, time)`

在应急检查里，先对上传照片、制度台账、整改凭证做三类基础检查：**文件是否重复复用、内容/时间与责任主体是否一致、必要的原始证据是否缺失**。将疑似问题放进专家复核队列，不自动判定“造假”，也不因检测器无结论就自动验收。做 30 份真实/历史可脱敏材料 + 10 份人工制作的对照材料，测高风险漏放、误报、专家复核成本和证据可追溯性。

**不值得抄**：从零研发通用深伪检测模型、把置信分当作事实真值、让 Agent 同时负责生成/审查/最终裁决。  
**最大反证**：若大多数真实问题来自业务上下文而不是文件篡改（例如合法照片拍错地点），通用文件取证的边际价值会显著低于“责任主体/检查点/时间/任务”交叉验证。**继续跟踪 5/5。**

## 2. 第二个 Observe：kosa8｜治理约束应该在 Agent 之外执行

**来源**：[官网](https://www.kosa8.com/)｜[2026-10-17 技术报告](https://www.kosa8.com/research/kosa8-research-paper)｜[2026-10-31 安全边界说明](https://www.kosa8.com/security/)｜[11/04 Product Hunt 发布与创始人问答](https://www.producthunt.com/products/kosa8)。

**结果**：Observe（Agent Runtime/治理层，不是应用层 Core）；Tracking **4/5**；Novelty **1–2/4**；Evidence **B**。

**问题**：Agent 在能执行任意代码、访问文件和 MCP 时，Prompt 层安全要求无法阻止已经失控的执行进程。

**旧流程**：Agent 在用户环境或普通容器执行；模型被要求遵守限制；权限、网络和凭据可能与进程混在一起。

**新流程**：每个不可信 Agent 进入独立 microVM；宿主 `kosa8d` 执行网络白名单、密钥代理、审批和哈希链审计；允许快照、恢复与分叉。创始人进一步解释：fork 复制沙盒状态但不复制真实密钥或 broker，若需要 API 访问要创建新的受代理沙盒。

**重要边界**：
- 官方明确 `kosa8 run` / Docker 兼容接口走共享 VM；只有 `kosa8 sandbox` / `kosa8 agent run` 是每工作负载独立 microVM。不能一概宣称所有容器都完全独立。
- 占位凭据不能直接泄露真实密钥，但**运行中的恶意 Agent 仍可能沿允许的目的地主动消耗该凭据**，需要最小权限和供应商侧限制。
- [安全页](https://www.kosa8.com/security/) 明确尚无第三方渗透测试或 SOC 2 报告；[技术报告](https://www.kosa8.com/research/kosa8-research-paper) 的 1,142 个测试和竞争比较是**厂商自测/自定义框架**，不应当作第三方安全认证。

**Composable Test**：microVM + egress broker + vault + policy + audit 可以通过已有隔离和治理组件实现，生产级安全集成困难但主要是基础设施工程。对应 #14 Agent Workspace + Governance Layer、#15 Proposed Action、#16 Context Supply Chain、#22 Agent Identity。**没有新的应用层工作对象，不能因技术复杂而晋级 Core。**

**对本地 Agent 的最小借鉴**：高风险 Tool Call 由 Agent 外的执行代理统一判权；不可变授权范围；短期凭据；“请求执行/已执行/真实结果”分离；写操作附可回放证据。无需为应急平台从零实现虚拟化内核。  
**最大未知**：真实对抗测试、跨宿主凭据与挂载风险、运维开销、审计记录的独立可验证性。**继续跟踪 4/5。**

### 4.1 Agno CompanyOS / AgentOS

[Agno v3.1.12，2026-10-29](https://github.com/agno-agi/agno/releases/tag/v3.1.12) 提供新的**可证伪实现细节**：
- Claude/Codex 原生审批可以在数据库里保存 `PAUSED` Run，并把批准/拒绝传回**同一次原生执行**，不是重新执行原 Prompt。

## 5. 跨产品机制判断：今天真正新增了什么？

**没有新 Pattern。** fileForensics、kosa8、Agno 三个独立方向共同提供了同一原则的更多证据：模型可以提出判断，但可信证据、权限和执行结果必须由独立机制承接。它们分别落在文件、执行环境和工作状态，不应为了三个行业形态制造三个新编号。

今天比昨天新增的具体认知是：**可信性不只属于输出结论，还属于输入材料；且“无法判定”必须成为正式状态，而不是被系统自动折算成通过。** 这是 #16/#24/#13/#15 的边界补强，不是独立 #31。

## 7. 今日结算

- **Core 0**：今天没有发现达到核心创新标准的新产品。
- **Observe 2**：fileForensics（证据可信性 Gate）、kosa8（外置执行治理）。
- **Reject / 去重 4**：OpenMail、QualityLayer、AirJelly、Basedash；原因见第 3 节。
- **Maturation 3**：Agno CompanyOS、TheySaid 4.0、Hycli；均未晋级。
- **新正式 Pattern 0**：仍为 30 个。

> **今日最值得记住的产品创新养料：不要把“能读取”当作“能相信”，也不要把“任务已完成”当作“所有检查已通过”。** Human 定义可接受证据和风险边界；AI 发现异常、提出假设；Deterministic Software 维护来源、每项检测状态、权限、真实执行结果与申诉/复核。输入可信性、输出正确性和执行授权，应该是三个独立 Gate。

## 重点观察：Stitch AI——Agent 进入业务系统原生权限边界

**时间与来源**：Stitch 官方 2026-11-17 公告（属于成熟观察，不冒充 Fresh）：https://www.stitch.co/press/stitch-casts-patrick-j-adams-to-launch-stitch-ai-agentic-ai-for-banks

**真实问题**：银行运营 Agent 若仅在外围读取副本、通过不受治理的脚本操作核心账本，容易产生权限、状态和审计断层。

**旧工作流**：员工使用银行核心系统的受控 UI；外围 AI 只能建议或在其他工具中执行；人手动转录动作并核验。

**新工作流（厂商宣称）**：Copilot 查询并操作银行产品配置；预置 Agent 执行开户、信贷、催收流程；Agent Harness 提供权限、审批、审计。Agent 直接调用核心系统的服务，而非维护业务记录副本。

**机制**：Agent 具有独立身份与 scoped permission；maker-checker；超限请求人工批准；动作在业务核心服务中执行并审计。核心不是“银行有 Agent”，而是业务状态与权限系统仍为执行的唯一真值。

**Human / AI / Software**：Human 定义授信政策、风险阈值、复核责任；AI 识别业务目标并提出/执行允许范围内动作；Deterministic Software 核验身份、额度、权限、审批和账本状态，留存审计证据。

**架构证据表**：
- 已确认的官方产品声明：三种产品入口（Copilot、预置 Agent、Agent Harness）、独立 Agent 身份、范围权限、maker-checker、审计。
- 合理推断：核心服务原生集成可减少外部复制和状态不一致。
- 未知：Agent Runtime、Memory、具体 Tool schema、审批事务原子性、Eval、回滚机制、生产成功率；官方发布不能代替独立测试。

**Composable Test**：用已有 Agent Runtime、RBAC、maker-checker、API、审计日志可在限定沙箱复刻大部分可见交互；真正难的是银行系统原生控制面和生产级治理，而技术集成难度不等于应用层新机制。因此 Observe，不晋级 Core。

**与历史模式比较**：#13 确定性/概率性分工、#15 Proposed Action、#22 Agent Identity、#26 Agent-facing System of Record 已覆盖。新增的是金融核心系统的垂直落地证据，**不新增模式编号**。

**可迁移原理**：AI 不应自己成为账本或最终权限判定器；所有有副作用的动作经过业务系统已有规则与状态验证。

**对 AI 产品设计/AI 原生研发/本地 Agent/应急 B/G**：将“检查结论建议”和“正式文书下发”分开；专家审批通过之后由业务系统执行；Agent 只能提交受限命令，业务系统产生唯一回执。可复刻：RBAC + 审批对象 + 业务状态机 + 审计；不值得抄：银行产品配置、金融支付/授信规则、通用 Agent Harness 平台。

**反证/高估风险**：若 Agent 仅复用既有 API 和权限，无新增交互原语，则是可靠的行业集成而非新模式；缺少真实授权误判率和生产测试。**继续跟踪 4/5**，等待真实产品演示、开发文档与外部用户证据。

## Fresh 观察：Backdrop

官方/创始人在 Product Hunt 近期发布中描述：从录屏教授工作流、共享组织上下文、Agent 任务交接、技能库、权限和审计。https://www.producthunt.com/products/backdrop

**事实**：创始人说明录屏教学、跨工具执行、任务队列式交接；**推断**：录屏比手写提示词更容易捕获隐性操作步骤；**未知**：从演示到稳定可复用流程的成功率、权限是否在 Tool 层强制执行、工作流变化后如何修复。

**Composable Test**：录屏转步骤、浏览器自动化、Agent Skills、Slack/Asana、审批日志可组合多数体验。历史 #05/#07/#19/#21/#27 覆盖。继续 Observe（3/5），不重复纳入核心产品档案。

## 今日产品创新养料

**“Agent 原生接入业务核心”不等于“Agent 获得业务真值的决定权”。** 真正可信的分工是：人定义责任与授权，AI 提出或执行受限动作，确定性业务系统对每一次状态变更作最终裁决。是否构成新产品模式，还必须证明它改变了人与软件的基本协作原语，而非仅做深度集成。

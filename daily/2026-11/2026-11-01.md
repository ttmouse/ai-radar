## 1. 条件 Core：Backenly —— 把后端运行状态变成可验证、可治理、可持续维护的对象

**来源**：[官网](https://backenly.com/)｜[开源代码](https://github.com/backenly/backenly)｜[架构说明](https://github.com/backenly/backenly/blob/main/AGENTS.md)｜[变更验证器](https://github.com/backenly/backenly/blob/main/lib/changes/verify.ts)。**状态**：条件 Core；Tracking 5/5；Mechanism Novelty 3/4（组合型结构变化）；Evidence B。**不新增 Pattern。**

### 1.1 真实问题与旧工作流

已有 Coding Agent 能生成 SQL、数据库 Schema、接口、认证和配置。但「代码写好了」「migration 执行成功」「真实生产系统仍满足安全和业务约束」是三个不同事实。人仍然要审核危险操作、检查 RLS、维护索引、处理配置漂移、发现失败并恢复。

**Before**：
```text
Human 提业务需求 → Agent 生成 SQL/API → 人运行/审查迁移
    → 上线 → 监控发现故障 → 人调查/修复/验证
```

### 1.2 新工作流与机制

**After（产品设计，非独立验收结果）**：
```text
Human 定义目标/风险边界
    ↓
Coding Agent 经 MCP 读取状态、提出结构化后端变更
    ↓
Governed Change：身份/权限/影响/版本/快照/审批
    ↓
确定性软件执行，并从真实 Postgres 读回验证
    ↓
上线后持续探针：观察 → 发现已知缺陷 → 提议修复
    ↓
可逆且低风险 → 自动修复 → 后置验证/回归
高风险/不可逆 → Human 审批 → 执行与验证
    ↓
可追溯变更记录；失败或无法验证不伪装成成功
```

**机制不是 MCP，也不是 AI 自动写 SQL，而是把后端状态的持续维护责任，从开发者手工巡检转向受治理的确定性控制层。**

官方将 Postgres、PostgREST、Auth、Storage、Realtime、Functions 暴露为 Agent-facing 能力；Agent 提出动作，后端平台统一执行和审计。自愈的部分修复是**规则驱动**，并非每分钟由 LLM 自主判断。

### 1.3 四个源码层面可检查的证据

**① 变更后置验证不是一句「完成了」。** [`lib/changes/verify.ts`](https://github.com/backenly/backenly/blob/main/lib/changes/verify.ts) 使用 `confirmed / contradicted / inconclusive` 三态结果，检查预期效果、连带损坏、RLS、凭据表暴露、认证与 API 可用性等。验证规则由控制层决定，不接受 Agent 自行降低验证要求。

**② 人的审批边界是硬规则。** [`lib/autonomy/autonomy-level.ts`](https://github.com/backenly/backenly/blob/main/lib/autonomy/autonomy-level.ts) 有 OFF/CONSERVATIVE/BALANCED/AGGRESSIVE 档位，但 Tier 2+（认证、外部凭据、破坏性/不可逆变更）始终不允许自动批准。档位仅调节 Tier 0/1 的自动执行范围。

**③ 不可验证不能冒充已修复。** [`lib/autonomy/action-postconditions.ts`](https://github.com/backenly/backenly/blob/main/lib/autonomy/action-postconditions.ts) 区分 catalog 已证实、已证伪和读取失败，并要求探针复查与回归检查。该文件当前显式登记的后置条件只有 `ADD_COLUMN`，不能由此推断全部修复类型都已覆盖。

**④ 监控「用户是否还在聊天」会错误地判断系统是否需要维护。** [`lib/autonomy/activity-gate.ts`](https://github.com/backenly/backenly/blob/main/lib/autonomy/activity-gate.ts) 的源码注释记载：早期只根据近 30 天 ConversationMessage 判断是否活跃，导致通过 MCP 细粒度工具调用、或长期服务真实流量但没人聊天的后端可能被排除在自愈之外。现改为参考 API 流量、受治理的变更、会话及创建时间。注释提及某项目 47 天没有消息而停止维护；这是开发者自述，尚非独立事故报告。

### 1.4 Composable Test：为何是「条件 Core」

**可在 1–2 天组合**：Supabase/Postgres + MCP + Agent + SQL migration + 定时检查 + 审批页，足以复刻单个 happy-path 演示，甚至简单的「缺索引→补索引→验证」。

**不能因此声称复刻稳定核心体验**：真正关键的是统一且不可绕过的变更内核、真实状态读回、可恢复的版本链、权限强制、误修复熔断、异常情况下仍可保留人的授权边界。这是持续运营责任的改变，不能只靠拼装一张 Dashboard 得到。

**判定**：Composable but Structural，条件 Core。它不满足「完全全新模式」，但有足够具体的开源实现证据，值得作为持续产品档案研究；**一旦独立部署显示只是拼装控制台、风险隔离不可靠，必须降级**。商业价值与代码量不是入选理由。

### 1.5 Human / AI / Deterministic Software

| 角色 | 旧方式 | Backenly 设计 |
|---|---|---|
| Human | 手动执行迁移、巡检、批准、回滚 | 定义目标、风险边界，批准高风险变更，承担生产责任 |
| AI | 生成 SQL/API 和修复建议 | 根据意图提出结构化变更、辅助诊断 |
| Deterministic Software | 提供数据库和监控 | 维护真实状态、权限、快照、不可弱化的验证、低风险自动修复和审计 |

### 1.6 事实 / 推断 / 未知 / 最大反证

**已确认（源码/官方）**：仓库有受治理的变更机制、三态验证、自治级别、活动门禁与自托管说明；官方 README 明示部分 PostgREST 共享 cluster 限制。

**合理推断**：让控制层而不是 Agent 判定执行成功，可降低「AI 自证成功」问题；以真实 API 活动决定是否持续监控，更符合生产业务的状态。

**未知**：生产级误修复率、可逆操作的真实恢复成功率、并发和权限安全审计、长期稳定性、用户采用率、各类自愈规则覆盖率。尚无独立部署结果。

**重要风险**：`autonomy-level.ts` 对读取项目设置失败有 `AGGRESSIVE` fallback；即使 Tier 2+ 仍必须人工审批，也需要专门测试「用户原本设 OFF，但设置暂时不可读」是否会出现 Tier 1 自动动作。不能由静态代码推断已发生安全事故。另需检验回滚能否覆盖间接副作用、修复循环是否震荡、以及业务模型是否正确。

### 1.7 Pattern 比较：真正新增了什么？

| 已有模式 | 关系 |
|---|---|
| #05 AI Build → Software Run → AI Repair | AI 构建、确定性运行与修复 |
| #13 Deterministic / Probabilistic Split | 自愈安全区与 AI 建议分离 |
| #14 Governance / #15 Proposed Action | 受治理动作与人工审批 |
| #17 Judgment Queue | 人处理高风险例外 |
| #26 Agent-facing System of Record | 后端成为可信状态与动作层 |
| #29 Runtime + Source + Telemetry | 真实运行证据决定是否执行 |

**它真正新增的是具体实现中的责任整合**：`Backend Change → Guarantee → Finding → Approval/Auto-fix → Independent Verification`，使维护成为默认生命周期，而不是上线后的临时补丁。现有模式已能表达这个组合，因此**不新增 #31**。

### 1.8 可迁移原理、最小复刻与不值得抄

**本地 Agent**：保留现有 Runtime/CLI/MCP，建立最小 `GovernedAction` 对象：`intent → proposed_action → risk_tier → precondition → approval? → execute → independent_postcondition → evidence → rollback`。先挑 3 类可逆操作，使用隔离数据库和确定性断言，禁止任意 SQL 直接写生产。

**AI 原生研发**：把「Agent 说做完」改为「真实系统读回 + 独立验收」；验证不可达必须保留 `inconclusive`。

**应急管理 B/G**：检查、隐患、整改、复核也应拥有独立状态与不可被 Agent 改写的闭环条件。提醒可以自动化；正式督办、风险等级修改、隐患关闭需要分级授权和专家裁决。AI 可以生成候选证据，不能自己确认自己的结论。

**不值得抄**：重写整个 BaaS、把定时巡检频率当成创新、把规则修复说成 AI 推理、没有独立验证就开放自动关闭或删除。

**最小验证**：隔离库准备 12 个用例（4 个安全修复、4 个危险变更、4 个异常），记录自动正确修复率、错误放行、不可验证误报成功、回滚成功率和人工时间。**继续跟踪 5/5。**

## 2. Maturation 重点：Specsight —— 「代码描述了什么」不等于「线上真实运行了什么」

**来源**：[官网](https://specsight.app/)｜[FAQ](https://specsight.app/faq)｜[自动同步](https://specsight.app/docs/automatic-syncing)｜[场景编辑](https://specsight.app/docs/features-and-scenarios)｜[Roadmap](https://specsight.app/vision)。**Observe；Tracking 4/5；Novelty 2/4；Evidence B。**

Specsight（10/25 已有发布记录，10/31 再次上榜）读取 GitHub/GitLab 代码，提炼 `Feature → Scenario(Context, Action, Outcome) → Product Map → Change`，供产品、销售和客服理解实际软件行为；每次 release 增量更新，手工修订的场景也会留在知识库。它强化 #12 Source → Self-maintaining Artifact、#25 Business Semantic Layer、#29 Operational Model，不构成新 Pattern。

**本轮真正新增的证据与反证**：
- FAQ 明确承认 Jira/Linear「计划 vs 实际」Gap Analysis 尚在 Roadmap，不能视为已交付。
- 官方自动同步说明：代码变更更新受影响场景，人工修改可保留；这带来「人工解释与代码推断不一致时以谁为准」的问题。
- 官方 FAQ 声称代码生成的场景即对应真实产品行为。但源码并不覆盖线上 Feature Flag、配置、权限、数据状态、外部依赖和实际用户路径。**源码是证据，不是生产真相本身**。
- 官方 FAQ 声称一个项目可关联多个仓库，Roadmap 页面仍将 Multi-repo 标为 Scoping，两个官方页面状态不一致；在真实使用前不能确认当前支持范围。

**Composable Test**：代码扫描 + LLM + Git diff + SQLite/Markdown + MCP 可组合主要体验。若没有 Runtime/Telemetry 和发布环境校验，不能称为「真实产品可观测性」。继续 Observe；不新增档案。

**对 AI Radar 自身的提醒**：自动生成的「功能档案」也可能漂移。必须保留证据来源、观察日期、已验证范围和人工修订的出处，而不能把模型总结写成「真实运行事实」。

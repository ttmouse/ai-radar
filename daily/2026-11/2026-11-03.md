## 1. Fresh 重点 Observe：Beacon（跨 Coding Agent 的可审核记忆晋升）

**来源**：[11/02 Product Hunt 发布](https://www.producthunt.com/products/asymptotelabs)｜[开源代码](https://github.com/asymptote-labs/agent-beacon)｜[Cross-Harness Memory 官方 Docs](https://docs.beacon.sh/concepts/cross-harness-memory)｜[Beacon Skills](https://docs.beacon.sh/concepts/beacon-skills)｜[数据脱敏限制](https://docs.beacon.sh/security/retention-redaction)。  
**结果：Observe；Tracking 5/5；Mechanism Novelty 2/4；Evidence B（开源与详细 Docs 可核查，缺少跨项目长期效果）；不新增 Pattern。**

### 1.1 真实问题、旧流程与新流程

真实问题不是“Coding Agent 记不住聊天”，而是同一项目在 Claude Code、Cursor、Codex 等工具里反复出现调试、部署和约束发现；知识被留在一次性 Session 中，下一次 Agent 不知道哪些经验已验证、哪些已经过期。

**旧流程**：Agent A 排查问题 → 对话与命令留在 Agent A 的会话 → Agent B 重新探索 → 人重复解释 → 项目文档靠人工偶尔补充。

**Beacon 提出的新流程**：跨 Harness 采集 Session/Prompt/Tool/Command/File/Approval Trace → 标准化本地 JSONL → 选择轨迹并评价是否含可复用经验 → 生成 Memory Candidate → 人审核并明确适用范围 → 批准为项目级 Memory → 通过 MCP 检索或安装为 Agent Skill → 后续 Agent 在工作前主动召回。

**Mechanism Delta**：把执行轨迹转为“带来源、范围、人工批准的知识候选”，让 Context 从工具私有会话转移到项目共享资产。但这种责任分配已与 #19 Organization Learning Loop、#21 Shared Artifact、#27 Context Belongs to Work 及 #13 确定性/概率性分工高度重合。

### 1.2 最关键的官方细节：宣传的 self-improving 不等于无人值守的自动学习

[官方 Cross-Harness Memory](https://docs.beacon.sh/concepts/cross-harness-memory) 明确写出：Memory 工作流是 **opt-in、local-first、review-gated**；Hook 不自动运行评价，也不会自动重写规则或安装 Skill。评估器返回成功概率、可复用性概率、证据支撑概率，**不生成可直接采用的经验文本**。通过门槛后成为 Candidate，仍由 Agent 结合原始 Trace 草拟 Lesson，最后需要 Human 审核批准。

公开默认筛选条件：task_success 概率至少 0.50，三项概率均值至少 0.60。这是“值得审查”的弱筛选阈值，不是“已经正确”的可信证明。Approved Memory 按项目存于 memory.db；Skill 安装到项目 .agents/skills；本地 MCP 提供只读搜索和 Context 获取。Cloud Memory 与 Local Memory 不自动互相同步。

因此要分清三个状态：
1. **Captured Trace**：发生过什么（包含错误与失败）。
2. **Candidate Lesson**：模型/人认为值得提炼什么（尚未授权成为知识）。
3. **Approved Memory / Skill**：经过人审核、在某项目与适用条件下可复用的经验（仍可过期）。

官方 Product Hunt 创始人回复称，未来运行轨迹可以用于识别失效 Skill、更新或淘汰旧知识；但当前公开 Docs 并未证明存在无需人工审核的可靠自动撤销/替换闭环。**不能把愿景当作已交付功能。**

### 1.3 Human / AI / Deterministic Software 的分工

| 角色 | Before | Beacon 目标分工 |
|---|---|---|
| Human | 反复讲解项目经验，人工补文档 | 判断候选知识是否准确、适用范围、是否可推广/废止 |
| AI | 执行当前任务、偶尔生成总结 | 从 Trace 提取候选经验、建议复用、在后续任务召回 |
| Deterministic Software | 仅保存各自会话 | 统一事件、关联项目/Worktree、保存 Provenance/审批状态、提供只读检索、控制 Skill 安装 |

**已确认**：跨 Harness Trace 采集；手动评价与审查；候选与批准态分离；项目级持久存储；MCP/Skill 复用；部分隐私和采集限制。  
**合理推断**：长期积累有机会降低重复排查时间；人工 Gate 有助于抑制错误经验晋升。  
**未知**：实际经验采纳率、错误 Memory 污染率、跨分支冲突处理、长期知识过期速度、复用是否提高任务成功率、维护成本。  
**分析判断**：值得跟踪，但目前是已有学习/Context 模式的清晰工程产品化，非独立新模式。

### 1.4 Composable Test 与最大反证

用本地 Agent Hook/Transcript、SQLite、定时抽取、LLM 打分、Markdown Skills、MCP 只读服务和 Git Review，1–2 天可以拼出针对单个仓库的主要体验。要覆盖 20+ Harness 并保证跨项目安全、去重、脱敏和回滚并不简单，但复杂性不是新机制的充分条件。

**Composable Test：Composable / 已有模式的结构化组合 → Observe，而非强 Core。**

最大的两个反证：
- **成功轨迹不一定包含正确经验**：某次问题解决可能依赖偶然环境、临时版本或错误的因果归因；task_success 0.50 只是候选门槛。若没有独立回归验证，经验会变成“有出处的错误”。
- **跨分支/环境失效**：同一仓库不同分支需要相反的解决方案；项目级 Memory 不等于已经具备 branch/commit/runtime 精确适用性。创始人在 11/02–11/03 Product Hunt 回复中建议用户自行决定是否跨分支共享 Markdown 经验，尚不能视为系统自动隔离的证据。

[安全文档](https://docs.beacon.sh/security/retention-redaction) 也承认脱敏为模式匹配：无标签、无可识别格式的秘密值可能无法识别。对于客户项目，不宜默认将完整 Trace 上传云端。另有 [2026-11-03 开源 PR #1164](https://github.com/Asymptote-Labs/agent-beacon/pull/1164) 报告 Windows 静默卸载可能因进程退出竞态意外重启；这是具体部署风险报告，不代表已独立证实所有版本均受影响，也与 Memory 机制新颖性无关。

### 1.5 对本地 Agent、产品研发与 B/G 的可迁移原理

**最值得复刻**：将经验建成带生命周期的对象：
- Trace（来源、时间、项目、Commit、工具、结果）
- Lesson Candidate（主张、证据引用、适用条件、冲突候选）
- Review Decision（批准/驳回/替代、审核人、理由）
- Active Memory（版本、适用范围、失效条件、最后复测）
- Skill（经批准的可执行知识，不等于原始对话）

本地 Agent 已有 CLI、文件访问、MCP 和 Runtime，不值得重新实现全量 20+ Harness Collector、Cloud Console 或为了“自动学习”而自动改写项目规则。先挑 20 个重复问题，做“有/无审核 Memory”对照，记录复用成功率、错误建议率、节省的重复探索时间与过期误用率。

**对应急管理**：专家一次检查的判断不应自动升级为辖区统一检查口径。区分“某企业一次检查结论”“专家可复用经验”“正式政策/检查规则”；每次晋升都需来源、权限、有效期和适用范围。旧标准应能撤销或标记失效。

## 2. Fresh 第二个 Observe：Hyperresearch（可检查的研究证据收据）

**来源**：[11/02 Product Hunt](https://www.producthunt.com/products/hyperresearch)｜[官网](https://hyperresearch.ai/)｜[Verification Receipt 说明](https://hyperresearch.ai/verification-receipt)｜[DRACO 测试方法，11/02 更新](https://hyperresearch.ai/benchmarks/draco)。  
**结果：Observe；Tracking 4/5；Novelty 2/4；Evidence B。**

**真实问题**：Research Agent 给出带引用的长报告，但引用可能指错、只支持句子的一半，多个新闻链接可能来自同一篇通稿。用户难以逐条验证，后续研究又重复搜索。

**旧工作流**：提问 → 搜索 → 生成带引用的报告 → 人逐条打开来源、手动核查 → 下次重新搜索。

**新工作流**：检索并保留来源到 Vault → 生成 Claim 与 Citation 关联 → 对引用句做 supported/partially-supported/unsupported/wrong-source 判定 → 对引文逐字核验、DOI 撤稿状态、同源转载做聚类 → 产生可读取的 Verification Receipt 与 Ship Gate → 下次研究优先复用 Vault。

**重要事实与限制**：官方说明 Receipt 有每条引用的判定与证据摘录；默认 sample: all，但可配置抽样，记录 checked/not_checked。其自述的撤稿检查存在 Crossref fallback 字段错误，不能覆盖所有撤稿；文字校验不覆盖图表图片与音频。官方更明确指出：**supported 只意味着“来源这样说”，不意味着“来源本身正确”**。部分 partially-supported 默认不会阻断发布。来源独立性聚类是审计信息，默认不构成发布 Gate。

官方 DRACO 2026-11-02 页面报告 Hyperresearch 10 项平均 77.7、Claude 73.0；这是**厂商自测**，10 项样本、各系统配置/完成任务数不同，不能独立证明全面领先。研究源数和引用数多也不等于事实质量高。

**Composable Test**：多搜索源 + SQLite/全文索引 + Claim Extractor + LLM Cite Checker + 引文匹配 + Gate 可以在 1–2 天完成主要流程原型；它是 #24 Evidence Gap、#27 Context Belongs to Work、#13 Split 与 #10 Artifact Semantic Object 的组合，尚无独立新 Pattern。若未来证明 Receipt 成为组织正式交付/审核对象且显著改变研究者默认工作流，再评估 Core。

**对 Radar 的直接启发**：每日结论不应只留“参考链接”，应尽可能记录 Claim → Source Passage → Verification Status → Confidence → Independence Cluster。相同厂商宣传被五家媒体转载，不能计作五份独立证据。对于每个 Core 的强判断，至少分开核验“引文准确”“来源可信”“结论可复现”。不值得复制其 40+ 数据 API 或长耗时 Deep Research 服务。

**最大未知**：实际错误引用检出率/误报率、独立人工对照、跨研究项目 Vault 的失效管理、用户是否查看 Receipt 而非只相信 passed 标志。继续跟踪 4/5。

## 6. Radar 自检：Methodology 与 Pages

- **Pages**：回读仓库 docs/index.html，确认已有 Methodology 一级入口、动态读取 methodology Markdown 与 Changelog、产品搜索的代码；线上 Pages 地址在本轮外部网页读取失败，**无法独立验证浏览器交互与移动端效果**。未观察到确定的新缺陷，不盲目改版。千条级检索仍需在可操作的浏览器中验证后再定方案。
- **数据**：无新增 Core，因此 products/、data/apps.csv、patterns/patterns.md 均保持不变；README 只更新日报日期/导航。未创建阶段性 Full Research，因为今天没有触发阶段性专题报告。

## 7. 今日结算

**Core 0；Observe 2（Beacon、Hyperresearch）；Reject/去重 4；Maturation 3；新正式 Pattern 0。**

> **今日产品创新养料**：AI 能捕获更多轨迹、检索更多来源，却不意味着它自动拥有更可靠的知识。真正的长期资产需要经历 **Trace / Source → Candidate Claim / Lesson → Independent Check → Human/Policy Approval → Versioned Memory / Business State**。人负责授权和最终责任；AI 负责提炼与质疑；确定性软件负责来源、版本、状态与可撤销性。**“曾经做过”不等于“应该复用”，“来源支持”不等于“事实为真”。**

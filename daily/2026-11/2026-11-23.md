## 重点观察：Databricks Genie ZeroOps——从运维告警转为可审查的修复工作对象

**来源与时间**：2026-11-19 Databricks 官方 Public Beta 更新（属于成熟期新证据，而非 11/23 新品）：https://www.databricks.com/blog/genie-zeroops-now-public-beta-autonomous-agent-fixes-data-pipelines-lessons-80000-customer 。2026-06-16 初始介绍：https://www.databricks.com/blog/introducing-genie-zeroops 。

**真实问题**：数据管道故障并不只来自代码错误，也可能来自上游 Schema、数据质量、运行环境与企业特定规则。单一 coding agent 缺少 lineage、作业日志和生产上下文；人需要在多个系统中追查根因。

**旧工作流**：监控产生告警 → 数据工程师查看日志/血缘/表状态 → 结合团队经验判断根因 → 修改代码 → 提交 PR → 测试/上线。

**新工作流（已公开能力）**：后台 Agent 持续监控工作负载，利用 Unity Catalog、metadata 和 lineage 调查异常；将问题放入共享团队 inbox；结合自定义业务指令提出修复，并生成一键 PR 供人审查。6 月产品定位是后台发现和建议；11 月的变化是从私测转 Public Beta，新增共享 inbox、团队通知、业务指令与 PR 交付。

**机制 Delta**：故障从「需要人跨系统收集证据的告警」变成「持续维护、带上下文、可审查修复提案的工作对象」。价值不在“AI 会修代码”，而在证据链、团队协作和可控执行闭环。

**Composable Test（v2）**：用 Databricks API/日志/lineage + Agent CLI + GitHub PR + Slack 可以在限定范围搭出大部分 happy path；但稳定生产的权限隔离、真实血缘与跨团队业务指令不一定能在 1–2 天内复制。分类为 **Composable but Structural / existing pattern extension**：有真实工作流变化，却与已有 #05/#17/#20/#24/#26/#29 高度重合，故不晋级新 Core。

**Human / AI / Deterministic Software**：Human 负责定义业务目标、补充公司特定知识、审查修复 PR、批准上线；AI 负责主动发现异常、跨日志/血缘调查、提出修复；确定性软件负责作业/表/血缘真值、权限、Git diff、测试、合并和部署控制。

**架构证据边界**：
- 已确认（官方披露）：Unity Catalog、metadata、lineage 访问；后台调查；共享 inbox、通知、PR、自定义指令；官方称从 80,000+ 客户 pipeline issues 中迭代，并在数百客户私测。
- 合理推断：共享 inbox 使故障从个人告警变为团队可追踪的处理对象；公司指令可能降低“通用修复建议”与实际运行规程之间的偏差。
- 未知：具体 Agent Runtime、Memory 生命周期、Tool Schema、审批原子性、失败恢复、自动修复成功率、误报率、独立 Eval；80,000 是观察到的问题数量，不是修复成功数。

**对 AI 产品设计**：将异常、证据、建议、审查、执行结果作为同一可追溯工作对象；不要让 AI 的自然语言成功宣称替代真实业务状态。

**对 AI 原生研发与本地 Agent**：已有 CLI、浏览器、MCP、文件访问时，可直接做最小实验：周期读取日志/数据血缘 → 建立 issue ledger → 生成修复 PR → 测试结果与人工审批关联。无需复制 Databricks 数据平台或开发通用运维 Agent。

**对应急管理/B/G**：将 AI 异常发现与专家检查流程统一为“待调查事项”：主体、证据、缺口、候选结论、责任人、审批、文书、整改状态各自有独立字段。AI 可补证据并建议处理，但不能把建议直接当作隐患闭环。

**最大未知/反证**：如果共享 inbox 只是现有告警系统的 UI 包装，PR 仍是普通 coding agent 输出，且没有显著降低人工调查时间，则没有强机制增量。官方 80,000 问题样本不等于生产效果。**继续跟踪 4/5；机制新颖度 2/4；证据成熟度 B（厂商公开 Beta，独立效果仍不足）**。

**与历史 Pattern 比较**：#05 AI Build→Software Run→AI Repair，#17 Judgment Queue，#20 Agent Ops，#24 Evidence Gap→Investigation，#26 Agent-facing System of Record，#29 Runtime+Source+Telemetry Operational Model 已能解释核心机制。真正新增的是数据血缘与团队业务指令的成熟交付证据，不是新模式。

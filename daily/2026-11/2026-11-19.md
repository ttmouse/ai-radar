## 1. 重点观察：S.Space（Observe；跟踪价值 4/5；机制新颖度 2/4）
- 官方入口：https://s.space ；发布和创始人问答：https://www.producthunt.com/products/s-space （2026-11-18）。
- **真实问题**：团队每个人有自己的 Claude Code/Codex 等 Agent，但项目上下文、决策、工作交接散落在个人会话，重复解释、协作不可追溯。
- **旧工作流**：个人分别指挥各自 Agent → 人工复制上下文 → 人工分派任务 → 汇总输出与复核。
- **新工作流（厂商描述）**：人和来自不同厂商的 Agent 加入同一 Room；共享 Commons 文档、表格、任务上下文；Agent 在 Room 中发送交接消息，接收方执行并返回结果；人审批关键动作。
- **具体机制**：① Context 属于 Room 而不是个人 Agent；② Agent 作为房间成员，受历史可见性设置限制；③ 新加入 Agent 可读取 Commons 的长期资料，而不是默认拥有完整历史；④ 交接以可见消息保留；⑤ 不同 Agent 可配置是否需要 @mention 才响应；⑥创始人称按人收费而不是按 Agent 收费。
- **已确认事实（公开声明层）**：上述功能和规则来自创始人在 Product Hunt 的逐条答复；产品已公开发布。另据其 Built With 页面，使用 Composio、Clerk、Claude 和 Codex 等现有组件：https://www.producthunt.com/products/s-space/built-with 。
- **合理推断**：Room 作为 Context 与协作的权威边界，能降低跨 Agent 的重复解释成本；历史可见性与 Commons 分离体现不同信任/知识范围。
- **未知**：Room 级并发写冲突如何解决；角色/Agent 权限是否在工具调用处强制执行；新需求写入后正在运行的 Agent 是否能即时感知；跨模型任务成功率；执行回滚、Eval、Memory 摘要机制及企业级审计能力。不可把创始人说明当作独立验证。
- **架构分层**：Human 决定目标、共享范围和审批；AI 执行、交接、总结；Deterministic Software 应当强制成员可见性、权限、版本、审批和对象状态（是否已全面实现未知）。Runtime：可接入已有 Claude Code/Codex（公开声明）；Context：Room/Commons（公开声明）；Tool：Composio 集成（公开声明）；Memory、Approval 的内部执行与 Eval：缺独立证据。
- **Composable Test**：Slack/Matrix 房间 + MCP/CLI Agent + 共享文件/数据库 + 任务队列 + 审批 + 审计，1–2 天内可复刻限定团队的 80% 可见体验。困难在于真实多人权限、并发一致性、跨 Agent 长期稳定性，而不是新原语。因此不晋级 Core。
- **与历史比较**：#27 Context Belongs to Work 已定义上下文归属于任务/Room；#21 AI Work as Shared Artifact 定义共享工作状态；#22 Agent as First-class Identity 定义 Agent 身份/权限；#04/#19 涉及组织上下文与记忆。**真正新增**：将“Room 成员历史可见性”与“可持续 Commons”组合，具体化跨供应商 Agent 共享上下文的产品边界，但未证明独立新模式；不新增 #31。
- **可迁移原则**：共享上下文不等于共享权限；聊天历史不等于长期业务知识；交接可见不等于执行结果可信。
- **本地 Agent 复刻**：用现有 Runtime、CLI、MCP、浏览器和文件访问搭建一个 Room Ledger：共享 Brief、版本、Agent 成员及授权、交接记录、动作提案、执行回执；测试需求中途变更、后加入 Agent 的历史可见性、并发写入冲突。不要优先复刻通用团队聊天软件、全部 Agent 连接器或商业计费。
- **应急/B/G 迁移**：围绕“责任主体/检查事件”建立共享上下文，专家、网格员、AI 检查 Agent 都可参与，但台账、证据、隐患结论的写入权限由业务系统核验；新增 Agent 不应天然看到全部历史或敏感资料。
- **反证与高估风险**：如果 Commons 只是共享文件夹、交接只是聊天消息、权限无法约束真实工具操作，那么主要是协作包装。下一次重点查 Room 并发版本控制、跨 Agent 真实完成率、权限执行点、撤销与审计。

## 1. 今日重点 Observe：Agno CompanyOS（Maturation）

**来源**：[官方发布（2026-10-23）](https://www.agno.com/blog/introducing-companyos)｜[官方完整使用流程](https://docs.agno.com/agent-platform/company-os)｜[AgentOS](https://docs.agno.com/)｜[Agno GitHub Issues](https://github.com/agno-agi/agno/issues)。  
**结果：Observe；Tracking 5/5；Mechanism Novelty 2/4；Evidence B（官方文档和可检查框架，缺少独立长期工作结果）；不新增 Pattern。**

### 1.1 真实问题与 Before → After

传统 Agent 的起点是“有人提出任务”：人发现需求/缺陷/文档落后 → 人整理需求和证据 → 人建立 Project/Task → Agent 执行 → 人审核。定时 Agent 虽可发现问题，却经常生成零散通知，不能自然归属于持续责任。

CompanyOS 将 **Product 定义为持续责任域**，为其配置 Sources（代码、文档、反馈）、Routines（定期发现值得做的工作）、Projects（明确结果）、Tasks（执行单元）和审核状态。它不是单纯增加定时器，而是试图把“发现应该做什么”从人的待办整理工作转移给持续运行的软件/Agent。

新流程：Human 定义 Product 的责任、目标和 Sources → Routine 定期读取真实资料并检查已有 Project/Task → Agent 提议有证据、有验收标准的工作（没有有用工作就不创建）→ Human 接受/调整 → 执行 Agent 在已授权环境中工作 → Human Review 结果 → 确定性软件保留状态、运行历史和边界。

**Mechanism Delta**：从“Agent 执行给定任务”，转为“围绕持续责任域主动发现、提议、执行和复核工作”。但这一方向与历史 #06、#08、#15、#17、#27 有明显重合。

### 1.2 关键机制与产品证据

1. **责任先于任务**：Product 是长期责任对象，Project 是有限结果，Task 是执行单元；Routine 不是一个新 Task，而是可反复发现任务的机制。官方 10/23 博客明确了层级。
2. **主动发现必须去重和允许无动作**：官方文档内置 `agentos-maintenance` 默认关闭，每日 09:00 UTC 运行时最多提出三个改进，要求先查现有任务；没有值得做的事应不创建工作。
3. **批准项目 ≠ 批准执行 ≠ 合并代码**：官方文档区分 Project 审核、Task 接受与执行、结果 Reviewing、GitHub PR Merge；不把任务状态当作代码实际部署状态。
4. **授权有硬边界**：官方 FAQ 称完成的 Task 必须由人审核，自动接受新 Task 仅能在指定 executor、scope、count、expiry 限制内启用；例子默认 `auto_accept=False`。运行需要 durable queue；SQLite 用于本地、PostgreSQL 用于生产。
5. **配置与运行状态分离**：初始代码声明创建 Routine 后，用户在 UI 修改的调度/启用状态不应被后续声明覆盖。责任与运行状态需持久保存。

### 1.3 Composable Test：为何不晋级 Core

用现有 Agent Runtime + cron/Automation + SQLite + GitHub/Linear + MCP + 审批界面，1–2 天可以拼出“扫描反馈 → 生成任务 → 人确认 → Agent 做事”的大部分体验。稳定的责任域、跨轮去重、权限、运行历史和真正的业务闭环并非一两天就可靠，但 **CompanyOS 没有证明一个现有 Pattern 无法解释的全新对象或默认交互原语**。

最近邻比较：

| 已有 Pattern | CompanyOS 对应 |
|---|---|
| #06 Persistent State → Proactive Action | 责任域长期存在，Routine 主动触发 |
| #08 Observe → Detect Pattern → Propose Automation | 从 Sources 发现值得执行的工作 |
| #15 Proposed Action as First-class Object | 发现的工作先成为可审查提议 |
| #17 AI Work Queue / Judgment Queue | Human 从列任务转向审核提议和结果 |
| #21 AI Work as Shared Artifact / #27 Context Belongs to Work | Product/Project/Task 持有共享工作上下文 |
| #30 Intent as Source of Truth | 责任目标约束执行和验收 |

**真正新增的具体证据**是这些模式被明确组织成 `Product → Routine → Proposed Project/Task → Approved Execution → Reviewed Result` 的责任链，尤其是“没有必要就不创建任务”以及“项目审核与代码合并不同”。这是可迁移的实现组合，**不是新 Pattern #31**。

### 1.4 重要反证：审批写在界面上，不代表运行时必然执行

本轮检查 Agno 开源仓库，看到近期**公开报告、附复现代码、仍为 open 的 Issues**。它们针对 Agno 框架的不同通用组件，**不能据此断言 CompanyOS 的相同代码路径已经受影响，也不能当作独立安全审计结论**：

- [Issue #11405（2026-10-30）](https://github.com/agno-agi/agno/issues/11405)：报告者复现 `HumanReview` 已在超时前拒绝，但 `continue_run` 在截止时间后调用，`on_timeout="approve"` 可能覆盖拒绝并执行步骤。核心问题是“人工已作决定”与“超时默认动作”的状态优先级。
- [Issue #11404（2026-10-30）](https://github.com/agno-agi/agno/issues/11404)：报告者称 `pre_hook` 抛出普通 `PermissionError` 时被记录为警告而工具仍执行；特定 `StopAgentRun` 类型才阻止。核心问题是“用于权限门禁的异常”不能被当作普通日志。
- [Issue #11406（2026-10-30）](https://github.com/agno-agi/agno/issues/11406)：报告 `PROPOSE` Memory 模式在工具层没有强制确认标记，`save_learning` 可直接写共享知识库。核心问题是“提示词说先批准”不是确定性授权。
- [Issue #11384（2026-10-29）](https://github.com/agno-agi/agno/issues/11384)：报告无效人工输入在校验报错后仍修改了暂停状态，随后继续运行可能消费已被拒绝的值。报告明确不主张远程漏洞或普遍认证绕过。

这些是**需要复测的风险报告**，并不证明实际生产事故。却揭示了一个产品设计层面的反证：把“人审”写在 UI、Prompt 或业务文案里，不等于运行时确实把“同一动作、同一参数、同一状态版本”绑定到人的批准。

### 1.5 Human / AI / Deterministic Software 分工

| 角色 | 传统 | CompanyOS 目标分工 |
|---|---|---|
| Human | 持续搜集、归类、拆任务、催进度、验收 | 定义长期责任和结果标准；批准值得做的工作与高风险动作；最终验收 |
| AI | 等待任务后生成/执行 | 从多源证据主动发现工作、提议 Project/Task、执行已批准任务、汇报证据 |
| Deterministic Software | 任务存储、调度 | 持久责任与任务状态、去重、权限范围、审批绑定、运行日志、失败/超时状态、真实外部结果验证 |

**已确认**：官方定义 Product/Project/Task/Routine、可配置 Sources、默认关闭 Routine、默认人工接受、任务审核与 PR 合并分离；GitHub 上存在上述 Issue 报告。  
**合理推断**：责任域比无主的定时任务更容易积累长期 Context、减少重复发现；严格审批状态机可以减少 Agent 误动作。  
**未知**：真实用户采纳提议率、任务质量、重复任务率、漏掉重要问题的比例、实际权限/审批实现覆盖率、长周期成本、跨 Product 冲突。  
**分析判断**：研究价值高，创新机制属于已存在模式的更明确产品化，暂不 Core；继续跟踪 5/5。

### 1.6 可迁移原理与最小复刻

**对 Radar**：不需要迁移 Agno。把“每天找产品”与“Radar 自身质量责任”分开，持续维护 `Responsibility → Evidence Sources → Finding → Proposed Improvement → Approval/Auto-safe Action → Outcome`。每次先检查已有问题和历史决策，允许“今天无需修改”。不要把日报任务变成无限自我优化任务。

**对本地 Agent/AI 原生研发**：在现有 CLI/MCP/SQLite 上增加 `Responsibility`（长期目标、资料来源、执行范围、验收标准）和 `Proposal`（证据、去重键、风险等级、候选动作、审批记录）。复刻发现-提议-执行的闭环即可，不值得抄整套 AgentOS/Control Plane/多 Agent 框架。

**对应急管理 B/G**：站长的“辖区重大隐患闭环率”是持续责任，不是一张固定任务清单；AI 可以从企业上报、视频看、现场看、风险变化中发现推进项，提出督办草案，但正式督办、风险等级变更、隐患关闭必须有业务权限和独立证据。检查可独立触发，不能因为 Product/Routine 模型就强迫每次检查都从任务出发。

**最小验证**：给一个责任域（例如每周应急风险异常复盘）和 20 条真实事件，记录：有效提议采纳率、重复率、重要问题漏报、审批误放行、超时后决策是否被覆盖、执行后业务状态读回成功率。若只是每天多生成几个待办，应降级为普通自动化。

## 2. Fresh 重点 Observe：Click Managed Agents API

**来源**：[11/01 Product Hunt 发布](https://www.producthunt.com/products/click-6)｜[官方 API 文档（标注 API 版本 2026-10-19）](https://useclick.ai/reference)。**Observe；Tracking 4/5；Novelty 2/4；Evidence B。** 同名产品 2026-01-05、08-12 已有发布，本次是第三次发布，不能把全部能力视作 11 月首次出现。

**实际问题**：嵌入 SaaS 的 Agent 执行时间长，进程重启、工具调用超时、断流后，应用很难判断任务究竟成功、失败，还是“已经执行但没拿到结果”。

**官方已确认的设计**：
- `Agent` 配置每次修改生成不可变版本；`Session` 持久保存；`Submission` 明确 `done/cancelled/failed`；`Entry` 与 `ToolCall` 保存执行轨迹。
- HTTP 接受请求用 `request_id` 做幂等；已接受输入持久化。Agent 可跨部署恢复，断开 UI 流不等于工作停止。
- **工具调用已经开始但结果未知**时，官方记录 `outcome="unknown"`，恢复时只重放安全的操作，要求应用到真实业务系统确认效果后再重试。
- 通过 Connection/Grant 约束每个 Agent 的工具；最终业务用户的鉴权、预算、审批、业务后置验证仍属于应用方。

**最值得保存的 Finding**：`accepted ≠ executed ≠ succeeded`；对外部副作用的 `unknown` 是必须存在的合法状态，不能由 Agent 猜测补全。它与 Backenly 的 `confirmed/contradicted/inconclusive` 形成跨产品独立证据：一类是“执行结果未知”，一类是“后置验证无法判定”，都反对把失败的观察通道当成成功。

**Composable Test**：Agent SDK + 任务队列 + SQLite + idempotency key + tool-call ledger + webhook 可以复刻核心体验；产品主卖点是 Managed Runtime，主要属于基础设施产品化，已由 #14/#15/#20/#22/#26/#29 解释，**不进 Core**。

**对本地 Agent/应急管理**：当“发送正式督办”接口超时，不能简单自动再发送一次。保存 Action ID、目标对象、请求参数哈希、审批版本、执行状态；先查询业务系统是否已创建督办，无法判定时进入人工例外队列。复刻状态机和幂等即可，不值得重新开发 Click 的托管浏览器/沙盒/运行时。

**未知/反证**：厂商自述的跨故障恢复是否覆盖任意外部副作用？不同工具的幂等性如何约束？实际长任务失败恢复率及租户隔离独立审计未知。**继续跟踪 4/5**。

## 6. 今日结算

**真正入选 Core 0；Observe 2（Agno CompanyOS、Click）；Reject/去重 5；Maturation 3；新正式 Pattern 0（仍为 30）。**

> **产品创新养料**：AI 原生组织可以把“发现应该做什么”交给 Agent，把“执行重复步骤”交给软件，但“是否值得做、是否授权、是否真的完成”仍是三道不同的门。尤其是审批必须绑定不可变的动作与参数；**一个会在超时或恢复时覆盖人工决定的系统，不是 Human-in-the-loop，只是有审批外观的自动化。**

# Airtop Agent Builder

**创新评分：★★★★★**  
**模式：AI Build → Software Run → AI Repair**

## 真实问题
很多浏览器自动化和业务流程自动化看起来适合 Agent，但如果每一步都依赖 LLM 判断，成本、延迟和稳定性都会很差；而纯脚本/RPA 又容易在网页结构或业务环境变化后失效。

## 旧工作流
人写自动化脚本 → 测试 → 部署 → 页面变化 → 自动化失败 → 人排查 selector / 流程 → 修复 → 再部署。

## 新工作流
人描述目标 → AI理解页面和流程、生成自动化 → 高频稳定步骤由确定性软件执行 → 环境变化导致失败时，AI重新进入诊断、修复和测试 → 人只在关键变化上确认。

## 核心机制
Airtop 真正值得看的不是“自然语言生成浏览器 Agent”，而是把 AI 放在**构建与修复**位置，把稳定运行交给传统软件。这形成了一个 AI 与 deterministic software 的循环，而不是让模型永远在线接管每一步。

## 为什么不是普通“加 AI”
如果只是 LLM + 浏览器操作，很容易被现有 Browser Agent 复刻。真正的产品机制变化是：AI 从持续执行者变成自动化系统的 builder / maintainer。

## Composable Test
技术上可以用 Playwright + Coding Agent + Eval + Cron 拼出，但需要把“生成—运行—失败检测—修复—重新验证”做成产品闭环。创新不在单个组件，而在职责重新分配。

## Human / AI / Software 分工
- Human：目标、审批高风险变化
- AI：理解流程、生成、诊断、修复
- Software：高频确定性执行、状态记录、触发异常

## 可迁移原则
> 不要让 AI 参与所有步骤。确定性工作编译成软件，不确定性工作再交给 AI。

## 对本地 Agent / B/G 的启发
应急检查、数据采集、后台录入等稳定步骤应尽量固化为 API/脚本；AI负责发现流程、生成逻辑、处理异常与维护。这样比“所有操作都让 Agent 点网页”更可靠，也更适合政府场景。

## 不确定性
真正难点是修复后的回归验证：如果没有稳定测试集和 approval policy，所谓“AI 自动修复”容易制造新的隐性错误。

## 跟踪判断
**强烈值得继续跟踪。** 它是理解 Agent 与传统软件重新分工的重要样本。

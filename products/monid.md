# Monid

**创新评分：★★★★★**  
**模式：Capability-on-Demand**

## 真实问题
Agent 的能力通常在部署前由开发者预先接好：要么固定一组工具，要么靠人维护插件/MCP 列表。随着任务越来越开放，真正的问题变成：Agent 如何在运行时发现“我缺什么能力”，并选择合适的提供者。

## 旧工作流
开发者提前配置工具 → Agent 只能在既定能力集合里工作 → 缺能力时任务失败或回到人。

## 新工作流
Agent 理解目标 → 发现能力缺口 → 搜索可用服务/工具 → 比较价格、质量与约束 → 获得能力 → 执行任务。

## 核心机制
真正的新点不是 API 聚合，而是把“工具采购/能力选择”纳入 Agent 的推理循环。能力不再是静态配置，而成为运行时对象。

## 为什么不是普通加 AI
普通 MCP marketplace 仍需要人选工具；Monid 的方向是 Agent 自己决定什么时候需要什么能力。

## Composable Test
可以用 registry + MCP + payment + router 拼装，但一旦把发现、选择、购买、调用做成自治闭环，就改变了 Agent 的基本能力模型。

## 可迁移原则
> 不要假设 Agent 的工具集合是固定的；让能力本身成为可发现、可比较、可授权的资源。

## 对本地 Agent / B/G 的启发
本地 Agent 可先从“动态工具目录”做起：本地脚本、CLI、浏览器、MCP、内部 API 都注册成带成本、权限、适用条件的 capability，Runtime 根据任务选择，而不是把全部工具一次性塞给模型。

## 不确定性
动态获取能力会放大安全、成本和供应链风险，因此必须与权限、Action Policy 和审计共同设计。

## 跟踪判断
**强烈值得跟踪。**
